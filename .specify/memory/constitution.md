# 草根黑客松情报局 Constitution

本项目是连接黑客松选手与主办方的带登录网站，帮助新人理解赛事要求、确定分工、
规划时间、找到合适的工具、设计参考与技能组合、保存成果并完成正式提交；
为主办方提供可配置的报名、沟通、赛事运营、正式收件与人工评审流程。
产品价值以真实参赛过程中的帮助衡量。

受众包括黑客松新手、已有参赛经验的选手和主办方。新人需要逐步指引，选手需要高效继续当前比赛与团队任务，主办方需要便捷发布和运营比赛。同一账号可承担不同授权身份，页面根据当前比赛和权限展示对应工作区。

本宪法约束后续需求规格、技术计划、任务拆解、实现和验证。
“必须 / MUST”“不得 / MUST NOT”表示强制约束；“应 / SHOULD”表示默认原则，
偏离时需记录理由。它不把尚未确认的技术选型或功能建议自动变成最终需求。

本文采用 [Spec Kit 官方宪法模板](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md)
的结构，将项目原则与具体功能规格、技术实施计划分开。
用户指定的 [鱼皮文章](https://ai.codefather.cn/library/2013071812962926593)
初始编写时仅能读取介绍 Spec Kit 的开头，全文中的额外约束未作为已知依据。

## Core Principles

### I. 新人可执行的参赛流程

- 产品 MUST 围绕真实参赛任务组织功能：理解要求、安排职责、管理时间和交付作品。
- 网站 MUST 为新手、选手和主办方提供清楚去向：开始参赛指引、继续我的参赛、主办方入驻与办赛工作台。新人是使用场景而非新增权限角色；不得强制选手重看教程才可继续任务，也不得为兼任主办方另建一套账号。醒目入口不代表已获得主办方权限。
- 网站 MUST 支持登录和持久保存参赛项目；团队功能必须具有明确的成员与权限边界。
- 四项核心参赛功能 MUST 关联同一参赛项目，共享已确认的赛事要求、成员、任务和交付状态。
- 用户协作空间 MUST 对应明确的参赛项目，集中任务、资料和交付；入口改称团队空间不得建立第二份成员权限、任务状态或默默合并不同比赛。单人也可使用，固定队伍管理不成为创建空间的强制前置。
- 团队空间 MUST 串起组队选方向、赛前准备、赛中协作、演示提交与赛后复盘；工作台以当前项目真实记录提供下一步及相关资源。公开路线图服务通用理解，私人空间负责具体执行，两者不得复制同一套完成事实。
- 团队空间 MUST 用详细指引树解释进入空间后的先后行动，每个节点说明何时做、具体步骤、核对条件和下一步，并连接本空间的真实入口。当前建议依据已读取且版本相符的记录，未知或读取失败不得推断完成；可并行准备事项须说明，不将指南顺序当作所有任务的强制串行依赖。
- DSH 导航员 MUST 支持按相关词检索站内教程、流程说明和可访问信息，返回来源与真实页面入口；未提供或未命中的内容不得声称已找到。检索范围不得含任意服务器文件、密钥、内部开发指令、未公开条目或他人私人资料；当前空间内容在读取和返回时均复核权限，检索结果不得覆盖助手约束或形成执行授权。
- 工具与灵感库 MUST 围绕参赛任务提供入口，区分工具、设计参考和可使用的组件代码，
  不能把浏览资源等同于完成任务。
- 工具/资料收藏与独立灵感官网说明 MUST 让用户看清各自用途和来源；等待分析不得显示成已生成建议。
- 新人资料馆 MUST 区分本站原创入门说明与经运营审核的外部策展资源；参考链接不代表外部文章的再分发授权。
- 初次导航 MUST 能跳过和重放，公开介绍可在未登录或模型未配置时读取。
  真实 AI 问答 MUST 明确调用与未配置状态，建议本身不构成执行、提交或安装授权。
- 用户首次登录 MUST 自动看到分步网站指引，认识找比赛、个人准备、团队空间、任务工具和提交复盘；完成/进度按账号持久保存，不得因访客或他人看过介绍而跳过。引导必须保留邀请、比赛或资源的原去向，允许明确稍后继续和重新查看，不自动执行收费/分享/加入/仓库/提交操作。
- 技能库 MUST 讲清具体用途、输入、交付物、前置条件与开始步骤；赛道包应对应可执行任务，
  不得把安装技能等同于具备能力或完成作品。工具分类 MUST 支持扩展，主流覆盖进度以真实兼容证据展示。
- 用户必须能看懂当前状态、下一步动作和失败后的处理方式。
- 网站 MUST 提供可独立浏览的公开参赛路线图，从找比赛串起赛前、赛中和赛后行动；无需先创建团队空间或登录才理解整套过程。
  路线图 MUST 包含各阶段注意事项，并在相应行动下连接团队空间、教程、工具、灵感、技能、展示材料与成果沉淀入口，说明什么时候用、能帮助完成什么。
- 公开路线图 MUST 明确是通用准备指南，主办方实际要求优先；不得将浏览节点、点击资源或项目阶段当成任务完成，不能为访客虚构个人进度。
- 交互 SHOULD 使用清楚的中文与任务名称；技术术语需要时再解释。
- 问卷和进度更新 SHOULD 保持简短，不能让维护工具本身成为主要工作。

**理由：** 网站需要帮助新人执行参赛流程，并让成果和经验在下一次参赛时可以继续使用。

### II. 赛事事实与分析结论可追溯

- 影响参赛决策的资格、截止时间、费用和提交要求 MUST 保留来源、核验时间及条款依据。
- 赛事事实、AI 推断和缺失信息 MUST 明确区分；无法确定的内容标记为待确认。
- 官方赛道名称、适用资格、评分重点和必交材料 MUST 以主办方实际公布的证据及规则版本为依据，
  团队选择的赛道必须能追溯到对应版本。没有划分赛道或信息不明时，应按统一要求或待确认状态处理，AI 不得编造官方赛道。
- 工具目录与技能套餐的通用分类 MUST 与官方赛道分别标示，不得用资源包分类替代主办方规定或推断参赛资格。
- 自动发现卡片 MUST 保留来源、摘录、抓取/分析时间与未知项；模型结果不得自动升级为 M03 已审核赛事。
  （2026-10-11 用户明确要求简化比赛页：卡片不再显示"未人工核验"标签，也不显示"免核验"说明；未核验事实仍保存在数据层，不得因此被当作已核验内容对外宣称。）
- 报名入口 MUST 来自实际获取的链接与报名证据，模型只能选择可核对候选，不构造地址。
  （2026-10-11 用户明确要求简化比赛页：缺少报名链接证据或报名截止时间未核实时，卡片不显示"尚未核实/暂未找到"占位文字，这些字段留空。系统仍 MUST NOT 编造链接或截止时间；留空不等于已确认，用户须自行向主办方核对。）
- 公开自动发现 MUST 只展示 DSH 已保存且状态为 active 的赛事分析卡片；报名状态、报名截止和开赛日期 MUST 作为独立字段显示。字段缺失时留空展示，不得把未知或已结束状态改写成开放，赛事时间和作品提交截止不得冒充报名截止，历史分析和项目保存快照仍保留。
  （2026-10-11 用户明确要求简化比赛页：不再展示"报名未知或已结束的比赛也保留"说明，也不在页面展示"已达到今日自动搜索上限"等后台运行状态；后台状态仍可在管理端查看。）
- 参赛建议 MUST 说明条件和证据不足，不得保证访问者符合资格、编造个性化匹配百分比或把旧分析补成已完成的新判断。
- 主办方认领已自动发现的赛事时，候选匹配 MUST 只作提示、**不得产生任何权限或归属**；未通过归属核实前 MUST NOT 改写任何公开内容。
  - 归属核实 MUST 依据可核对的材料（官方域名邮箱、可核对的官方声明、盖章授权文件、官方平台页互证），**MUST NOT 以机构名相似或来源域名相同直接判定归属**。
  - 认领 MUST 为显式授权关系并由平台当前管理员批准；机构负责人不能自审，`reviewer` 身份不自动获得批准权。
  - 同一场自动发现赛事 MUST 只能被认领一次；已被认领时后续申请 MUST 明确拒绝并说明现有归属。
  - 认领 MUST NOT 复制或删除自动发现记录：发现的原始记录与其不可变历史保持完整，主办方确认的值只写入其自己的赛事草稿与发布版本。
  - 撤回认领 MUST NOT 删除已发布的赛事、报名或评审事实，也 MUST NOT 自动回退成抓取版本。
- 公开赛事内容 MUST 能区分「自动发现的线索」与「主办方确认的事实」；只有后者可标注为主办方已确认，MUST NOT 把抓取结果或模型摘要升级为主办方声明。
- 用「待补字段」引导主办方填报时，该清单 MUST 为派生视图：MUST NOT 新增完成百分比、勾选表或第二份完成状态，浏览清单不等于任何确认。
  - 抓取证据与主办方确认值 MUST 分别留存并可区分；两者冲突时 MUST 同时展示依据由人决定，**MUST NOT 自动以任一侧覆盖另一侧**。
  - 补全 MUST 由本赛事当前工作人员执行，带版本校验；失败或并发冲突 MUST 保留输入并明确提示。
  - 时间字段 MUST 带时区，多阶段截止 MUST 分别记录。
- 平台对主办方的能力范围 MUST 明确说明且不得夸大：MUST NOT 表示平台负责收款/退款/开票、发送短信、接管选手私人备赛空间或私人 AI 对话、自动决定录取/晋级/获奖，或替主办方在第三方平台发消息。
  - 入驻或认领成功 MUST NOT 被表述为赛事质量、招生效果或获奖机会的保证。
- 持续搜索 MUST 说明查询、可访问页面、robots、频率与预算的覆盖边界；有界查询和分页不得宣称字面全网完整。
- 日期 MUST 保留时区；多个阶段的截止时间必须分别记录。
- 来源过期、冲突或采集失败时 MUST 显示状态，并提供纠错路径。
- 系统 MUST NOT 无依据认定赛事“内定”“不正规”或“奖金不会兑现”。
- 任何分数或推荐标签 MUST 定义含义、依据与适用边界，不得将其展示为事实保证。
- 工具与灵感资源 MUST 保留官方或原始链接、用途、最后核验时间和可用状态。
- 已确认采用 DSH 更新的灵感说明 MUST 基于实际取得、允许读取的官网文本生成并校验证据；固定候选元数据或编辑说明不得冒充真实 DSH 结果。
- 影响选择的费用、账号要求、技术栈与许可信息 MUST 标明来源和未知部分；
  不得把未核实的“免费”“可商用”或“比赛允许使用”展示为确定事实。
- AI 推荐资源 MUST 引用已审核条目或明确标记待核验，不能编造链接。
  设计灵感不得被展示为自动获得图片、品牌或代码的使用许可。
- skill 的来源、作者、文件版本、许可和适配环境 MUST 可追溯；公开仓库不得自动视为允许打包分发。
  镜像、再分发及组合包必须核对适用条件并保留必要许可与署名；许可未知时不得提供再分发安装包。
- 安装量、Star 和第三方评价 MUST 与本站任务测试分开。宣称好用或给出评分 MUST 说明任务、
  环境、日期、样本和评价依据，不得以热度宣称“全网最好”或保证效果。

**理由：** 错误信息会直接影响报名和交付，分析的可信度需要来自可核查的证据。

### III. 测评服务于任务分工

- 分工 MUST 提供成员自选职责与 AI 建议两种可执行方式，允许选择多个职责并在团队确认时调整。
  不清楚负责什么的成员可以使用 AI 提问帮助；已有明确意愿的成员不得被强制完成整套测评才可参与分工。
- 测评 MUST 结合实际任务、过往经历、岗位意愿与可投入时间；自评和试做证据分别记录。
- 题目可以动态变化，但能力维度、评分依据和评分版本 MUST 明确并可追溯。
- 百分比 MUST 说明是本次测评得分或有定义的任务匹配指标，
  MUST NOT 直接宣称为真实能力百分比、岗位成功概率或科学排名。
- 未经校准的不同题目和难度结果 MUST NOT 被直接用于统一能力排名。
- 分工 MUST 给出负责人、交付物、依赖、期限和推荐理由，并允许队伍修改。
  AI 建议必须结合当前官方赛道要求与全队可投入情况，向成员解释具体工作和推荐依据；建议不得自动成为已确认分工。
- 测试、文档、设计、需求整理和路演等贡献 MUST 被纳入任务安排。
- 团队缺少关键能力时 MUST 指出缺口，提供范围调整或协助建议；不得强行凑齐岗位。
- 实际交付反馈 SHOULD 用于修正分工，年龄不得作为能力推断依据。

**理由：** 分工需要回答成员接下来能交付什么，而不是给人贴永久标签。

### IV. 时间规划以可交付性为约束

- 计划 MUST 使用赛事实际截止时间、必交材料、剩余工作和成员可用时间。
- 计划 MUST 区分最小可交版本与可选功能，并体现任务依赖、集成、测试和提交缓冲。
- 每项执行任务 MUST 明确负责人、交付成果、验收条件、预计用时、计划开始时间、最迟完成时间和前置依赖；缺失输入须标记假设，
  不能只用“负责开发”或“负责设计”等方向名称代替可执行任务。
- 依赖 MUST 来自实际交接条件，可以并行开展的工作不得被强制串行。等待前置成果时，
  成员必须能看清在等谁、等什么，并查看当前权限和时间条件下可以先做的任务；不得虚构依赖已解除。
- 交接提示 MUST 引用真实任务、负责人和当前检查状态；只在当前计划、时间与前置条件允许时提示可以开始。并行准备建议不得自动变为已分配任务或改变既有依赖。
- 工时 MUST 标明为估算，并体现不确定性；不得把测评分数直接换算成开发速度。
- 推荐陌生工具或技能包时 MUST 计入配置、学习、试用与排错时间；临近截止时提供适用的熟悉工具或手动路径。
- 休息、学习和排错时间 MUST 计入容量；不得把比赛持续时间当成所有成员的可用工时。
- 关键输入未确认时 MUST 标记假设，输出草案，不得伪装成已核实的安排。
- 当必需工作超过容量时 MUST 明确报告不可行部分，并提出删减范围或补充协助的方案。
- 进度变化后 MUST 能重新评估计划；没有更新时不得假装知道实际完成度。
- 任务完成勾选 MUST 明确表示成员报告完成还是已经通过验收，成果与验收依据分别记录；
  勾选、AI 生成或通知发出均不得自动等同于验收通过。后续任务是否可开始须按所需交付条件判断。
- 当前任务状态、负责人和依赖变化 MUST 在当前有权限的队内成员之间可见，保留更新时间、修改人与变更记录，
  不得仅在操作者的浏览器中显示成功。并发修改须检查版本，发生冲突时保留本地输入并明确提示，不静默覆盖。
- 完成状态的误勾或更正 MUST 有清楚路径并保留原记录；已验收成果的更正须保留依据、相应权限和受影响依赖，
  不得通过删除历史让已确认的交付事实消失。
- 核心目标、负责人和截止安排的重大修改 MUST 可见并保留记录，不能静默应用。
- 系统 MUST NOT 承诺保证按时完成或默认所有比赛均为 48 小时。

**理由：** 规划需要及早暴露无法按时交付的风险，并帮助团队作出取舍。

### V. 仓库与本机操作可靠且有授权依据

- 网站登录、GitHub 身份绑定、仓库授权和具体操作权限 MUST 分别处理。
- 每次仓库写入 MUST 验证网站权限、应用授权范围和所需的操作人权限。
- 写入范围 MUST 与用户明确动作或已设置的自动化规则一致；AI 建议本身不构成写入授权。
- 上传或保存前 MUST 展示目标仓库、分支与文件变更，并检查不应上传的依赖和疑似密钥。
- 版本保存 MUST 处理队友并发更新、网络失败和重复操作；不得静默覆盖或丢弃他人成果。
- GitHub 凭据 MUST 仅在受控服务端使用，不得出现在前端、公开文件或普通日志中。
- 文件保存成功、作品运行验收、赛事正式提交 MUST 分别记录和展示。
- 操作成功 MUST 以实际返回或经验证的状态为依据；用户自报的提交状态须标明来源。
- 复杂冲突或权限不足时 MUST 保留待提交成果，并给出明确的恢复或处理路径。
- 本机技能安装 MUST 明确工具、安装范围、固定包版本、将写入的内容和前置条件；
  推荐、收藏、选套餐或复制命令不得自动构成执行脚本、覆盖已有技能或新增服务授权。
- 本机安装 MUST 处理同名冲突、部分失败与恢复，默认保留已有内容；恢复或移除不得删除用户后续修改。
- 命令已复制、文件已安装、客户端已加载和样例已验证 MUST 分别记录，标明用户自报或客户端回执来源。
  没有具备相应能力的本地桥接时，网站不得声称已完成本机一键安装。

**理由：** 操作更简单的同时，用户仍需知道改了什么、是否成功以及怎样恢复。

### VI. 最小权限与数据隔离

- 私人参赛项目、成员信息和测评数据 MUST 由服务端执行访问控制，
  不得仅依靠隐藏页面按钮或难以猜测的链接保护。
- 个人参赛准备、出行信息、账号画像和私人生成记录 MUST 与团队项目资料、共享任务和验收记录分别管理。
  整合入口或复用组件不得自动公开私人资料；共享范围与采用动作必须由本人明确选择。
- 同一项目的简介、目标用户、已完成内容和依据 MUST 提供经用户确认的复用方式，减少重复填写；采用时 MUST 核对当前项目权限与输入版本，
  展示可供用户确认的来源，并为本次生成保留输入快照。项目资料后续修改不得静默改写已有讲稿、PPT 或计划，私人画像也不得自动成为团队事实。
- 团队角色 MUST NOT 自动扩大 GitHub 的仓库权限。
- 邀请 MUST 支持有效期或撤销机制；加入团队不得顺带公开成员的所有私人数据。
- 邀请链接与二维码 MUST 对应同一受控邀请；原始令牌不得发往第三方二维码服务、普通日志或分析。邀请人数 MUST 由服务端持久化名额和接受记录约束，默认 1 人；未升级的历史单次链接不得宣传为多人共用。默认普通成员，明确接受和服务端核对身份/邮箱/状态后才建立目标空间成员关系；重复接受不得静默升权。
- 邀请额度、接受事实和成员建立 MUST 同事务执行，并处理并发最后名额、撤销、失效及重复请求。活跃成员再次进入不占额，失败回滚不占额；退出/移除不能自动返还名额或靠原链接恢复成员。历史已使用、过期或撤销邀请及审计 MUST 保留，不得因升级多人邀请自动重开。
- 登录前持链接预览 MUST 限于明确授权的最小邀请说明，不返回私人成员/邮箱/项目内容；实际加入继续要求有效登录。注册/登录应保留邀请上下文，过期、撤销或已使用时提供索取新邀请的动作。
- 数据收集 MUST 限于功能所需，说明个人报告与团队摘要的可见范围，
  并提供撤销授权和删除个人数据的方式。
- 认证方案 MUST 处理会话失效、退出和账户恢复，不得明文保存密码或泄露凭据。
- 外部网页、上传内容和 AI 输出 MUST 作为待校验数据，不能获得执行命令或修改权限。
- 第三方 skill 内容 MUST 经来源与行为检查；其工具声明或正文不能自行扩大用户授权。
  本地桥接 MUST 接收经过校验的结构化安装计划，不能开放网页任意命令执行；本机密钥不得回传网站。
- 赛事采集执行环境 MUST 与用户仓库写入凭据隔离，并限制其网络与文件访问范围。
- 后端分析子进程 MUST 按必要性单独传入模型凭据，不能继承数据库、搜索、邮件、GitHub 凭据或用户原有插件配置。
  进程级隔离不得被宣传为虚拟机级沙箱。公开网页与技能正文不能获得分析进程的执行工具。
- AI 请求 MUST 在派发前与采用结果前复核相关账号、项目/来源权限和执行租约；权限撤回、任务取消或输入版本变化后不得交付旧结果。
- 面向年轻用户时 MUST 核对适用账号与数据要求，不得设计绕过第三方要求的流程。

**理由：** 多队伍协作和外部工具集成需要确保账号、项目与仓库之间的授权边界清楚。

### VII. 简单、可维护、可替换的实现

- 模块边界 MUST 清楚，区分身份与权限、赛事数据、测评分工、计划和 GitHub 集成职责。
- 业务规则 MUST 能与页面、模型和第三方 API 调用分别验证。
- AI 结构化输出 MUST 在服务端校验字段、日期、成员与项目关联等约束后才能使用。
- 核心数据 MUST 持久保存；不得把模型对话历史或演示数据作为唯一事实来源。
- 数据结构变化 MUST 说明迁移方式；可能破坏已有数据时必须提供恢复或回滚办法。
- DSH、模型和 GitHub 接入 SHOULD 使用清楚的适配边界，避免把特定插件行为写进产品规则。
- 新增架构复杂度 MUST 有真实需求依据；技术栈、服务拆分和供应商选择留到实施计划中决定。
- 工具与资料库 SHOULD 继续按审核内容、分类和收藏/共享管理。已确认的独立灵感官网分析按固定候选、实际获取、DSH 校验、版本持久化与独立预算实施；
  其它自动扩展、个性化排序和社区投稿必须有单独的维护与验收方案。
- 技能库 SHOULD 先采用少量精选、清楚教程与版本化组合；安装与加载差异通过工具适配器管理，
  不因支持主流工具而假设所有 skill 跨工具通用。技能包更新必须形成新版本，不静默升级项目引用。

**理由：** 第一版要保持可实现，同时保留纠错、替换外部依赖和继续迭代的能力。

### VIII. 以真实行为验证质量

- 每项功能 MUST 有可观察的验收条件，区分演示效果、实际实现和仍未验证的部分。
- 权限隔离、时间计算、评分规则、关键数据变更和仓库写入 MUST 有相应自动化验证。
- 核心参赛流程 MUST 进行贯通验证，覆盖正常使用及典型失败后的恢复。
- 主要动作 MUST 按真实新人流程验收，覆盖首次使用、自选或 AI 建议分工、查看可开始的任务、报告完成、
  队友读取最新进度和接手成果；手机端还须验证主要按钮、表单、导航和结果可读性，不能只验收桌面截图。
- 外部集成验证 MUST 区分模拟服务与真实测试环境，不得把模拟成功说成真实操作成功。
- 代码接通、服务端已配置、第三方真实调用和容器实际运行 MUST 分别说明；缺少配置或目标环境验证时不得宣称已完成上线验收。
- 技能兼容 MUST 区分安装器声明、命令验证、文件安装和示例任务验证，按工具版本与操作系统记录。
  尚未验证的组合不得展示为已实测兼容，已安装不能替代交付物验收。
- AI 代码和方案 MUST 经适合该改动的运行、规则或行为检查，不得因生成成功就标记完成。
- 低影响、可逆的文案与样式改动 SHOULD 使用适当检查，不强制制造重复实现的测试。
- 发布判断 MUST 依据验证记录；未经解决的关键权限、数据丢失和错误成功状态不得带入发布。

**理由：** 新人依赖产品给出的状态，验证需要证明具体行为和失败处理可靠。

### IX. 外部依赖失败时仍可继续工作

- 模型生成和赛事采集 MUST 有超时、失败状态及合理的重试限制。
- 付费调用 MUST 有明确的调用数、输入/输出和费用限制，真实用量与保守预留分开记录，费率未知不得显示为免费。
  导航、来源分析、赛事发现与灵感官网分析应有可核对的独立预算范围。
- 持续发现与说明更新 MUST 由后台调度负责，不依赖用户保持网页打开；公开查询与刷新只读取保存结果，不能隐式发起收费任务。
- 已派发请求结果未知时 MUST 保守结算并禁止自动重发；增加 attempt、租约回收或页面刷新不能绕过此限制。
  明确重新收费的操作必须具有新的授权依据和可追溯执行记录。
- 长任务 MUST 展示进行中、成功或失败，不得无限等待或展示虚假的完成状态。
- DSH 或模型暂不可用时 MUST 保留已有项目和成果，允许查看任务及进行适用的手动操作。
- GitHub 操作失败时 MUST 保留草稿和错误上下文，不得丢弃用户上传的待处理成果。
- 技能目录或安装服务不可用时 MUST 保留计划、旧版本引用和现有本机环境，提供适用的教程或手动路径。
  部分安装失败不得将整个包误报为成功，也不得假报已恢复全部变更。
- 错误与操作记录 MUST 足以定位问题，同时避免包含敏感数据。
- 性能与成本目标 MUST 在技术计划中给出测量方式，避免无依据承诺零成本或固定响应速度。
- 生成结果 SHOULD 按输入和版本合理复用，避免每次查看页面都重新执行昂贵任务。

**理由：** 比赛有截止时间，单个外部服务失败不能让团队失去已有进展。

### X. 体验优先，协作状态清楚

- 新人入口 MUST 提供可识别的参赛主路径：找比赛、核对报名、准备与组队、执行任务、演示提交、复盘。首页说明如何开始，登录后根据当前可读记录帮助继续，不能要求用户先阅读整站功能清单。
- 每个工作区首屏 MUST 突出一个主要行动，并用简短说明解释为什么现在做；其他开始方式和已存在入口可以保留为次要操作。未读取、读取失败和缺少事实时不得伪造个性化推荐或完成状态。
- 长指南、辅助工具、AI详细解释、高级配置和历史记录 SHOULD 按需展开，在相应任务处解释用途；折叠不得隐藏当前阻塞、重要期限、权限、费用、错误、未保存输入或正式提交回执。
- 新手指引完成后的重看入口 SHOULD 归入账号或帮助，不在每个工作区重复占据首屏。邀请、报名和原目的地仍优先，浏览指引不代表报名、任务或提交成功。
- 页面 MUST 按用户要完成的任务组织，不得把源码模块数量直接变成同等数量的一级入口；
  常用任务使用少而清楚的一级导航，相关功能可在同一工作区按步骤或标签呈现。
- 页面整合 MUST 保留必要详情的独立直达、既有数据和权限边界，不得以精简菜单为由删除已有成果、教程或资源。
  具体入口名称、数量与路由归当前规划管理，不在宪法中永久锁定。
- 名称、按钮和状态说明 MUST 使用新人能理解的中文；需要出现 GitHub、分支、PR、技能等术语时，
  必须在使用场景中说明含义和操作结果，不能要求用户先理解内部模块或技术实现。
- 每个页面 MUST 让用户看清当前在做什么、当前状态及下一步主要动作；空状态应帮助开始或选择替代任务，
  错误状态应说明是否保留输入和成果、如何恢复及是否可以重试，不能以无说明的空白或不可恢复错误结束流程。
- 同一参赛流程 MUST 尽量保留当前项目和已确认资料，避免重复选择项目、重复填写同一事实或为了连续操作多次跳回列表。
  可直接读取已保存结果的操作不得隐式重新生成，AI 生成与明确修改动作仍按原有授权和预算规则处理。
- 手机上的主要动作 MUST 方便触达并可独立完成；长说明、高级参数和低频操作应按需展开，
  不得用密集模块入口或技术设置遮住用户当前要做的事。
- 新功能和入口 MUST 先判断能否加入现有任务流程；只有明确的新需求和独立使用场景才增加新的工作区，
  精简界面与保留准确状态、证据和失败恢复必须同时满足。
- 参赛路线图 MUST 以树状层级呈现整套流程：起点、阶段、具体行动、对应辅助资源；桌面与手机都能识别父子关系，
  不能只堆放互不关联的模块卡片。节点必须能够到达相应已有功能，缺少账号或空间时给出清楚的下一步。
- 路线图的准备顺序 MUST 与任务实际依赖区分；UI 草图、素材、PPT 和讲稿大纲等可提前并行，
  最终演示素材需要相应可展示成果，具体前置与完成仍由当前团队任务和交付事实判断。可选工具不得默认成为所有参赛者的强制步骤。
- 路线图关联私人计划、出行、讲稿与 PPT 时 MUST 保留本人权限与主动确认；仅提供入口不得自动共享到团队。
- 团队空间的邀请入口 MUST 在可操作页面方便找到；生成后优先帮助复制或展示本地二维码，解释人数、有效期和丢失处理。低频成员管理不得遮住邀请与当前任务；邀请权限仍以服务端身份为准。
- 阶段导航与清单 MUST 从已有事实派生，明确未读取、待核对、成员自报和已确认记录。浏览阶段不得修改项目阶段、任务、报名或提交事实；不得另建无依据完成百分比或浏览打卡。
- 工作台 MUST 区分首次准备与已有计划；前者提供可选择的开始入口，后者突出本人当前任务、等待交接、最近截止和队内变化。工具、教程、灵感与技能应在相关任务位置说明用途，不能因展示入口而强制使用或自动执行。
- 团队空间 MUST 是操作台而不是说明书：能就地完成的事必须能就地完成。需要离开当前页再回来才能继续的操作 SHOULD 改为就地展开；节点点击默认展开对应组件，不得只跳转到另一页。就地展开不得绕开既有的写前授权、revision 校验与审计。
- 默认自由画布 SHOULD 预置少量常用组件，当前为待办、团队进度、队友、协作提醒、流程与文档，用户可自行摆放或收起；不沿用旧协作视图“一屏最多两张”的强制折叠。收起是压缩显示，不是隐藏，不得以折叠深度掩盖当前阻塞、期限、权限或未保存输入。
- 待办清单 MUST 聚合"要我填、要我确认、要我做、要我读"四类，每一条 MUST 有一个本人可独立完成的明确结束条件。没有明确结束条件的关注项不得进入待办清单。
- 待办清单 MUST NOT 出现"尚未读取""未知""需要复核"一类内部状态；系统未知的信息不得伪装成待办或已办，应说明读取状态并提供重新读取的入口。
- 队友的消息、交接、求助与共享资料 MUST 可以转成本人待办并保留去向：弹窗、提示与通知只是入口，待办清单才是归宿；关闭提示不代表事情完成，也不得因关闭而丢失该事项。
- 视觉提示 MUST 分级：只有真实阻塞（有人等待本人确认、本人负责的期限临近、队友求助）可以用红色提示；一般待办使用中性标记。红色标记不得因长期常亮而失去含义。
- 主路径线 MUST 保持单向、不分支，节点顺序清楚；节点按真实事实标注"还没轮到 / 该我了 / 已完成"，并按需显示依赖或交接是否挡路。线本身不分叉，但节点 MUST 随时可展开——不得用线性顺序锁死操作，也不得因上游变化使已完成记录失效或要求重填。
- 站内"路径"表现 MUST 收敛为一套：主页一条主路（找比赛、组队、执行、交付、复盘）负责"我该往哪走"，团队空间线负责"这段路里的细步"；新增入口前必须先判断能否并入现有路径，不得再增加并行的第二、第三条线路或同义导航。
- 主页的下一步 MUST 依据当前可读记录指向具体动作，并区分首次到访与继续参赛两类人；不得只重复固定步骤清单而不反映用户当前状态。
- 团队空间 MUST 默认提供预置常用组件的自由画布，内容直接铺开并去掉重复标题和多余视觉容器；空间名称、邀请、本人待办和团队交接清楚可达。用户无需先布置组件才能参赛，旧私人布局不得自动覆盖。布局为本人偏好，移动、折叠、移除或缩放 MUST NOT 改变业务数据、权限或完成状态。
- 组件长按激活移动，不显示拖动抓手；短按、文字选择和表单操作 MUST 保留。普通滚轮只有位于已圈选对象上时才缩放整个选中组，未选组件、空白画布、输入区保持正常滚动；仅拖动组件不得自动获得圈选缩放资格，父组件与子节点不得双重缩放。核心操作有键盘等价入口，手机以单列内容展示且不改桌面坐标。流程行动作为连线节点，工具和资源收在对应节点详情，不显示六处编号阶段标题；线端点跟随移动与缩放，不建立第二份完成状态。
- 桌面空白左键按住拖框可圈选多个组件或流程行动，长按也可启动；不能因提前移动而让框选消失。整组移动、缩放保持成员相对位置与比例，边界统一约束，只保存本人摆放；圈选矩形仅在手势中显示，选中状态轻量标记具体项目，不画包住整片画布的大框。点开行动 MUST 直达相关编辑或下一步，账号表单不得重复插入，必填交接须在提交前可见。
- 文档保持已有正文白底，参赛流程保持现有透明铺陈；其余画布组件使用用户指定的 #FFFDF8 暖白底。底色贴合真实组件内容，不增加巨大外层容器或冗余标题。
- 主线与团队概览 MUST 区分读取中、读取失败、未知、需要复核和实际完成。只有当前计划及有效检查记录可用于完成展示；规则变化不等于有人等待。共享文档 MUST 可完整阅读，允许编辑时必须真实持久化成功才显示保存成功；归档业务保持只读。
- 空间文档 MUST 默认只显示带一层边框的连续正文，像TXT一样阅读和选择；不显示多余标题、标题表单或常驻说明，不截断或内部滚动遮挡。编辑区随文字延长，手机自动换行；保存、复制、编辑、共享权限操作归正文框的小菜单，真实确认和草稿冲突保护保留。
- 队友状态 MUST 紧凑展示当前活跃成员及本人，入队后从同一成员记录刷新到各人的空间；当前任务与主动共享职责可展开，不能把未更新推断为没工作、在线或能力低。私人布局不得成为成员权限或进度事实。
- 团队AI护航 MUST 以本人确认职责、当前生效计划和已授权团队记录为依据，区分只读事实提醒与真实DSH建议。自动分析需明确开启、按关键版本去重并限制频率与预算，未知结果停止自动重发；不得替成员改分工、确认计划、完成任务、接受成果或公开私人记忆。
- 私人文档草稿 MUST 按账号、空间和文档隔离持久保护；自动保护不等于共享保存，只有明确保存才更新团队正文。读取不写初始化，双窗口冲突、共享编辑撤回、删除及归档均保留可复制的本人输入，不绕过权限发布；身份失效或离队须隐藏旧输入，不能用保留草稿绕过当前空间权限。
- 成果交接 SHOULD 写清位置、版本、打开方法与检查条件，复用原进度和成果引用，不另造完成状态。关键目标、范围、截止和生效分工变化 MUST 保留版本并给相关当前成员提供显式“我已了解”；了解、同意、完成和正式提交分别记录，不由普通查看自动确认。
- 同一工作区出现多个 AI 入口时 MUST 用一句话说明各自分工与边界，不得让用户自行猜测差异；AI 助手与站内导航员的对话隔离仍按既有条款执行。
- 任务式体验 MUST 优先执行效率与团队交接：当前可做、等本人检查、阻塞求助和队友动态可直接找到；指引、资料与设置按需展开。领取、开始、提交、检查通过、运行与正式提交必须分别说明，点亮只由实际检查事实派生。
- 待领取任务 MUST 复用现有任务与计划集合，原子校验身份/归属/版本；领取后保留负责人，不以词条消失掩盖工作。未生效草案须经容量、依赖和规则校验确认，不能用认领绕过计划生效要求。
- 个人参赛目的 MUST 与作品目标分开；职责可多选并随比赛调整。简历/年龄/MBTI/头像为选填，不作为能力排名依据。公开组队名片/招募内容必须由本人或活跃空间管理员明确发布，私人编辑不自动公开，不泄露邮箱/原始测评或其他私人材料。
- 团队动态 MUST 围绕成果、交接、阻塞与明确共享建议，不新增重复完成状态。本人预览确认后才能发布AI片段；待讨论建议与已采纳决定分开，撤回/版本变化需对后续AI可见性生效。
- 空间AI MUST 与站内导航员有清楚独立入口及本人/空间隔离的对话，继承当前账号的网站导航记忆与个人资料；完整历史保留，每次有界检索，不承诺全部历史同时进入模型。记忆读取、当前团队资料和回答前后均复核授权，不用旧记忆绕过其他项目撤权，不自动共享私人对话。
- 选题检查 MUST 区分规则、最小演示、待验证技术、团队能力时间与风险；未知条件必须明确，不用排程可行性证明技术可行或获奖，不自动改变目标/任务/正式决定。

**理由：** 用户应把时间花在完成参赛任务上；协作工具需要减少寻找入口、重复填写和等待交接的负担。

#### 效率工具（v1.20.0 追加）

- 团队空间 MUST 让用户**在看得见任务的地方就能动手**。只呈现"该做什么"却要求跳到另一套界面才能做，属于未完成的体验；新增的协作小工具 MUST 优先消除"看在这里、做在那里"。
- 任何新增的效率工具 MUST **复用既有的写入路径、权限判定与并发冲突处理**，不得为同一件事另写一套写逻辑；出现第二套写逻辑比缺少该工具更糟。
- 提出新工具前 MUST 先核对既有能力。**已经实现的能力不得被当作新功能重复建设**（例如任务认领/释放/指派已存在于计划服务、路由与任务板三层）。
- 协作信息 MUST 让人看出"在等谁、谁在等我、时间与余力在哪里"。这些 MUST 从既有真实记录**派生**，不得为此新增完成状态或第二份事实来源。
- 效率工具 MUST 能从用户当前所在位置到达；仅在另一条路由里可达、或需要登录后才出现在菜单里的功能，不得当作已交付。
- 提示与浮层 MUST 不遮挡它所在位置上用户需要阅读的内容，也不得压住同区域的其他入口；出现遮挡时必须改位置，而不是要求用户绕过。

#### 配色与令牌（v1.20.0 追加）

- 配色 MUST 以设计令牌为单一来源（见 [配色方案](../docs/设计/配色方案.md)）。组件 MUST 使用令牌而非写死色值；新增字面色值 MUST 有理由。
- 可选配色皮肤 MUST 只覆盖颜色变量，**不得改变布局、结构或行为**；切换配色不得影响任何功能、权限或数据。
- 任何配色方案 MUST 满足可读性门槛：正文与链接对底色不低于 4.5:1，按钮文字对按钮底色不低于 4.5:1，品牌色块不低于 3:1。
- 颜色语义 MUST 保持："红"只用于真阻塞；品牌强调色与阻塞提示不得混用同一语义而使人误判。

### XI. 多赛事运营、官方沟通与公正评审

- 主办方 MAY 配置本机构专用发信邮箱，用于官方公告和专属入选通知；不得只修改From地址冒充邮箱所有人。当前组织管理员 MUST 以真实SMTP认证验证发信权限，成功后才生效；凭据按机构加密、HTTP仅返回脱敏配置，其他主办方/选手/评委不得读取。发信使用安全固定服务配置，禁止客户端任意主机/端口。失败保留旧可用设置，未配置或明确停用时可用已配置网站邮箱；登录验证码仍由网站身份服务发送，不受赛事选择影响。

- 开启网站报名的赛事 MUST 在正式发布前具备真实已发布的本场报名表；分享入口引用正式版本而非未发布草稿。主办方可复制本站报名链接自行发布到社交平台，公开链接不附带审核或名单权限。
- 入选通知 MUST 只向当前本场真实审核通过的选手发布，发送前复核账号、报名版本及工作人员权限。主办方可编辑标题、正文、有限样式并预览，发布后保留不可变内容与目标快照；修改模板不得重写已经收到的通知或自动重发。
- 通知模板只接受受限文字、白名单变量和安全样式；不得执行任意HTML、脚本或CSS。站内已发布、邮件排队、服务接受、实际投递和选手已读是独立事实。外部发送结果未知时持久保留并禁止自动重试，不用另一幂等键掩盖未知结果。
- 多组织、多赛事 MUST 有明确归属和当前服务端授权。客户端选择的机构/赛事标识不得被当成权限；机构通过审核不等于赛事质量或获奖保证。
- 机构管理员、赛事工作人员、评委与选手 MUST 按组织、赛事、模块及评审指派授权；既有平台 reviewer 不自动获得机构审批或评委权力。
- 主办方正式发布的规则与 DSH 发现线索 MUST 清楚区分。规则、表单、行程及评分配置的已发布版本不可被覆盖，重要变更新版本并说明影响。
- 主办方不得因报名、建队或项目关联自动读取私人团队资料、测评、草稿、个人AI记忆；选手明确提交/共享的范围是上限。
- 通用配置 SHOULD 使用模板、合理默认值和有限参数；不得提供任意代码/表达式执行。关闭模块不得破坏既有回执和历史记录。
- 主办方和选手操作 MUST 简单顺手，突出当前待办和下一步，复用可授权带入的资料；高级设置按需展开，重要期限、费用、发布范围及权限不可隐藏。
- 页面 MUST 清楚展示当前比赛、主办方与身份，切换比赛不得将草稿或操作转投另一场；登录/首次指引保留原目的地，移动端主要操作可直接完成。
- 官方公告、公开问答和私人求助 MUST 分清范围；私人内容公开需本人预览确认。AI建议不冒充官方答复，发布、已读、邮件接受与实际投递分别记录。
- 报名额度、审核、自愿接受队伍邀请、退出和锁定 MUST 复核真实事实并原子更新。队长不能代全员同意；住宿仅向本人/当前授权人员展示，餐券核销具备并发防重放。
- 保存、运行验证、正式收件、参赛资格、评分和获奖 MUST 是不同事实。正式收件保留不可变材料快照及回执；接入M06通过可信服务端Port，公开接口不能自报平台验证成功。
- 评分标准、范围与权重 MUST 在评审开始前锁定；缺失分与并列规则明确。人填分、系统按规则汇总，最终结果由授权人员确认公布，不由AI判分、晋级或决定获奖。
- 评委 MUST 明确指派并申报回避；已知参赛/备赛关联需核查。回避者不得继续读取或评分该作品，修改记录和结果发布版本可追溯。
- 评审AI MUST 使用与选手备赛AI独立的记忆、检索范围、缓存和队列上下文，仅处理当前授权的正式提交材料；不继承选手私人记忆。AI只做格式、规则核对、去重提示和摘要，AI不可用时人工流程仍可执行。
- 根验收 MUST 覆盖至少两机构、多赛事、角色与撤权、私密沟通、并发名额/核销及人工收件评审全链路；模块测试、隔离演练、真实试用与公网部署分别记录。

### XII. 对标与公平：机制可以学，事实不能编（v1.21.0 新增）

- 对标竞品 MUST 以**可核对的证据**为起点：公开页面的被动观测、公开仓库的代码与文档、官方自述。**官方自述与实测必须分开标注**，未观测到的能力记"未知"，MUST NOT 写进对比当优点，MUST NOT 用竞品功能数量推导我们的需求。
- 从竞品吸收任何能力前 MUST **先核对既有实现**（与"效率工具"同一条纪律）；已经实现的能力不得重复建设，MUST NOT 为了对齐竞品而新增第二套事实或第二套写逻辑。
- 对外描述竞品或其他平台时 MUST 限于已取得的证据范围，MUST NOT 编造其定价、机制或数据。
- 组队与推荐 MUST 以**缺口覆盖**表达：团队还缺哪几项已声明技能/职责、候选人能补上哪一项，**逐条给依据**。
- 推荐 MUST NOT 输出能力值、适配度、匹配百分比或综合评分，MUST NOT 对候选人做跨人排序或“最佳人选”判定；同一缺口有多人覆盖时，使用用户可理解的稳定中性顺序，并说明这不是能力评价。
- 推荐的每一条依据 MUST 标明来源类别：**平台记录已核验**（已确认的参赛、已收件的交付、已发布的复盘等）或**本人自述未核验**。MUST NOT 把自述合成为"战绩分"，MUST NOT 用年龄、MBTI、头像或外貌参与匹配。
- 公平规则 MUST **公开可查、开赛前锁定、带版本**；规则变更 MUST 影响后续轮次并保留旧版本依据。
- 系统对"赛前开发、截止后变更、材料不全、重复或相似提交"等 MAY 依据真实记录（提交时间戳、仓库活动、材料哈希）自动生成**待复核建议**；MUST NOT 自动判定作弊、自动扣分或自动失格。扣分与失格 MUST 由授权人员确认，MUST 保留依据、版本与不可变审计，并给当事人可见的依据说明。
- 无依据 MUST NOT 认定赛事"内定""不正规"或某队"抄袭"；相似只是待核查，不等于结论。
- 评分校准（如按评委严格度标准化）MUST 是**派生视图**：原始分永久保留并可复核，校准分与原始分并列展示；样本量不足时 MUST NOT 校准，只提示；评委打分无区分度（分数压缩）或异常的 MUST 提示主办方，MUST NOT 静默计入。
- 校准结果 MUST NOT 单独决定晋级、获奖或公布名次；最终结果仍由授权人员在可见依据下确认公布。
- 选手互评 MUST 与评委分**分列**，默认不并入正式名次；启用时 MUST 有去自评规则、参与率门槛与公开说明，且不得成为人身评价或报复渠道。
- **明确不做**：代替选手向第三方提交作品；读取或展示他队/他人的私有仓库与进度；绕过第三方反爬、伪造请求头或凭据取数；用 AI 决定正式评分、晋级或获奖；展示不透明的适配分或"最佳队友"排名。
- **对标以改善我们自己为目的**：吸收竞品机制 MUST 先回答并在规划中记录三个问题——① 它解决我们的哪个真实问题（要能指出当前体验的具体摩擦点）；② 会与哪些既有能力重叠或冲突；③ 如何避免重复入口、第二份事实与第二套写路径。**答不出，或冲突无法避免时 MUST 不做**；MUST NOT 因为竞品有某项功能就新增同等功能。
- 吸收时 MUST 优先改进既有流程内的呈现与规则，MUST NOT 为对标新建第二套并行流程、第二套评分或第二个同类入口；与既有功能冲突时 MUST **保留既有单一事实来源**，调整新想法而不是复制一套。
- 已经存在的同义入口、状态或事实 MUST NOT 因为"竞品这样做"而被替换，也 MUST NOT 两套并行保留。
- 对外页面 SHOULD 让"这个结论依据哪条记录、哪个版本、什么时间"可被任何人复核；这比增加功能数量更接近我们的差异点。

#### 用户数据与算法（v1.22.0 追加）

- 用户行为数据——包括参赛行为、技能声明、完赛情况、评审偏差与赛后转化——**MUST NOT** 被用于训练匹配、评分校准、成果预测或任何"越用越准"的模型。这与"不出适配分与跨人排名"是同一条边界的延伸：既不允许展示模型结论，也不允许为将来训练而囤积数据。
- 平台 **MUST NOT** 以"数据授权"作为交换条件去换取免费接入、流量、补贴或生态资源位；也 **MUST NOT** 在协议或文案中承诺"匿名化行为数据归平台所有"。
- 本条 **MUST NOT** 被理解为禁止既有的、有明确功能依据的数据保存与展示。以下**不属禁止范围**：
  - 主办方**自有且可公开复核**的赛事事实、规则版本与不可变发布版本（M03、`organizer_*`）；
  - M07 结构化复盘与既有只读"下一届可复用清单"在**当前权限内**的复用（含赛后只读清单只列本队自己内容的既有约束）；
  - 宪法 IX 既有的、**预算内且按关键版本去重**的 DSH 建议与订阅类分析；
  - 选手**本人**对自己数据的导出与删除（既有账号自助能力）。
- 判断一个新想法是否触线，问一个可检验的问题：**"这条数据是否会在本人看不到、或未就当前用途另行同意的情况下，被用来改变平台对其他人的输出？"** 是则不做；答不出也按不做处理。

### XIII. 主办方自治、模块助手与选手社区（v1.23.0 新增）

#### 主办方自治与可配置

- 与主办方运营有关的每一项能力（模块负责人邀请、模块助手、作品公开与点评、选手社区、互评量纲与维度、消息保留口径等）**MUST 在主办方工作台里可单独配置**，**默认关闭**；MUST NOT 由平台私自开启，MUST NOT 把多项能力绑成一个不可拆分的总开关。
- 配置 MUST 随**正式发布版本**冻结并可追溯：改配置走既有"预览 → 发布 → 变化回执"，MUST NOT 出现"线上实际行为与已发布版本说明不一致"。
- 配置只决定"该能力在本场是否可用"，MUST NOT 改变既有报名、收件、评审的规则与权限，也 MUST NOT 让主办方替**选手本人**做只属于本人的选择（如是否公开自己的作品、是否愿意被联系）。
- 平台对主办方的能力范围 MUST 如实说明；邀请、助手与社区能力 MUST NOT 被表述为效果保证（与 II 一致）。

#### 工作人员受限邀请（取代"点开即授权"）

- 工作人员授权 MUST 继续以既有**单一授权事实**为准。邀请链接 MUST 提供**一次**领取机会，MUST 有有效期、可撤销、可绑定指定已验证邮箱，且 MUST 只能由**已登录且邮箱已验证**的账号领取；领取时 MUST 按既有规则复核并按既有并发与保护约束写入（含"最后一名机构管理员不可撤销"）。
- MUST NOT 提供"打开链接即成为负责人"、免登录领取或永久有效链接。过期、已领取、已撤销、邮箱不符 MUST 给出明确状态，MUST NOT 静默成功或静默失败。
- 生成、领取、撤销 MUST 留下不可变审计，组织管理员 MUST 能看到"谁、何时、领取了哪些能力"，并可撤销。

#### 模块专属助手（AI 边界）

- 每个主办方流程模块 MAY 配一个助手。助手 MUST 使用**独立于选手备赛 AI 与全站聊天**的记忆、检索范围、缓存与队列上下文（与 XI 的评审 AI 隔离同一条）。
- 助手输入 MUST 限于该模块**当前授权**的既有事实：只读、不跨赛事、不读他人私人材料；评审助手只处理当前授权的正式提交材料，MUST NOT 继承任何选手私人记忆。
- 助手产出 MUST 只是**草稿、核对清单、摘要与去重提示**，用户 MUST 显式复制或应用。助手 MUST NOT 发布、发信、扣分、改结果、改权限或改变任何业务状态。
- 助手调用 MUST NOT 设平台强制的固定次数上限（用量由主办方自行决定），但每次调用 MUST 计入既有 AI 账本并**可核对地记录**（谁、哪个模块、读了什么范围、花费）；MUST NOT 静默限流或偷偷降级；若设置限额，MUST 是主办方的显式配置。
- 助手不可用或超出主办方自设预算时 MUST 明确提示，**既有模块的人工流程 MUST 照常可用**（与 IX 一致）。助手界面 MUST 说明它读了什么范围，并标注 AI 身份与"建议不构成执行授权"。
- **明确不做**：用 AI 判分、晋级、获奖，决定联系或录取，或自动执行任何模块动作。

#### 作品公开与点评（分列、不计入名次）

- 作品材料属于**提交的队伍**。作品对他人公开 MUST 同时满足：① 主办方在本场开启了该能力；② **队伍本人明确选择**公开范围。主办方 MUST NOT 替队伍决定披露；未选择即不公开。
- 公开投影 MUST 只含队伍选择公开的字段，MUST NOT 含联系人、邮箱、答卷、求助、住宿、队伍专属反馈或评委身份。
- 点评 MUST 分为**文字留言**与**互评分**两类，分列存储、分列展示；两者 MUST NOT 并入正式汇总、名次、公布或对外导出。
- 互评启用时 MUST 具备：**去自评**（依据收件时的队伍成员快照）、**参与率门槛**（不足只显示"样本不足"）、**公开说明**、**可隐藏与举报**；MUST NOT 成为人身评价或报复渠道。互评的量纲与维度 MAY 由主办方配置，但 MUST 与评委维度**分开定义**并公开说明，MUST NOT 暗示两者等价。
- **评审隔离**：评分期间，评委侧 MUST NOT 返回文字留言或互评内容。

#### 选手社区（名录、连接、私信）

- 赛事内的选手名录、连接与私信 MUST 默认关闭，按赛事配置，并由**本人**决定是否参与；MUST NOT 对访客或非本场参赛者开放。
- 连接 MUST 是**双向同意**；MUST NOT 提供服务方定义的"单向关注"式社交图谱。请求 MUST 有数量与冷却限制。
- 私信 MUST 只在已接受的连接内可用，MUST 提供**屏蔽与举报**（不是可选项）、内容限长与频率限制、本人撤回；MUST NOT 由平台自动补全或公开邮箱、电话等联系方式。
- 平台 MUST NOT 声称提供年龄核验或未成年人保护；因此私信默认关闭，由本人在须知下逐场开启。
- 消息与通知 MUST 复用既有通知与保留边界，MUST NOT 新建第二套通知系统；消息内容 MUST NOT 进入任何模型训练（与 XII 一致）。
- 主办方关闭某能力后 MUST NOT 再返回新数据；既有消息的保留、冻结或清理口径 MUST 由主办方配置并在界面写明。

#### 明确不做

- 打开链接即获得权限、免登录领取、永久有效邀请；
- 用 AI 判分、晋级、获奖，或自动执行模块动作；
- 不经队伍同意由主办方公开其作品材料；
- 把互评默认计入名次、替代人工评审，或与评委分混在同一张表/同一页面；
- 单向关注式社交、跨赛事社交图谱、对访客开放社区；
- 把私信做成第二套通知系统；
- 用参赛行为、技能声明、完赛情况、评审偏差或赛后转化训练任何模型（与 XII 一致）。

### XIV. 内容归属与许可（v1.24.0 新增）

主办方自助建站把内容归属问题带进平台，本节把口径钉死：**能力归平台、表达归主办方、作品归选手、默认不训练**。

#### 三层归属

- **平台拥有能力**：模板、区块组件、渲染器、设计系统与默认模板。主办方仅有使用权，MUST NOT 转售或再分发。
- **主办方拥有表达**：其上传素材（及其许可方）、页面文案，以及本次页面的具体编排（选择与安排）。
- **选手／队伍拥有作品**：提交材料与作品内容；主办方仅在本场赛事的评审、展示与公示范围内使用。

#### 许可与导出

- 主办方就其在平台发布的内容，向平台授予**为提供服务所必需**的非独占许可：托管、存储、展示、缓存、备份与必要公开传播。
- 该许可 MUST NOT 包含模型训练、转售、再分发、向第三方提供原始内容；MUST NOT 被解释为平台取得内容所有权。
- 平台 MUST 提供**文案与素材清单的导出**；模板与组件源码不在导出范围。

#### AI 生成内容

- 平台 MUST NOT 承诺 AI 生成内容必然受著作权保护，或具备新颖性、唯一性与特定商业适配性。
- 归属按「本次编排归主办方、底层能力归平台」约定；生成内容 MUST 经主办方人工确认后才可发布。
- AI 生成内容与页面文案 MUST NOT 用于训练任何模型（与 XII 一致）。

#### 素材、投诉与下线

- 主办方 MUST 声明其对上传素材享有权利；平台不承担权利审查义务，但收到有效投诉 MUST 能下线或停用相关页面。
- 平台 MUST 提供页面停用与短码回收；停用 MUST NOT 删除已有赛事记录，也 MUST NOT 影响平台默认页与报名／提交／结果能力。
- 因主办方素材侵权造成的责任由主办方承担。

#### 事实与展示分离

- 报名截止、资格、赛程、评审结果等事实 MUST 以平台记录为准；专属页上的对应内容 MUST 为只读投影。
- 主办方 MUST NOT 在页面文案中手写与平台记录冲突的事实。

#### 明确不做

- 把主办方文案、素材或页面编排据为平台所有；
- 把选手作品用于主办方或平台的商业用途；
- 以「内容授权」交换流量、补贴或资源位（与 XII 一致）；
- 把统计结果用于对选手的排名或能力评价。

### XV. 模型供应商中立与插件接入（v1.25.0 新增）

#### 供应商中立

- 平台 MUST 通过统一模型端口接入模型；**任何厂商**（云端或本地、官方或自建兼容端点）MUST 能在不改业务逻辑的前提下接入与替换。
- MUST NOT 把某个厂商的模型名、接口形状或计价硬编码进业务层、前端或数据库约束。
- 厂商特有差异 MUST 表达为**数据**（地址、密钥来源、能力、计价、限额），而不是散落的 `if` 分支。

#### 密钥与凭据

- 密钥 MUST 只存在于服务端环境或加密凭据库；MUST NOT 入库明文、MUST NOT 进入 API 响应、MUST NOT 写入日志或错误信息。
- 用户级令牌（含第三方插件令牌）MUST 只存哈希、MUST 支持撤销，撤销 MUST 立即生效。

#### 计价与失败语义

- 每个厂商 MUST 独立计价与独立账本；未配置计价时 MUST NOT 扣费。
- 结果未知时 MUST 保守结算并禁止自动重放；MUST NOT 因换厂商而自动重试（会产生重复计费与不可审计的重复调用）。
- 厂商不可用时 MUST 返回明确错误并降级；人工流程 MUST 照常可用。

#### 第三方插件（MCP 等）

- 插件 MUST 通过用户主动签发的令牌或设备码授权接入，MUST NOT 内置任何共享密钥。
- 默认权限 MUST 为只读；`ai:ask` 一类消耗额度的能力 MUST 单独授权、单独限流、单独审计。
- 插件 MUST NOT 获得提交、发布、改状态、发信或评分类能力。
- 所有插件调用 MUST 记录工具名、令牌标识、耗时与结果码（MUST NOT 记录正文）。

#### 产品语义不因厂商而变

- 无论使用哪家模型，AI 仍 MUST 只出草稿/清单/摘要，MUST NOT 执行动作、判分、决定晋级或代替用户提交。
- 换厂商 MUST NOT 改变任何用户可见的边界说明。

  报告完成后队内按权限查看进度和交接成果。具体模块安排及实现状态由规划与验收记录管理。
- 辅助功能：工具与资料库保留审核、个人收藏和项目共享；独立灵感页汇集视觉网站、网页案例、组件与动效官网，DSH 说明完成后展示，未完成保留等待状态。

  按 AI 工具分类，目标覆盖主流工具，并提供经验证的一键安装与安装指导。

- 导航员提供可跳过/重放的初次介绍，登录后可通过真实后端 DSH 问答了解下一步，不能替用户确认规则或执行操作。
- 参赛项目及成果需要保留，为复盘和后续参赛提供参考。
- 视觉方向：暖白＋橙红的情报编辑部风格；具体布局、设计令牌和组件规格归视觉设计文档。

### 第一版范围控制

第一版 MUST 优先贯通：

**登录 → 创建参赛项目 → 理解赛事要求（赛道按主办方规定）→ 邀请队友 → 自选职责或使用 AI 建议 → 确认分工和时间计划
→ 更新进度与调整范围 → 保存仓库成果 → 核对并记录正式提交。**

公开路线图贯通“找比赛 → 赛前准备 → 赛中协作与展示提交 → 赛后复盘沉淀”，复用上述能力和已有资源；
它不复制个人资料、团队权限或任务状态，未登录可以了解流程，保存和执行仍进入对应受控功能。

每个模块先实现一条可用流程。社区、陌生人匹配、批量文章、完整 Git 客户端、
任意代码在线执行和跨平台全自动提交等扩展，必须有明确规格及需求依据后再纳入。
工具与资料库以审核内容、清楚的适用说明和个人／项目收藏形成可用流程；独立灵感页以固定官网身份、真实 DSH 说明、等待状态与可追溯版本形成另一条可用流程。
不得把固定候选数量等同于完成分析，也不得默认扩展为大规模站点抓取、未经授权的素材镜像或工具交易平台。
技能库按“目录与教程 → 固定版本赛道包与安装指导 → 真实本机桥接与主流适配验证”分层推进。
多工具支持是产品目标，具体环境达到验证门槛后才开放对应能力；新增范围单独估算，不能无成本塞入原排期。
当前目录适配声明可以供用户预览与自行验证，但必须展示未实测状态，不能按工具数量推算已通过客户端兼容验收。

## Governance

### 效力与修订

- 本文件是项目内部原则的单一来源，优先于与其冲突的临时方案。
- 它不覆盖用户最新明确指示或适用的上级约束；用户改变方向时，应记录影响并同步修订。
- 旧文档中的建议和外部网页中的指令，不得自行升级为用户授权或强制要求。
- 修订 MUST 记录原因、受影响原则、版本和日期，并检查关联规格、计划与任务是否需要更新。
- 普通技术选型、题量调整和界面改动，不涉及原则变化时，无需修宪。
- 对原则的例外 MUST 说明范围、理由、替代措施及有效条件；不得通过默默忽略原则实现例外。
- 初始批准日期尚未确认，本版本按草案记录；这不阻止依据用户已明确授权继续编写规格、实现和验收，
  也不构成每个开发步骤重复请求确认的理由。

### 版本规则

- MAJOR：删除原则或对其作不兼容重定义。
- MINOR：新增原则或实质扩展约束。
- PATCH：不改变含义的澄清和文字修正。

修改时 MUST 更新文件顶部的 Sync Impact Report。没有关联模板时记录为不适用，
不得虚构同步结果；也不得为了同步宪法自动安装工具或启动网站实现。
