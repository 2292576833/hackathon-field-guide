## 二、现状的真实摩擦

1. `/organizers/workspace` 的标题写着"选一场比赛，**处理当前待办**"，但页面里**没有任何待办视图**——主办方要知道还差什么，得先猜是哪个页面。
2. 发布门槛（待补赛事信息）只存在于比赛设置页的深处；在"报名审核 / 收件与评审"等 section 里工作时看不到"还有 3 项没确认"。
3. 状态散落：草稿/已发布/已结束、机构是否暂停运营、正式规则版本，分别在标题徽标、提示条和 400 多行组件里各出现一次。
4. 导航本身是好的（`IdentityFrame` 的 section 标签已按**已开启模块 + 本人能力**过滤），所以**不该再加一套入口**。

## 三、改动

新增 `src/components/organizer-action-center.tsx`（客户端、只读派生），接入两处：

- **每个 section 页顶部**（`StaffSection`：报名审核、队伍管理、通知与答疑、行程管理、现场服务、收件与评审）；
- **工作台事件页顶部**（`OrganizerWorkspace` 选中比赛后）。

面板结构（自上而下）：

1. **状态徽标**：草稿（选手看不到）/ 已发布（选手可见）/ 已结束 / 已归档 + 正式规则 vN + 机构暂停运营（仅当确实暂停时显示，不猜）。
2. **唯一下一步**（按优先级只给一条）：机构暂停 → 先处理机构状态；草稿且有缺口 → "还有 N 项信息需要你们确认"；草稿且无缺口 → "可以预览并发布了"；已发布 → "照看正在进行的事项"并列出你身份可处理的模块；已结束 → 归档与复用提示。每条都带**一个**直达按钮。
3. **发布门槛清单**：把 `readiness` 的事实分三类呈现——`missing`（需要确认）、`conflicting`（两侧不一致，附来源原文链接）、`known_from_source`（**仅有抓取线索**、你们尚未确认）。时间类字段明确写"在比赛设置里改，**避免出现两份时间**"。
4. **"你的身份可以处理：…"**：纯文字，不重复导航（导航已在顶部标签里）。
5. 一句说明：数字与状态都来自本站已保存的事实，刷新即重新计算。

## 四、纪律（与宪法一致）

- **不新增端点、不新增状态、不写入任何打勾**；面板只是 `GET /organizer/events/:id/readiness` 的派生视图。
- **不显示完成度百分比**：只说"还有 N 项没有权威答案"，清单不代表完成度。
- 可见项严格按**本人能力 + 本场已开启模块**过滤（服务端事实决定，前端不硬编码可用性）。
- 抓取线索与主办方确认值**必须可区分**（沿用既有 readiness 的语义）；机构暂停只在事实成立时显示。
- 视觉沿用我们自己的令牌与既有组件样式（`competition-workspace.module.css`），不引入任何竞品的配色或版式。

## 六、精确待办计数（已补）

报名列表接口是**分页且没有总数**，拿第一页数量当总数就是造假数字。因此补了一个**只读计数端点**（服务端算）：

- `event-registration`：`RegistrationStore.countRegistrations()`（一条 `GROUP BY status` 的 count，草稿显式归零——草稿只有本人可见）＋ 服务 `registrationCounts()`（`registration_manage` 权限）＋ handler `registrationCounts` ＋ 路由 `GET organizer/events/:eventId/registration-counts`；
- 工作台面板只在**本人有报名管理权限且本场开启报名**时请求它；**请求失败就不显示数字**（不猜、不显示上一页的残留）；
- 已发布且有待审报名时，唯一下一步变为"有 N 条报名等待审核 / 去处理报名"（直达报名审核页）。

测试：报名模块 39/39（含新增方法进入 handler 方法表断言）；`npm run typecheck` 通过。
