## 已完成

- 固定页面服务为 `http://127.0.0.1:3101`，只有显式 `ORGANIZER_READY=1` 才运行；不启动服务、不构建、不读取 `.env.local`。
- 复用 `isolated-workspace.ts`，加载真实 `createApplication`、全部根迁移、真实账号会话和根 HTTP handler，数据库仅为当前测试独占的内存 PGlite。
- 浏览器全部 API 请求拦截至隔离应用；外部请求被阻止并记录。不调用真实邮件、模型、GitHub 或生产数据库。
- 场景一：没有报名表时首次发布被阻止 → 主办方在页面配置和发布报名表 → 预览并正式发布赛事 → 复制当前比赛报名链接 → 匿名选手从链接进入正确比赛 → 注册/登录入口保留该比赛 → 使用隔离邮箱验证码完成实际页面注册 → 提交待审核 → 主办方在页面查看答卷并批准 → 选手刷新看到已通过 → 未开启组队时进入本场安排和官方通知。
- 入选通知：主办方保存本场绿色简洁模板 → 已通过列表选择本人 → 预览实际收件人 → 勾选核对后发布 → 选手刷新自己的通知。姓名、赛事、机构与正文均对应本场和本人；未配置邮件时明确显示“邮件未配置”。真实隔离数据库保存 1 条站内通知，邮件 outbox 为 0，不把站内发布冒充邮件送达。
- 场景二：手机分享使用已正式发布的名称与审核规则，保留未发布赛事修改；复制权限拒绝时选中只读链接并明确手动复制；切换比赛后所有报名和审核入口指向当前比赛。
- 场景三：已认证机构管理员在工作台直接找到自配发信入口 → 明确登录验证码仍用网站邮箱 → 填写完整邮箱及授权码并确认 → 认证失败时保留原设置和邮箱输入、清除授权码、禁止自动重试 → 读取最新设置不重新认证 → 用户明确再次验证并保存 → 只显示脱敏邮箱，不回显授权码或写入浏览器存储 → 确认停用后清除数据库凭据并回到网站邮箱。
- 手机视口 390px 检查横向溢出，并输出主办方分享、选手批准状态及主办方发信设置的页面截图。
