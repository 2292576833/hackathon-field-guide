### 关键设计取舍

1. **输入是"剩余毫秒"，不是截止时刻**。当前时刻由调用方传入，因此模块内**没有 `Date.now()`**，也没有时区换算，
   同一输入永远同一输出，测试不依赖运行时间。
2. **事实不足一律 `unknown`**，且 `notice` 逐项写出缺哪个字段、为什么缺（见 README 表格）。
   计数自相矛盾（`done + blocked + inProgress > total`）时不猜哪一项对，直接报 `unknown`。
3. **`remainingMs` 为负也算事实不足**，不推断"已截止"或"已经过点了该怎么办"。理由：本模块不知道截止之后发生了什么，
   把负值当成"你已经迟到了"是一种编造。
4. **只引用两类数字事实**：传入的剩余毫秒（真实时间预算，说成"约 5 小时"）、传入的任务计数（原样引用）。
   不把计数换算成百分比或完成度。
5. **`unknown` 时也给动作**，但只做两件事：说明缺什么、建议先补事实或先冻结新增范围；不推测进度、不建议删代码。
6. **`on_track` 也给 `cut`**。不给"没事"的结论，而是给防膨胀动作（新功能进「提交后再做」清单）。
7. **`cut` 必须具体**：每条都包含可执行动作（停手 / 降级 / 推后 / 收敛 / 先占位），
   且必须至少有一条把"降级成什么"写清楚（如"实时协作降级为「一个人改、其他人刷新看」"）。
8. **阶段识别容错**：识别不了（`"打怪升级"`）照常给建议，只在 `notice` 里说明"阶段未识别，未叠加阶段专项建议"；
   `stage` 为空串不报错、不编造阶段名。

## 6. 需要主会话装配时的边界注意（重点）

1. **不要把 `verdict` 翻译成完成状态**。`on_track` / `at_risk` / `must_cut` 是**对时间压力的建议**，
   不是"完成度"或"交付判定"；尤其 `must_cut` ≠ "交付失败"。
2. **`unknown` 不等于"没有进度"**。它是"本模块读不到可依据的事实"。规划27 第 9 节第 4 条要求待办清单不出现
   "尚未读取/未知/需要复核"这类内部状态词——所以装配时请把 `unknown` 处理成**面向用户的动作**
   （例如"先写下最小成果"），而不要把 `notice` 原文照搬成状态标签。
3. **`keep`/`cut` 是建议，不是命令**。`notice` 里已写明"最终由你们定"，UI 不要写成系统裁决。
4. **`cut` 里没有任何"删除代码"的动作**。所有"停手"都写成"移进「提交后再做」清单（代码留在分支或注释里，不删除）"，
   UI 若加复制/导出按钮，请保留这句话，避免被当成"删代码"授权。
5. **不要缓存结论跨时刻复用**。`remainingMs` 变了结论就会变；如果 UI 需要轮询刷新，请每次传入新的 `remainingMs`，
   不要复用上一次的 advice 对象。
6. **不要 patch 输出文本**。若需要不同措辞（例如更短的 `sayToTeam`、去掉 `notice` 里的字段名），告诉我改模块，
   而不是在 UI 层做字符串替换——替换会绕过禁用词表测试。
7. **事实口径只有一个**：`done` 必须是"由真实记录判定为完成"的计数，不要传"自己觉得做完的数量"。
   本模块对 `done` 只做原样引用，不校验真实性（也无从校验），口径错了结论就错了。
