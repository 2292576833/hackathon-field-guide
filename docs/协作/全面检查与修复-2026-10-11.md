## 一、发现并已修复的问题

### 1.（已撤回两次）关于 `AUTH_ORIGIN` 的判断反复出错

这一项我连续判断错了两次，**并直接造成用户一段时间内无法登录**，完整记录如下。

**第一次错判**：我判定"`AUTH_ORIGIN` 指向不存在的域名 `hib.mywire.org`，导致用户无法登录"，据此把配置改成 `https://frp-off.com:44353`。
**第二次错判（更严重）**：我发现本机 DNS 对 `hib.mywire.org` 返回劫持结果后，改用固定节点 IP + SNI 验证出该域名与 ZeroSSL 证书完全有效，于是**又把配置改回 `hib.mywire.org`**。

**第二次改动的后果**：用户实际一直用 `https://frp-off.com:44353` 访问。站点把 `AUTH_ORIGIN` 设成另一个域名后，用户在 `frp-off.com` 上的**登录、注册、AI 提问等全部写操作被 `assertMutationAllowed` 拒绝，返回 403「请求来源不匹配」**。

**根因（我的推理漏掉的一环）**：**两个域名都在真实使用中**，而当前实现只支持**单个** `AUTH_ORIGIN`：

- `https://hib.mywire.org:44353` —— 受信任 ZeroSSL 证书；但本机 DNS 被劫持，部分网络解析不到
- `https://frp-off.com:44353` —— 自签证书（浏览器有警告）；但解析稳定，**是用户当前实际入口**

我只看"证书是否受信任"，没先问用户"你实际用哪个地址"，就把后者从配置里删掉了。正确做法是先确认实际入口，再决定。

**当前处理**：`AUTH_ORIGIN` 设为用户实际在用的 `https://frp-off.com:44353`，实测其写操作 origin 校验通过（畸形邮箱返回 422 `AUTH_EMAIL_INVALID`，说明 origin 已被接受），登录/注册/AI 恢复正常。

**尚未解决的取舍**：现在换成 `hib.mywire.org` 访问会得到 403，反之亦然。要让两个入口同时可用，需要把 `config.origin` 从单值扩展为多值白名单（涉及 `application.ts` 的全局守卫与 auth handler 的 origin 选项），属于独立改动，本轮未做。

**仍成立的 DNS 事实**：本机（`192.168.31.1`）及 8.8.8.8、1.1.1.1、223.5.5.5、9.9.9.9 对 `hib.mywire.org` 返回**互不相同**的 IP，是劫持特征；因此**不要用本机解析结果判断该域名是否可用**，应固定节点 `60.215.128.117` 并以 `hib.mywire.org` 作 SNI/Host 验证（实测 trusted: true，链长 3，有效至 2027-01-09）。

### 2. 构建门禁：PowerShell 下成功构建会返回退出码 1（已记录，未改代码）

同一份代码：
- `cmd /c npm.cmd run build` → **退出码 0**，`✓ Compiled successfully`，28/28 静态页，追踪检查 `failures: 0`、私人引用 0
- PowerShell 下 `npm.cmd run build` → 退出码 **1**

原因：PowerShell 把 npm 转发的 Turbopack warning 当作 native command error。**使用 `$LASTEXITCODE` 判断构建是否通过时会产生误判。**

结论：构建本身健康；在 PowerShell 里判断构建结果应以构建日志中的 `Compiled successfully` 与 postbuild 的 `failures: 0` 为准，或改用 `cmd /c`。

### 3. 采集后台长期失败（随配置移除已自愈）

移除无监听的 `SOURCE_HTTP_PROXY`（127.0.0.1:22321）后，采集恢复正常：
`[discovery] {"status":"completed","searched":1,"fetched":3,"saved":2,"unchanged":1,"rejected":0}`
此前该后台每轮报 `FETCH_UNAVAILABLE` / `DISCOVERY_MODEL_REQUIRES_REVIEW`，全部失败。此项由配置变更解决，本轮无需改代码。

## 三之二、本轮我自己的失误（如实记录）

为避免把失误当成果，单独记录：

1. **DNS 误判导致两次改错配置**：先误判域名不存在，后发现本机 DNS 被劫持又改回 `hib.mywire.org`，而用户实际在用 `frp-off.com`——**导致用户登录、注册、AI 全部 403 一段时间**。教训：改 `AUTH_ORIGIN` 前必须先确认用户实际使用的入口地址，不能只凭证书是否受信任来推断。

3. 因上述误判，我**多做了数次停服重启**。虽然每次都正常恢复、站点始终健康，但这属于不必要的停机风险。
4. 一次探测请求携带了配置中的 `AUTH_ORIGIN`，使服务端**真实受理并发出了一封验证码邮件**到构造地址 `audit-probe@example.invalid`（无效地址，不会打扰真人，但消耗了 1 次发送额度）。
5. 采纳外部审计代理的结论过快：其"工单越权"严重指控经我逐行复核**不成立**，我在写报告前已驳回，未据此改代码（其"邮箱枚举"一条经核实属实，已记入待加固项）。

教训：验证生产配置与数据前，先确认调用签名、解析来源与可用的旁证，再决定是否改动或停机。

### 检查过程中的一次误判（已更正）

本轮检查中我曾得出"数据库未持久化、每次重启都会新建空库丢数据"的结论，**该结论错误，已撤回**。

原因是我的诊断脚本调用了 `createDatabase({ localDatabasePath: ... })`，而该函数的参数名是 **`localPath`**（`src/server/database.ts:17`）。参数名不匹配使 `localPath` 为 `undefined`，PGlite 便以**内存模式**打开，于是每次连接都是空库、需重跑 55 个迁移——我被这个假象误导，并基于它多做了数次无谓停机。

正确调用 `createDatabase({ localPath })`（与 `src/server/application.ts:63` 一致）后，第二次独立连接即可读到已有账本，持久化确认正常。**已复核：站点数据没有任何丢失。**

同时更正：`projects` 与 `ai_unknown_requests` 这两张表在迁移与源码中**都不存在**（项目主表真名是 `projects_project`），早前把它们列为"不可读"同样是脚本表名写错所致。

## 七、建议的后续动作

1. **多入口 Origin（优先）**：`AUTH_ORIGIN` 目前是单值，只能在 `frp-off.com:44353` 与 `hib.mywire.org:44353` 中二选一。已发生一次"因为给 A 配了 origin，B 的用户无法登录"的故障。建议把 `config.origin` 扩展为多值白名单（`assertMutationAllowed`、auth handler 的 `origin` 选项、cookie 的安全判定），让两个域名同时可用，避免换网络就登不上。
2. **域名稳定性**：`hib.mywire.org` 在部分网络被 DNS 劫持解析不到；`frp-off.com` 稳定但证书自签。若要长期对外，需要解决解析稳定性或申请自控域名的证书。证书有效至 2027-01-09，**建议 2026 年 12 月底前续签**，目前无自动续期任务。
3. **安全加固（剩余 4 项）**：机构状态自我重置、公开赛事目录分页、公开报名表名额投影、公开结果读取去锁。见第四节表格。
4. **构建警告**：5 条 Turbopack 警告来自 `.runtime`（7.1 万文件）被路径表达式扫入追踪，可考虑用 `turbopackIgnore` 注释或调整路径写法消除。
5. **PowerShell 构建退出码**：在需要以退出码判断构建结果的脚本/文档中，改用 `cmd /c npm.cmd run build`。
6. **局域网访问**：用户已明确不需要。当前服务只监听 `127.0.0.1`，`192.168.31.246:3000` 不可达；手机通过公网域名访问（会再弹一次自签证书警告）。若以后需要，需同时改监听地址与来源白名单。
