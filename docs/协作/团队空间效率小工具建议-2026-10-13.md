# 团队空间：可添加的效率小工具建议（2026-10-13）

**方法**：读代码找真实摩擦点（附文件:行号），不凭印象。只提建议，未改任何代码。

## 0. 先纠正一个我差点提错的建议

我原本准备建议"加一个任务认领（claim）工具"——**查完发现已经有了**，而且是完整的三层实现：

| 层 | 证据 |
| --- | --- |
| 服务 | `planning/service.ts:341-353`：`claimDraftTask`、`releaseDraftTask`、`assignDraftTask` |
| 路由 | `router.ts:236-241`：`claim` / `release` / `assign` |
| 界面 | `team-task-board.tsx:236-239`：待领取按钮、退回草案、管理员指派 |
| 并发 | `claims.test.ts:61`：并发认领只有一个成功 |

**所以问题不是"缺功能"，而是"功能没出现在用户干活的地方"。** 这是本文件的核心结论。

---

## 1. 核心问题：看的地方能看，做的地方要跳走

| 位置 | 任务类写操作数量 | 说明 |
| --- | --- | --- |
| 团队任务板（`team-task-board.tsx`，子路由 `/plan`） | **38 处** | 认领、退回、指派、更新进度、标阻塞、检查、筛选 |
| 画布上的「团队进度」概览（`space-collaboration-overview.tsx`） | **1 处** | 基本只读，主力操作是 `<Link href="${base}/plan">任务列表 →</Link>`（`:37`） |
| 画布上的「我的待办」（`space-todos.tsx`） | **0 处** | 纯派生清单 |
| 画布上的「队友状态」（`space-teammates.tsx`） | 4 处 | 仅状态相关 |

**证据**：`space-collaboration-overview.tsx:37` 明确把用户送去 `/plan`。也就是说——
**用户在画布上看到"我有 3 件事要做"，但想动手就得离开画布、跳到一个**另一套轮询、另一套词汇**的页面。**

这不只是"多一次点击"，而是：

- **两套界面各刷各的**：画布每 **15 秒**刷新（`space-canvas-board.tsx:137`），任务板每 **10 秒**（`team-task-board.tsx:120` 的文案"页面可见时每 10 秒读取队内任务"），两边可能短暂不一致。
- **新人建立不起"一个地方"的概念**：他在画布上学到的词，到了 `/plan` 全变了（详见 `团队空间优化建议-2026-10-13.md` 的 C2）。

### 建议 1：把「我的任务」做成画布组件（最高价值）

- **它是什么**：一个可以直接动手的组件——列出分给我的任务，就地「开始」「标阻塞」「交成果」「请队友检查」，不用跳页。
- **现在没有它会怎样**：见上表；`space-todos` 能告诉他要做什么，但点了只能跳到 `/plan`。
- **为什么现在做不到**：不是缺接口（`claim/release/assign` 与进度更新都已有），而是**没有把任务板的能力包成一个画布组件**。
- **不违反"不建立第二套完成状态"**：它写的是既有任务状态与进度，**不新增状态字段**，与任务板共用同一份事实。
- **成本**：中（需要把任务板里的操作抽成可复用部分，或做一个精简版的就地操作面板）。
- **风险**：中——**必须复用同一套写入路径与冲突处理**，否则会出现两套写逻辑，这比现在更糟。

## 2. 第二类摩擦：等待与阻塞没人"催"

- **证据**：`space-workflow/teammates.ts` 的四态里已有 `blocked` 与 `handingOff`；`handoff.ts` 要求交接填 4 个字段（位置/版本/打开方式/检查方式）。
- **摩擦**：一个人交出成果后等检查，**系统不告诉他该催谁、也不告诉检查人"有人在等你"**。
  `team-collaboration/TeamFeed.tsx` 有任务活动流，但那是**流水账**，不是"待办在谁手上"。
- **建议 2：「在等谁 / 谁在等我」两个小清单**。
  从既有 `status === "review"`、`ownerMembershipId`、`reviewerMembershipId` 直接派生，**不新增存储**。
- **成本**：小（纯派生 + 一个小组件）。**风险**：低。
- **不违反原则**：只读派生，不写状态。

---

## 3. 第三类摩擦：站会靠手动翻页

- **证据**：`TeamFeed.tsx` 已有任务活动流（`TaskActivity`：状态变更 + 时间 + 操作人，`team-collaboration/types.ts:24-25`）。
- **摩擦**：团队要知道"昨天谁做了什么、今天要做什么"，得自己翻动态流和各人的任务。
- **建议 3：「今日站会摘要」小工具**：把最近 24 小时的 `TaskActivity` 按人分组，加上"他手上还有什么"。
- **成本**：小-中（数据都有，只差聚合与呈现）。**风险**：低。
- **注意**：输出**不得出现完成百分比**，也不得把"未读取"写成状态（宪法约束）。

---

## 4. 第四类摩擦：时间压力看不到"人"

- **证据**：`planning/types.ts:125` 的 `allocations[]` 里有 `membershipId` + `workMinutes`；`memberIntensity`/`availability` 也在。
  但画布上的「倒计时与资源」（`space-resource.tsx`）只给**全队**的截止倒计时。
- **摩擦**：看不出"谁被排满了、谁还有余力"，所以无法把任务挪给有空的人。
- **建议 4：「每人剩余工作量 vs 剩余时间」一行视图**。
- **成本**：小-中（数据已存在）。**风险**：低。
- **不违反原则**：只做呈现，不等于完成状态。

## 5. 明确**不建议**做的

| 不建议 | 理由 |
| --- | --- |
| 再加一套"任务清单"组件 | 已有 `space-todos`（派生）与任务板；再加就是**第三套**说法，与"不建立第二套完成状态"的精神冲突 |
| 做实时推送/WebSocket | 现在 10–15 秒轮询对黑客松节奏足够；引入长连接会带来断线重连、多实例、与 PGlite 单写者等一堆新问题，收益不成比例 |
| 给任务加"打钩完成" | 直接违反宪法：完成只由真实记录判定 |
| 在画布上加"完成百分比"进度条 | 同上，且我们已经全线避免百分比 |
| 做复杂的富文本协作文档 | 现在 `space-documents` 是简单文档；做富文本实时协同是**另一个产品**，不是"小工具" |

---

## 6. 如果只做三个

1. **建议 1：把「我的任务」做成画布组件**（解决"看在这里、做在那里"）——价值最高，但风险也最高，需要复用同一套写入路径。
2. **建议 2：「在等谁 / 谁在等我」**——纯派生、成本低、直击协作断点。
3. **建议 3：「今日站会摘要」**——数据已有，明显省手动翻页的时间。
