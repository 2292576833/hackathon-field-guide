> 依据：用户 2026-10-14 要求「拆解这些项目，把优点我们这个项目能用得上的点拆出来，必要时用 REA 逆向拆解，然后整理起来，然后写宪法和新规划，我们的目标是超过他们做的更好」。

## 1. 方法与证据分级

| 级别 | 方法 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| A · 被动观测 | REA CDP 观测（`list_browser_targets` / `inspect_web_page`），只读、不改页面 | 真实路由、DOM 结构、脚本与资源清单、可访问的公开文案 | 服务端算法、登录后功能、真实数据规模 |
| B · 静态检索 | 下载公开 JS chunk 到本地后做字符串/结构检索（不执行） | 组件目录、功能文案、依赖与集成痕迹 | 运行时行为、A/B 分支、服务端规则 |
| C · 一手自述 | 官方项目页/README 的技术描述 | 作者声称的机制与技术栈 | 是否真的做到、效果如何 |
| D · 二手搜索 | 搜索引擎摘要与第三方文章 | 线索与身份对照 | 细节与真实性 |

规则：**未观测到的能力一律记为"未知"，不写进对比矩阵当优点**；官方自述与实测必须分开标注。所有 REA 结论都带 evidence id 可复核。

## 2. 逐产品拆解

### 2.1 HackerMate（hackermate.in）——"Team Operating System"

**观测记录**：REA CDP 被动观测，Edge 155.0.4283.45 无头实例，目标 `https://www.hackermate.in/`（`list_browser_targets` = `ev_da1cf1e3…`，`inspect_web_page` = `ev_ee5ad847…`）；另将页面引用的 18 个 JS chunk 下载到 `.runtime/竞品逆向/hackermate-in/` 做本地静态检索。

**页面事实（A/B 级）**

- 一条五段流水线：`#find`（找）→`#review`（查）→`#merge`（并）→`#build`（建）→`#ship`（交）。
- 公开路由：`/`、`/login`、`/developers`、`/teams`、`/hackathons`、`/hackathons/<uuid>`、`/profile/<handle>`、`/contact`、`/faq`、`/terms`、`/privacy`；导航含 `practice`、`messages`。DOM 2261 节点。
- 首页数据条：registered builders **499**、teams **31**、hackathons listed **260**；学生免费；登录方式是 **Google 或 GitHub**（无邮箱验证码）。
- 组队机制文案（原句）：按"缺什么技能"搜索而不是"谁先回复"；过滤维度为 **Skill / experience / availability / college / year**；排序原则是"**People who add to your stack come before people who duplicate it**"；**每条推荐都给出理由（plain words）**；团队页显示**还缺哪些技能**，队伍状态只有 `Recruiting` / `Full`；候选人卡片显示 `Strong fit` / `Good fit`。
- 加入方式两类：`Requests`（对方申请，看资料后接受/拒绝）与 `Invites`（从搜索或工作区里的 squad matcher 邀请）。
- 工作区组件目录（B 级，来自 `2fp3ifzl9uvys.js`）：`chat`（语音条、图片、链接预览、表情）、`tasks`（列/负责人/优先级/截止，可拖拽）、`brainstorm`（发想法+投票，或共享文档共写）、`resources`（Figma/仓库/PPT/题目一处可达）、`github`（关联仓库看最近提交与谁在推）、`deployments`（填 demo/API 地址并在评审前检查可达）、`activity`（新任务/完成任务/共享链接/文档保存）、`ppt`（**按本赛道评审量规对 pitch deck 做 AI 复查**）、`gap_filler`（**具备团队仍缺技能、可直接邀请的人**）。
- 技术痕迹（B 级）：Next.js App Router + Turbopack；Supabase（`…supabase.co`）、Vercel、Resend、Sentry、Cloudflare（R2/S3 字样）、GitHub、Discord；websocket/realtime（`3to4ujc34co8n.js`、`221-t1kmilko-.js`）；观察到 1 个 API 路径 `/api/broadcast`；自托管分析脚本 `/<hash>/script.js` + Simple Analytics。

**可迁移优点**

1. **以"缺口"为组队的第一性问题**：不是"我们缺人"而是"我们还缺哪几项技能，下一个邀请要覆盖什么"。可在我们已有的招募帖 `neededRoles` + 成员职责事实上直接派生。
2. **每条推荐必须给理由**（且用普通话解释）。与宪法"每项建议说明依据"一致，可直接吸收。
3. **技能覆盖度是非打分布尔事实**（覆盖/未覆盖），天然规避我们不做的能力百分比与排名。
4. **工作区把"外部可核实状态"搬进来**：deployments 在评审前检查 demo 可达、github 显示最近提交——把"能不能演示"变成赛前可检查项。
5. **按赛道量规做赛前自检**（`ppt`）——注意它自称 AI 复查，不是正式评分；这正是我们允许的定位。
6. 五段命名极其好懂（找/查/并/建/交），比我们的"阶段编号"更利于新人。

**它的弱点 / 我们可超越的点**

1. 登录只有 Google/GitHub：**中国大陆新人常无法直接用**；我们有邮箱验证码 + 观猹 OAuth。
2. 只有英文界面与英文赛事语境，赛事列表是普通清单；我们有 DSH 分析 + 来源证据 + 报名/截止字段留空规则。
3. `Strong fit` / `Good fit` 出现在首页「Example data」演示区，**真实排序算法在登录后（`/developers` 返回 "Checking your session"）不可观测**：这类不透明分级容易被当成能力判定（与我们"不给能力百分比/匹配度"的既定约束冲突）。
4. 战绩字段（wins / teams / delivered）来源未标注是否可核验；我们的设计必须区分"平台记录已核验"与"本人自述未核验"。
5. 未见无障碍/中文/移动端的公开承诺；我们已有手机单列与键盘等价入口的既有约束。

### 2.2 HackBuddy（devpost.com/software/hackbuddy-uyxs83）——选手端 + MCP

**观测记录**：一手页面自述（C 级，官方项目页全文），URL 抓取于 2026-10-15，HTML 136KB。

**它自称做的事**

- 形态：Next.js 14 全栈应用，**同一份部署同时是实现了 JSON-RPC 2.0 的 MCP 服务**，网页 UI 与 IDE 内（Claude Code / Cursor）工具共用。
- 选手侧：从 Devpost URL 自动识别赛事 → 注册队伍 → 关联 GitHub 仓库 → **用真实量规做"练习评审"**（agentic AI 迭代读代码，每次最多 10 次工具调用，**引用具体文件**）→ 30 秒刷新一次的**对手仓库提交热力图**（SSE + 后台轮询 GitHub API）→ 倒计时与里程碑提示 → **相似度检测标记重叠项目** → 生成 pitch deck / README / 提交草稿 → **用浏览器自动化自动填满 Devpost 提交表单**（人类只负责过验证码）。
- 主办方侧：另有一套 dashboard，可创建/从 Devpost 导入赛事、向选手分享 MCP 配置、实时看队伍注册/练习分/提交。
- 多智能体：orchestrator 委派 organizer / participant / judge 子智能体。
- 技术栈自述：Gemini 2.5 Flash（评审主模型）、Groq/Llama-3.3-70B（降级链）、Clerk + GitHub OAuth、Puppeteer、Cheerio、Material UI、pptxgenjs、nodemailer。
- 自述的"坑"：**为翻分页参赛者数据逆向了 Devpost 的会话 cookie / Referer / X-Requested-With 组合**；GitHub 速率限制需要多 token 轮换、限制 8 仓库；Gemini 安全过滤会拦正常代码。
- 自述的经验：agentic 循环比单次提示判得好；**展示 agent 的调查轨迹让分数显得可信**；**绝不相信 LLM 的算术，加权总分一律在服务端重算**。

**可迁移优点**

1. **"服务端重算总分，不信模型算术"**——我们已按固定整数精度在服务端归一并加权（`src/modules/event-judging/validation.ts`），这条要继续写明。
2. **赛前"练习评审"必须与正式评审分开**：它明确是 practice-judge，我们的对应物只能是"本人/团队自检报告"，不能进正式分。
3. **引用具体证据（文件级）**：我们的评分/建议也应逐条给依据，而不是结论。
4. **相似/重叠提示**：与我们既有的"去重提示"一致，可作为人工复核的触发器。
5. **MCP 与网页共用一套事实**：我们已经有 DSH 与站内导航员，方向一致；可考虑让赛前自检也能从本机工具调用。

**必须明令禁止照搬的部分（红线）**

1. **不窥探竞争对手的仓库进度**（对手提交热力图）：未经同意读取他人私有/半公开进度，属于越权与不公平竞争；我们只做队内进度。
2. **不逆向第三方站点的反爬保护**（伪造 Referer / X-Requested-With / 会话 cookie 取分页数据）：与宪法"遵守 robots、公开网络范围"冲突。
3. **不代选手提交作品**（浏览器自动化填表）：正式提交必须本人确认；我们的边界是"核对清单 + 材料清单 + 回执"，不是自动投递。
4. **不让 AI 决定正式分数/晋级**：练习评审可以 AI，正式评分必须人填、系统按既定规则汇总、授权人员确认公布（宪法 XI 已有）。
5. 不做"对手进度"这类以竞争焦虑为卖点的功能；我们把同样的算力用在"自己队伍的差距与阻塞"上。

### 2.3 TechBurn（devpost.com/software/techburn）

**观测记录**：一手项目页全文（C 级）。Devpost 项目，提交于 Google Cloud/GitLab 系黑客松。

**它自称做的事**

- 形态：**去中心化、无数据库**的黑客松 OS，由 Gemini 3.1 Flash-Lite（Vertex AI）+ **GitLab MCP** 驱动，Google ADK 编排，Python Flask（`asyncio`）后端 + 单页看板，Cloud Run 部署，Web Speech API 语音输入 + Google TTS 语音回复。
- 主办方侧：用**语音对话**几秒内搭出赛题；agent 自动创建 GitLab 仓库、提交定制 `README.md`、生成 5 个里程碑 issue；赛事结束时触发 **Originality Scanner**，审计 commit 历史、时间戳与提交体积，**标记疑似抄袭或套用既有模板**。
- 选手侧：AI 结对开发——读代码、写实现、提交 bug 修复、自动开 MR；自动识别语言并生成 `.gitlab-ci.yml` 部署流水线；提交时把演示视频与说明打包成 `SUBMISSION.md`，**自动贴到主办方的集中提交串**。

**可迁移优点**

1. **"Originality Scanner" 用代码活动事实做原创性提示**（提交时间戳/体积/历史），与我们既有的"去重提示"同一类，但更有事实依据。
2. **里程碑 issue 化**：把赛程变成 5 个可见的里程碑，和我们"任务与计划"同构，可作为导入模板。
3. **语音/最简输入**降低门槛的方向值得记录，但对我们不是优先项。

**弱点与超越点**

1. 无数据库 = 数据在 GitLab，**没有权限模型、没有多机构、没有评审**，全靠 GitLab 的权限与人工。
2. "AI 自动提交/自动开 MR"存在**归属与合规争议**：谁写的代码、AI 生成算不算本人作品，它没有说明；我们必须保持"本人确认 + 如实标注"。
3. 强依赖 GitLab 账号与英文语音环境，中国新人门槛高。
4. **没有任何评分/评审机制**，只到"提交链接"为止。

### 2.5 CraftStadium Organize（organize.craftstadium.com，日本 CoPalette Inc）

**观测记录**：官网 pricing 页（A 级，已抓取）+ 公开扣分规则页 `www.craftstadium.com/en/help/penalty-rules`（A 级，已抓取全文）+ 分会话笔记（[竞品调研/craftstadium-hackathonos-brightidea.md](竞品调研/craftstadium-hackathonos-brightidea.md)）。

**页面事实**

- 定价透明且不按人数：**Free ¥0**（赛事创建/公开、参与者管理、成果物管理、结果与奖项、给全体参与者发信、提交表单自定义字段 1 个）；**Pro ¥20,000/月**（按队伍群发、邮件 CC、报名表单自定义字段至多 20 个、提交表单自定义字段至多 20 个、参与者/成果物 CSV、**Webhook 通知**）。
- 用于：企业招聘与品牌、教育机构 PBL、地方政府；有 iOS 参与者端；面向主办方把活动后数据做成为"给赞助商/议会/委托方的上报材料"。
- **团队编成是产品级对象**（分会话核实）：3 种编成模式 + 队伍 4 段状态机（募集中→调整中→確定→ロック）+ 拖拽调整 + 参与者技能自动带入编成视图。
- 成果物收集走 **GitHub App「选仓库即提交」**。
- **公开的量化公平规则（我逐字核对了该页）**：
  - 提交类：超时 15 分钟内 2 分、15 分钟–1 小时 5 分、超 1 小时 10 分；材料不全 轻微 1 分/重大 3 分；完全未提交 15 分。
  - **赛前开发（依据 GitHub 活动历史判定）**：开赛前轻微准备仅警告；提前 1 天开始写代码 5 分、2–3 天 10 分、4 天以上 20 分或失格；**复用既有项目 → 直接失格**。
  - 其他：盗用创意/侵权 → 失格；使用非官方工具 轻微 3 分/重大 10 分；违反组队规则 5 分；主题偏离 0/3/5 分或失格。
  - 递减扣分率：累计 <5 → 0%；5–10 → 5%；11–20 → 10%；21–30 → 20%；≥31 → 失格。
  - **基分 = 评委评分 × 0.75 + 选手互评 × 0.25**；最终分 = 基分 ×（1 − 扣分率）。规则页注明 2024-07-22 制定。
- 分会话核实到它官方自认的最大缺口：**「審査・採点 △」**——只有评审基准展示、评委登记与评语登记，**没有评委端打分与自动汇总**；此外无签到、不支持参赛费、无 SSO、只有日/英、API 自评"受限"。

**可迁移优点**

1. **公平性可以写成公开、可核验、可配置的规则表**（而不是含糊的"我们会公正评审"）。我们已有开轮冻结/回避/审计，缺的是**公开的量化规则包**。
2. **用仓库活动事实做"赛前开发/截止后变更"提示**：我们已有 M06 提交记录与 GitHub App 授权，这是最接近的既有资产。
3. **选手互评作为独立评分维度**（占 25%），可提升参与感与区分度。
4. **成果物"选仓库即提交"**把提交成本压到最低（与我们正式收件的材料快照互补）。
5. 团队编成状态机与拖拽调整，让"还在招人"这件事对主办方可见。
6. **活动后数据作为对赞助商/委托方的上报材料**——这是"办赛要交差"的真实需求。

**弱点与超越点**

1. 它**没有评委端打分与汇总**：这正是我们已实现的强项（维度加权、等权平均、冻结、回避、公布版本）。
2. 选手互评与评委分**混成一个基分**，解释性差（0.25 的权重写死）；我们可以做成"分列显示、可配置是否计入正式名次"。
3. 无中文、无 SSO、无签到、Webhook 只在 Pro。
4. 扣分规则虽然公开，但**判定依据主要是人工**；我们可以把"截止后变更/赛前提交"做成自动标记 + 人工确认。

### 2.6 JUDGELAYER（Tanya-garg10/JUDGELAYER-Self-Hosted-Hackathon-Submission-Judging-Platform）

**观测记录**：仓库页面 + `JUDGING.md`／`ARCHITECTURE.md`／`DATA-MODEL.md`／`README.md` 原文（B 级，代码级规格；仓库 2 star，DOGFOOD 2026 参赛作品）。

**机制事实（逐字核对）**

- 量规：4 个维度，权重 30/25/25/20（功能性/代码与架构质量/技术创新性/影响与可行性），1.0–5.0 分；原始分 = 加权和。
- **评委校准（这是它最大的卖点）**：对每个评委的 $N_j \ge 2$ 张已交评分算均值 $\mu_j$ 与标准差 $\sigma_j$；若 $\sigma_j < 0.15$ 判定"分数压缩"（打分无区分度）并在主办方控制台**标记该评委**；$Z = (S - \mu_j)/\max(\sigma_j, 0.25)$；再按全局均值/标准差映射回 1.0–5.0 并 clamp；项目分 = 各评委归一分的平均。
- 边界规则：每项目目标 3 份评审，不足则在控制台告警；**评委互盲**——评委与参与者都不能读同侪的草稿或原始评分表，服务端中间件硬拒绝（明确写"仅在客户端隐藏分数是无效的"），越权尝试返回 403 **并写不可变审计**（`PEER_ISOLATION_BOUNDARY_PROBED` / `BLOCKED_403`）；判据取服务端会话里的 `req.user.judge_id`，不信任客户端传参（`server.ts` L772–793）。
- **代码级核对（分会话逐行核实，重要）**：Z-score 公式在 `JUDGING.md` L25–41，唯一实现在 `server.ts` L294–382 `calculateScoresAndNormalization()`；压缩检测在 L890–902（`count>=3 && std<0.15`）；越权审计在 L178–199；另有 `POST /api/audit/probe` 一键自证清白（L1157–1213）。
- **实测与宣传的差距（负面发现）**：`JUDGING.md` L54 声称用标题 Levenshtein >85% 检测重复提交，**`server.ts` 全文没有该实现**，只读取 `fixtures.json` 里预置的静态 `is_duplicate`（L365/L888）。也就是说它的"重复提交检测"是**演示数据**，不是功能。
- 架构：**没有数据库**——内存 JS 对象 + `fs.writeFileSync` 全量 JSON 快照，启动时还会删旧文件（47 个文件，MIT，2 star，最后更新 2026-09-29）。

- 角色：organizer / judge / participant / visitor，逐端点允许/禁止表；截止后提交/改稿被拒（`DEADLINE_VIOLATION_REJECTED`）；CSV 导出仅主办方，RFC-4180 格式。
- 技术：零云依赖、自托管，Express REST + React（Vite），`run.py` 启动，数据在本地 `data/`。

**可迁移优点**

1. **评委严格度校准**：解决"遇到严评委就吃亏"，这是我们目前（等权平均）没有的。**但它的实现有明确缺陷**：`N_j = 1` 时 $\sigma_j = 0$，`Z = (S−μ)/max(0,0.25) = 0`，于是该评委给谁都返回全局平均——**一个只评了一个项目的评委，其评分区分度被完全抹平**。
2. **分数压缩检测**：一个评委给所有项目同一分数时，他实际没有区分度——应提示主办方，而不是静默计入。
3. **越权尝试即审计 + 一键自证**：把"试图看别人评分"本身记成事件；`/api/audit/probe` 让主办方随时验证隔离边界仍然生效（成本极低）。
4. **逐端点权限表 + "客户端隐藏无效"的明确立场**（`ARCHITECTURE.md` L101），与我们既有原则一致。
5. 压缩阈值、$\sigma$ 下限这类参数**写在文档里**，可被外部复核——比黑箱好。


**弱点与超越点**

1. **归一化分替换了原始分**：`S_p` 只用归一后的分，原始分在汇总里消失，事后无法回答"某评委到底给了几分"。我们应**原始分与校准分并列保留**。
2. $\sigma$ 下限 0.25、压缩阈值 0.15 都是硬编码常数，且 $N_j \ge 2$ 就开始校准——**样本极少**，两三个项目算出的标准差没有统计意义。我们应规定最小样本量，并在样本不足时**不校准、只提示**。
3. 校准可能**改变名次**却只体现在结果里，没有"校准前后对照"与人工确认环节；我们要求校准是**派生视图**且不得单独决定晋级。
4. 演示级认证（页面里直接给 persona/token 做"角色热切换"）、**没有数据库**（内存对象 + `fs.writeFileSync` 全量 JSON，启动删旧文件）：没有并发控制、没有事务、异常退出即丢状态，不适合真实赛事。
5. **宣传与实现不一致**："重复提交检测"在文档里承诺、代码里不存在（详见 2.11）。这提醒我们：**看到竞品文档的功能声明，必须落到代码或实测才能算数**。
6. 无中文、无移动端承诺、无申诉流程、无多机构隔离。


### 2.7 Synnovator（Synnovator/monorepo）

**观测记录**：仓库页面 + `README.md`（B 级）。

**机制事实**

- 自我定位：**Git 原生的 Hackathon 平台，由 GitHub Issue/PR 驱动活动全流程**；README 写 Apache 2.0，但**仓库里没有 LICENSE 文件**（分会话核实 API `license: null`），使用前需向作者确认。
- 目录即数据：`hackathons/`、`profiles/`、`teams/`（都是 YAML）、`docs/`、`apps/web`、`packages/`、`config/`、`scripts/`；pnpm + turbo 单仓（825 个文件，0 star，19 个 issue）；含 `.mcp.env.example`、`CLAUDE.md`。
- **GitHub Actions 就是后端**（22 个 workflow）。状态机在 `status-update.yml` L32–45：`draft → registration → development → submission → judging → announcement → award`（超期额外 `ended`），由 `hackathon.yml` 的 timeline 计算；L57–88 **幂等地摘掉旧 `stage:*` 标签再挂新标签**。标签规范：`hackathon:<slug>` / `stage:<s>` / `track:<t>` / `registered` / `nda-approved` / **`score-validated`**。
- **评审的"校验后再聚合"闸门**：`validate-score.yml` L26–141 跑 7 项检查，**通过才贴 `score-validated` 标签**，聚合脚本 `aggregate-scores.yml` 只消费带该标签的评分（L68）。这是很聪明的设计——**用标签当"已校验"的凭据，而不是相信输入**。
- **"AI 原生"名不副实**（分会话核实）：指的是仓库里 `.claude/` 技能驱动**运维审核**，产品本身没有 AI 功能。
- 分会话核实的其他实现状态：**没有 Z-score**（`aggregate-scores.yml` L153 直接算术平均）；硬约束 L117–124 自承未实现且 `hard_constraint_violations: []` 硬编码为空（L177）；投票分是 `// TODO`（L168）；并列无破平（L183）；**结果 JSON 泄露评委真名**（L81/L195 直接复用 `issue.user.login`）。

**可迁移优点**

1. **状态机 + 标签闸门**：赛事阶段由时间线派生、评分必须"先校验后聚合"——这套思路可以直接搬到我们的评审：**未通过校验的评分不进入汇总**（我们已有锁定与 checksum，但"闸门"这个表达更清楚）。
2. **一切变更都有公开的 PR 历史**：赛事规则、队伍、提交的每次变更都能被任何人追溯审阅——比我们"后台审计日志"更公开。
3. **数据即文件**：可 fork、可离线、可用 Git 备份，天然版本化；`profiles/_schema.yml` L30–39 的 `skills[].category+items[]`、`interests[]`、`looking_for{roles,team_size,collaboration_style}` 与 `teams/_schema.yml` L14 的 `status: recruiting|formed|disbanded` 是**可计算的结构**（对比 H@ckollab 的空壳匹配）。
4. **MCP 一等公民**（`.mcp.env.example`），与我们 DSH 方向一致。

**弱点与超越点**

1. 目标用户是**会写 YAML、会开 PR 的开发者**；我们要服务的"新人"根本进不来。
2. 无权限模型（靠 GitHub 仓库权限）、无邮件通知、无移动端、无隐私隔离（私人资料与公开数据同仓）；**结果还泄露评委真名**。
3. "AI 原生"是营销标签；评分是算术平均、无校准、无破平，硬约束未实现。
4. 我们可以吸收"公开可追溯"这一点，用**站内可读的版本与依据**实现，而不要求用户碰 Git。

### 2.8 Brightidea Hackathon 6（brightidea.com）

**已核实的空白（竞品有、我们没有）**

1. **技能缺口驱动的互补匹配**：只有"按角色/关键词浏览帖子"，没有"还缺哪几项技能 → 谁能补上 → 为什么"。
2. **可核验战绩**：名片与招募不含"已确认参与赛事 / 已收件交付 / 已发布复盘"这类平台记录派生的战绩；现有字段全部是本人自述。
3. **赛前自检报告**：没有"按本赛道量规检查我们自己的材料/演示/可达性"的自检（HackerMate `ppt` + HackBuddy practice-judge 的交集）。
4. **评委严格度校准**：目前只有等权平均，没有跨评委标准化的派生视图（JUDGELAYER 的 Z-score 思路），也没有"样本不足不校准"的规则。
5. **相似材料/重复提交提示**：没有查重或重叠提示（HackBuddy 有 similarity detector）。
6. **主办方长期影响与活动后分析**：只有结果公布，没有赛后统计与下一届复用（CraftStadium / Brightidea 的强项）。
7. **开发者友好的对接**：没有对外 API/Webhook/MCP 目录（Synnovator 用 GitHub Issue/PR 驱动；HackBuddy 把平台做成 MCP）。
8. **中文本地化与可达性**是我们的既有优势，但**未在对外页面形成清楚的对照说明**。
9. **公开的量化公平规则包**：我们没有公开的扣分/失格规则表（超时、材料不全、赛前开发、复用旧项目、主题偏离），也没有把这些规则接到真实事实（提交时间戳、仓库活动）上；CraftStadium 有一整套并公开。
10. **选手互评**：Brightidea 有参与者投票、CraftStadium 把互评做成基分的 25%；我们只有评委分。
11. **团队编成状态机与拖拽调整**：我们只有"接受/退出/冻结"，没有"募集中→调整中→確定→ロック"这样对主办方可见的编成状态。
12. **赛后统计与下一届复用清单**：我们公布了结果就没有下文；Brightidea 把它做成转化工作流，CraftStadium 做成对上汇报的图表。
13. **多时区按参与者本地时间展示/开赛**：字段有时区，展示与调度没有。
14. **线下赛事的三件套**（场馆导航、现场日程、现场聊天）：HackMate 有，我们没有；我们目前假设线上协作。

## 5. 可迁移清单（三分法）

> **这一节不是待办列表。** 按用户 2026-10-15 的要求——"目的是让我们的产品更好，不是把他们的功能无脑融入，避免新功能与网站本来功能冲突"——每一项都要先过 [规划 32 第 4.0 节](../规划/32-竞品能力对标与超越路线.md)的吸收闸门（① 解决我们哪个真实问题 ② 与哪些既有能力冲突 ③ 如何避免重复入口/第二份事实/第二套写路径）。**答不出，或冲突无法避免的，不做。** 经闸门判定后，A 类多数收敛为"只改既有流程内的呈现"，另有若干候选（选手互评、团队编成状态机、多时区调度、音频评语、场馆三件套、对外写入型 API）已明确不做。

**A. 直接吸收（与既有原则一致，且能促进超越）**

1. 缺口驱动组队：从"团队还缺哪几项已声明技能/职责"派生，逐条给理由，**不出综合分、不做跨人排名**。
2. 战绩只列**可核验事实**并标注来源类别（平台记录 / 本人自述），不合成"战绩分"。
3. 赛前自检报告：按本赛道量规逐项列"文件/材料级依据 + 缺什么 + 下一步"，明确非正式、不进正式分。
4. 相似材料提示 → 人工复核状态（复用既有 `needs_review` 语义，不自动判定作弊）。
5. 评委严格度校准作为**派生视图**：保留原始分，样本不足不校准，校准不得单独决定晋级。
6. 演示可达性检查（demo/API 链接是否可打开）挂在提交前核对清单里。
7. 工作区组件命名与"五段式"直白语言（找/查/并/建/交这类），用于新人主路径文案。

**B. 需改造后吸收**

1. 对外 MCP/API：先把"本站已实现能力"整理成只读目录，不承诺写入；不复制 HackBuddy 的"代提交"。
2. 赛后分析：先从既有公布结果、报名接受率、材料齐全度派生统计，不做"长期影响力评分"式的新事实。
3. GitHub 集成：只读展示本项目仓库的提交/健康度，不读取他人仓库（与 HackBuddy 的红线相对）。

**C. 明令禁止照搬（写入宪法）**

不透明匹配分/适配百分比、AI 决定正式评分或晋级、代选手提交、窥探他队/他人仓库进度、绕过第三方反爬、以竞争焦虑为卖点的对标排名。

## 6. 结论

**竞品的强项集中在五处**：缺口驱动的组队（HackerMate）、赛前自检与 AI 结对（HackBuddy/TechBurn）、公开量化的公平规则（CraftStadium）、评委校准与隔离审计（JUDGELAYER）、活动后闭环（Brightidea/CraftStadium）。**它们共同的天花板**是：英文或日文语境、要么不管评审要么只给大企业、要么靠第三方平台权限兜底、且**没有一家把"可核验事实"贯穿到组队、评审与结果**。

**我们的既有优势**：可核验的赛事事实与来源、中文与新人主路径、权限与私有空间隔离、正式收件与人工评审的不可改写、以及"不夸大、不给百分比"的既有纪律。

**超越路径**（写进宪法 v1.21.0 与规划 32）：

1. **把四段机制补齐，但每一段都接在可核验事实上**：缺口互补（依据本人声明 + 平台记录）、评分校准（依据原始分与足够样本）、公平规则（依据提交时间戳与仓库活动）、赛后复用（依据既有公布与复盘）。
2. **把它们的红线写成我们的"不做"**：不透明分、AI 判分、代提交、对手窥探、绕过反爬。
3. **把"可核验"变成看得见的产品差异**：同一份结果，任何人都能看到"这个结论依据哪条记录、哪个版本、什么时间"。
4. **不与它们比功能数量**：矩阵里我们要补的只有四处，其余格子我们已经领先或不需要补。
5. **把"宣传 ≠ 实现"变成我们的可信度资产**：本轮实测发现至少四家竞品的公开能力声明与代码/实测不符（见 2.11）。我们的对外文案与规划只写做过且可复核的事，并让用户能一键看到依据——这比多一个功能更难被模仿。
