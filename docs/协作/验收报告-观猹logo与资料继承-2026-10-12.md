# 观猹登录：官方 logo、头像与昵称继承 · 2026-10-12

用户三项要求：**显示观猹 logo**、**登录后无需再验证邮箱直接进入**、**继承观猹头像与名称**。
经确认，实现口径为：首次仍验证邮箱并关联（观猹通常不返回邮箱，本站账号以邮箱为唯一标识），
**之后用观猹登录直接进入**；头像存进本站既有头像能力并在页头显示；观猹昵称仅作**首次默认名**。

## 1. 观猹 logo（真实渲染已验证）

- 官方品牌资源来自观猹官网：`https://watcha.cn/_nuxt/brand.*.svg`（另有 `favicon.svg` 是吉祥物插画，不适合按钮）。
- 项目**没有静态图片目录**，一切资源内联，因此把它转成 `src/components/guancha-logo.tsx`：
  保留原始矢量路径（2 条）、`viewBox="0 0 92 32"`、品牌绿 `#3AAF78`；只做确定性清洗——
  去掉 XML 声明与编辑器残留的 blend 样式，并把连字符属性名转为 JSX 写法。
- 真浏览器证据（`tests/e2e/guancha-logo.spec.ts`）：按钮文案「使用观猹登录」、按钮内 1 个 svg、
  可见尺寸 **43×15px**、`viewBox` 与路径数正确、填充色为官方 `#3AAF78`、`aria-hidden="true"`（装饰元素不重复朗读）。

## 2. 继承观猹头像与昵称

链路：观猹 `userinfo` → 待关联记录 → 邮箱验证后确认关联 → 一次性同步。

| 环节 | 实现 |
| --- | --- |
| 取回头像地址 | `provider.ts` 读取官方 `avatar_url`（官方文档：有头像才返回），并做**格式白名单**：仅 https、host 属 `watcha.cn`/`*.watcha.cn`/`*.volces.com` |
| 待关联期间不丢资料 | 迁移 **069** 给 `guancha_pending_links` 加 `avatar_url`、`display_name`（都可空） |
| 下载头像（不可信输入） | 新增 `src/server/guancha-avatar.ts`：只允许 https+白名单、**不跟随跨站跳转**（≤3 跳且每跳重过白名单）、**按流限流读取**、按**魔数**判类型（不信响应头）、上限 512KB |
| 写入头像 | 复用招募模块**既有且已校验**的 `saveAvatar`（`validateAvatar` 会验尺寸与完整性），并保留其审计记录 |
| 昵称继承 | 迁移 **070** 给 `auth_users` 加 `display_name_customized`；仅当该标记为 `false` 时采用观猹昵称，随后置 `true` |
| 页头显示 | `site-shell.tsx` 的 `AccountAvatar` 用既有 `GET /me/recruiting-profile/avatar`；加载失败或没有头像**回落姓名首字** |

**关键安全约定**：`syncLinkedProfile` 的任何失败**只记录、不抛出**——头像或昵称拿不到绝不能
让一次已经成功的关联登录失败（有测试锁定）。

## 3. 过程中发现并修掉的真实缺陷

### 3.1 昵称继承原本永远不会生效（我的实现错误，被测试逼出来）

我最初用"昵称是否等于邮箱前缀"来判断能否继承。测试证明该谓词恒为假——注册时的默认昵称是
**「参赛新人」**（`src/modules/auth/postgres.ts:134`），不是邮箱前缀。也就是说这条逻辑在真实环境里
**一次都不会生效**，而且靠猜默认值本身不可靠（用户完全可能取一样的名字）。

改为**显式标记**方案：迁移 070 加 `display_name_customized`（注册为 `false`，用户经 `patchMe` 改名时置 `true`，
迁移按"昵称既非空也不等于注册默认值"回填既有账号）。同步逻辑据此判定，并有测试覆盖
"默认名被继承并置标记 / 自定昵称不被覆盖 / 再次登录不改写 / 非法昵称被忽略"。

### 3.2 观猹模块夹具 schema 与真实库脱节

`src/modules/guancha-login/schema.sql` 是模块自带的测试建表脚本；迁移 069 的两列没有同步进去，
导致 11 项 `guancha-auth` 测试直接因缺列失败。已同步该文件，并在 `guancha-auth.test.ts` 中更新
`confirmLink` 的返回断言（现会带回 `profileSync`）。

### 3.3 我自己造成的站点 500（已修复并记录）

执行顺序 `停止 → 跑根测试 → 启动` 时，根测试里的 `graceful-stop` 用例会覆盖
`.runtime/server-control/current.json`，导致真正监听 3000 的进程被遗弃（仍占用端口），
新实例的 instrumentation 加载失败并报 `GRACEFUL_STOP_REJECTED`，**全站 500**。
按既有规则修复：结束监听 3000 的孤儿进程 → 确认端口释放 → 重新启动。
**教训：绝不在启停之间夹跑会改动控制状态的测试。**

## 5. 仍需真人完成的一次验收

`https://frp-off.com:44353/api/v1/auth/guancha/callback`、真实令牌交换、身份绑定落库，
以及**首次关联后头像与昵称是否真的落到本站**。本次仅验证到"跳向观猹官方端点、且对端认识该 client_id"。

**未解决边界**：普通公网 DNS 与旧入口自签证书仍为独立事项。
