# 数据与接口协作约定

日期：2026-10-08 · 草案 v0.2  
用途：统一独立模块之间的数据、权限和状态。实现时由数据库迁移与接口 schema 固化，不以各页面自己的临时字段作为事实。

## 1. 基本约定

- API 前缀 `/api/v1`，示例中的 `{id}`、`:id` 都是路径参数，实施时统一代码风格。
- 内部 ID 为稳定不透明字符串；知道 ID 不代表有权限。
- 服务端从会话取得 actorId，不能信任请求中的 userId、role 或 projectId 归属。
- 时间存储实际时刻，传输带时区的 ISO 8601，并保存规则原始时区/文字来源。界面显示完整截止时间和时区，倒计时只作辅助。
- 所有数值标明单位：估时使用分钟或小时中的一种统一存储；百分比分母/公式定义清楚。
- `version` 与 `revision` 都表示乐观锁修订号，均为单调递增整数；实现可统一命名，但不能丢掉检查。客户端对应发送 `expectedVersion` 或 `expectedRevision`。
- 已应用历史版本不可原地改写；新修改生成新版本。资料单独有撤回/删除规则，不承诺审计数据无限保留。

## 2. 建议公共响应

正常响应包括 `data` 和 `requestId`；分页包括 `nextCursor`。
长任务返回 202、jobId 和当前状态，客户端不把 202 显示为完成。

```json
{
  "data": { "jobId": "job_example", "status": "queued" },
  "requestId": "req_example"
}
```

失败返回稳定错误 code、可理解的中文 message、适用恢复动作与 requestId。
HTTP 状态建议：401 会话无效、403 无权限、404 对象不存在/需要隐藏存在性、409 版本冲突、422 输入/业务校验失败、429 频率/预算限制、503 服务暂不可用。

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "队友已更新这份计划，请对照最新版本后再应用。",
    "recoveryAction": "review_latest_version",
    "latestRevision": 8
  },
  "requestId": "req_example"
}
```

不得返回第三方令牌、原始隐私答案或服务器内部栈作为普通错误详情。
幂等键限定 actor、项目、操作和输入哈希；相同键不同内容拒绝。不同队伍不会因为共享缓存键而获得彼此数据。

## 3. 权限单一依据

| 域 | 角色/关系建议 | 权限依据 |
| --- | --- | --- |
| 团队 | TeamMembership `captain / member` | 团队成员与邀请管理 |
| 项目 | ProjectMembership `manager / member` | 本项目数据与管理动作 |
| 本人数据 | owner userId | 本人原始测评、个人收藏、账号 |
| 后台 | 独立运营角色 | 公开内容审核，不自动读取全部私人项目 |
| GitHub | 用户与 App 的实际授权/仓库操作条件 | M06 单独校验，不由本站角色扩张 |

团队队长与项目管理员是不同域；UI 可以把某项目管理员称为“负责人”，但代码不能用 Team captain 代替 Project manager。
个人项目不必有 Team，但必须有本人的 ProjectMembership.manager 记录。
同队不自动进入所有私人项目。最后管理员退出/降级需先转移，避免项目无人管理。

成员可更新本人任务进度、本人可用时间、本人共享资料。规则确认、分工/计划应用、管理角色与项目范围修改默认由项目管理员操作。
GitHub 保存操作还需校验 M06 能力；“项目管理员”本身不能授予任何仓库写权限。

## 4. 数据所有者与引用

| 内容 | 所有者 | 关键引用 |
| --- | --- | --- |
| User/Session | M01 | actorId 从认证生成 |
| Project/成员/邀请 | M02 | 私人业务均关联 projectId；Membership 统一使用 status |
| MemberAvailability | M02 管本人输入与权限 | 是项目内个人可用时间集合，含窗口/版本与确认时间 |
| AvailabilityWindow | M05 定义排程所需窗口 | 属于 MemberAvailability，不另建相互矛盾的可用时间来源 |
| Event/RuleEvidence/EventAnalysis | M03 | 规则快照带来源和版本 |
| SourceConfig | M08 | 域/路径白名单、频率、凭据策略、来源健康状态 |
| EventSource | M03 内容契约；M08 采集保存 | 单次来源快照/证据，引用 sourceConfigId；不把配置与多次快照混为一个对象 |
| ProjectRequirementLink | M02/M03 | 项目引用已确认条款版本与确认时间 |
| QuestionSet/RubricVersion/AssessmentAttempt/Score | M04 | 固定版本；原始回答本人私有 |
| AssignmentVersion | M04 | 项目分工草案/应用版本 |
| PlanVersion/Task/Dependency/ProgressUpdate | M05 | 输入快照含规则、分工、成员、可用时间版本 |
| RepositoryBinding/GitOperation/DeliveryVerification/SubmissionRecord | M06 | 仓库保存、运行验证、赛事提交三种独立事实；M07 读取或调用 M06 服务 |
| Retrospective | M07 | 引用必要证据，复用时不继承授权与成功状态 |
| Resource/ResourceCategory | M09 定义；M08 发布 | 统一字段，不因前台/后台另建两份资源 |
| ResourceReview/CrawlRun/AnalysisRun/AuditEvent | M08 或对应操作模块 | 记录核验/执行事实，脱敏与限定保留 |
| ResourceBookmark | M09 | 个人私有收藏 |
| ProjectResourceBookmark | M02 | 项目共享资料，引用 resourceId 或成员自定义 URL |
| Skill/SkillVersion/TrackBundleVersion/SkillCompatibility/BundleCompatibility | M10 新增规划 | 独立于 Resource；固定来源 commit、内容哈希与单项/整包实测环境；M08 经发布 Port 审核 |
| InstallationPlan/InstallationReceipt | M10 新增规划 | 用户、工具、范围、manifestHash、有效期与每项结果；本机路径/密钥不回传 |
| ProjectSkillBundleRef/Task.skillRefs | M02/M05 后续明确接入 | 引用固定 skillVersionId/bundleVersionId，不能用 Resource 的发布状态替代兼容状态 |

M04/M05 不能直接写 M02 成员权限；M03 新规则发布不能静默覆盖项目快照；M09 下架资源不能自动删除项目引用。
需要影响生效计划的输入变化，标记需复核并创建调整建议，由管理员确认。
`Project.createdBy` 仅记录创建者，不形成第三种权限角色；当前管理权限只由活跃 ProjectMembership 决定。
M10 目前只有规划，没有落地接口或新模块会话；这些新增行不要求现有模块自行改表、扩枚举或实现安装执行。主会话登记新增契约后再集成。

### 技能与本机安装契约

- `SkillVersion` 是不可变内容版本，ID 与内部修订号分开；上游 tag/版本标签仅作来源字段，不能替代完整 commit 与内容哈希。
- 已发布包固定引用确切 SkillVersion；修改产生新版本。兼容证据绑定工具版本、操作系统、方法与日期，不自动延用到新环境。
- 整包兼容必须验证同一环境中的全部必需项与最小产物，不用不同环境的单项结果拼成整包成功。
- 安装授权绑定 userId、agentId、scope、manifestHash、adapterVersion、有效期和 operationId。网站不发送任意 shell 文本让本地端执行。
- 网站登录不代表本机目录授权；用户在本机选择目录，配对客户端校验计划与操作范围。本机敏感绝对路径与凭据留在本地。
- 安装回执按项记录 source、文件校验、客户端加载、样例验证与错误。用户自报与配对客户端回执分别标明，不能宣称服务器已独立验证本机全部行为。
- 复制命令仅是 UI 操作；安装器声明仅是能力线索。两者都不构成实际安装记录。
- 同名冲突默认保留已有内容；恢复/移除先比较当前文件与本次写入，不能静默丢弃用户修改。
- 安装写入前重新校验计划与当前撤回状态；已撤回内容的未执行计划失效，不因下载暂存成功继续安装。

### 交付事实契约

`DeliveryVerification` 由 M06 管理，字段至少包含 projectId、关联 commit/演示版本、结论、verificationSource、evidenceRefs、记录人和时间。
M07 可以提供填写入口，但通过同一 `POST /projects/{id}/delivery-verifications` 服务写入，不建立第二份验收事实。
`SubmissionRecord` 只记录赛事提交，建议字段为：projectId、eventId、stageId、requirementsVersion、platformUrl、submittedAt、verificationSource、repositoryCommitSha（可空）、status、evidenceRefs。
verificationSource 为 user_reported/platform_verified；status 建议 not_submitted/reported/verified/rejected_or_withdrawn。
未发生提交不应伪造 submittedAt；单个阶段提交不能代表所有阶段已完成。平台验证状态仅在官方能力实际接入并返回证据时可用。

### 事件名称

M03 生产 `EventRulesChanged / ProjectRequirementsConfirmed`；M02 生产 `ProjectMemberJoined / ProjectMemberLeft / MemberAvailabilityChanged`；
M04 生产 `AssessmentSummaryUpdated / AssignmentApplied`；M05 生产生效计划和进度相关事件；M06 生产 `GitSaveSucceeded / DeliveryValidationRecorded / SubmissionRecorded`。
下游按以上名字引用，成员变动不再另发意义不明的 MembershipChanged。规则变更提示复核，只有项目确认的新版本才进入正式计划输入。

### 页面与 API 路由

页面统一 `/app/projects/{id}` 为概览，`/rules /team /assessment /plan /delivery /resources /retrospective` 为子页面。
API 为 `/api/v1/projects/{id}/...`。旧示例的页面 `/projects/{id}` 或 `/overview` 若在实现中保留，则显式重定向到规范页面，不维护两套独立页面。

## 5. 不同状态不要复用同一字段

- `Project.stage` 是流程位置：draft/preparing/active/finalizing/submitted/retrospective/archived 的候选集合；阶段显示不能替代事实证据。
- `AssignmentVersion.status=ready` 只表示结构可确认，不意味着时间上可行。
- `PlanVersion.status` 表示草案、校验、生效与替代；`feasibility` 单独表示 unknown/feasible/at_risk/infeasible。
- 计划不确定或不可行时展示缺口。管理员选择应用包含风险的计划，只能表示已知情选择，不能变成绿色“可按时完成”。
- `Task.status` 由进度与验收定义；计划日期过去、AI 生成代码或仓库有 commit 都不自动让任务 done。
- `GitOperation.status` 表示一次仓库操作。未知结果要核对，不盲目重复写入。
- 运行验收和 `SubmissionRecord` 是独立记录。用户自报提交显示 user_reported，平台确认才可标 platform_verified。
- Resource `publicationStatus` 表示审核发布；`linkStatus` 表示链接核查；费用与许可分别可以 unknown，不能合成一个“认证安全”标签。
- Skill 内容发布、许可、兼容、文件安装、客户端加载、示例结果分别记录。套餐部分成功不显示全包成功，安装完成不使 Task 自动 done。

## 6. 版本、并发与事务

规则确认、分工应用、计划应用、角色修改必须验证预期版本与当前成员资格。
在同一数据库事务中更新生效指针、必要任务引用与审计；不允许应用一半留下两套生效计划。
外部 GitHub 写入不能包在长数据库事务里。先保存 GitOperation 与幂等键，再执行；返回不明时查询已知分支/commit/PR，对账后定最终状态。

若采用 outbox，它是事务性待通知记录：最少包含 eventId/type/aggregateId/projectId/version/occurredAt。
事件可能重复，消费者按 eventId 和版本去重。事件携带必要标识与差异摘要，不广播原始答案、凭据或完整文件。
没有跨模块异步通知需求时使用同一业务服务内的明确调用即可，不为统一命名强行搭建消息平台。

## 7. 生成与采集任务

记录 Job 的输入哈希/版本、状态、执行次数、时长、错误类别、结果引用和预算。
建议公共状态 queued/running/succeeded/failed/cancelled；模块可以保留自己的执行步骤。
重试仅针对明确可重试错误，默认上限由实测与模块规则确定。取消不会声称已撤回已经完成的外部动作。

模型输出需验证 JSON schema、对象归属、成员 ID、资源 ID、日期和必填信息。
输入更新、成员离开、共享权限撤回或资源下架后，旧缓存不得绕过当前权限校验。
DSH 只处理批准来源与采集草稿。采集/提取 succeeded 不等于内容 published。

## 8. 模块集成时的最低检查

1. 字段、ID、状态与权限是否符合本文？
2. 是否能从结果追溯输入和规则版本？
3. 输入变化如何标记过期、提示并重新确认？
4. 是否允许重复调用、并发修改与离开页面恢复？
5. 是否存在将草稿、模拟结果或用户自报显示为已验证成功的路径？
6. 是否有两份拥有同一事实、可能互相矛盾的数据？

## 9. 主办方与多赛事补充（2026-10-11）

公共契约为 `src/shared/organizer-contracts.ts`，由主会话维护。OrganizerPrincipal 包含真实 Actor 与同事务会话/账号 guard，模块私有读写须执行 guard，并由 HostedEventAccessPort 复核当前组织/赛事授权；不能以请求中的 organizationId/eventId 直接授权。

O01拥有机构、授权、HostedEvent与发布版本；O02拥有报名答卷和正式队伍，导出 EventParticipationPort；O03拥有官方沟通与现场服务；O04拥有收件与人工评审。HostedEvent.eventId 是运营赛事ID，linkedEventId 是显式M03关联；不能按标题合并。私人Project是M02事实，关联正式队伍不复制权限。跨模块复用传入SqlExecutor，不私查其他模块表，不并行嵌套事务。

正式队伍只计已接受成员，eligible从当前批准报名派生。评委来自当前明确指派与回避检查，不借平台角色直接授权。正式收件通过 VerifiedEventSubmissionPort 关联M06；公共用户输入不得构造 platform_verified/verified。没有M03/项目关联时允许主办方收件，但不伪造M06项目提交。

导出/公开缓存/检索/模型上下文均保留组织、赛事、权限范围；联系人、答卷、私人求助、住宿、评委材料不混入公开投影。评审AI不复用选手的记忆、会话或队列。通知发布、站内已读、发信接受与实际投递分别记录。模板隐藏未启用模块，但不能消灭历史事实。
