# 主办方入驻与多赛事运营实施规划

日期：2026-10-11。依据用户本轮“完善想法，写宪法，写规划，分会话执行任务”，以及一个网站同时接待多场比赛、主办方与选手紧密沟通、操作简单顺手的明确要求。对应宪法 v1.11.0。

本文件定义实施目标，不把写文档、派发任务或模块测试当作实际上线。既有赛事发现、团队协作、私人 AI 和交付记录继续保留。域名证书是独立并行事项，不能用暂缓公网来阻止本机开发，也不能把本机测试冒充公网通过。

## 1. 产品定位与完善后的想法

同一平台服务选手执行参赛任务和主办方运营赛事。主办方配置正式规则、报名、队伍、行程与评审；选手进入正确的赛事空间，再进入属于自己的团队工作台。共同交集是明确发布的规则、通知、问答、正式作品及回执，不包含选手私人助手记忆或未提交草稿。

目标是覆盖常见黑客松，通过线上、线下、校园/社区练习赛模板和有限参数复用。首版不承诺适配所有任意流程，不提供可执行脚本/任意表达式的流程配置。新复杂度需由实际主办方需求证明。

一账号可跨组织参加多场赛事、担任不同身份；一个组织可管理多场赛事。角色范围按组织、赛事、模块及评审指派分别授权，不是全站角色继承树。比赛 A 与比赛 B 的资料、草稿、报名、队伍、通知和评审隔离。

## 2. 简单顺手是实施约束

- 主办方主要路径：入驻/审批状态 → 选模板创建赛事 → 检查预览并发布 → 处理当前待办。高级设置收起，模板默认值可修改。
- 选手主要路径：进入赛事 → 完成简短报名 → 看当前下一步与自己的队伍。允许先浏览公开规则，不强迫先建机构或固定队伍。
- 固定展示比赛名、主办方、举办时间、当前身份和切换入口；报名、问答、作品提交、餐券核销均明确目标赛事。
- “我的比赛”来自真实报名/赛事身份；切换后清掉另一赛事的私人页面缓存和未提交表单，先提示保存/放弃，不能偷偷转投。
- 表单字段优先提供常用预设及上下移动；拖拽不是必需。展示默认、必填及说明，不让主办方写 JSON 才能开赛。
- 选手页面只显示启用且本人可用的模块。主办方后台用待审核、待回复、待收件、待评审等真实计数，不并列堆满所有源码模块。
- loading、空、失败、过期、已保存分别说明，失败保留本页输入。手机主要按钮无需横向滚动；高级信息折叠但关键期限/权限/费用不隐藏。
- 登录、注册、首次引导均保留赛事链接/问答/报名原目的地；不自动接受邀请、报名、发布或共享。

## 3. 本轮实施范围

本轮 O01–O04 实现持久的首版运营闭环及基础现场服务：
1. 机构申请、平台人工审核、组织/赛事工作人员按范围授权。
2. 版本化赛事模板、模块开关、正式发布与公开赛事大厅、我的比赛、赛事工作区。
3. 免费个人报名、动态字段、可选人工审核、人数额度、撤回；事件内正式队伍和自愿加入，关联已有私人项目需明确确认。
4. 官方通知/版本已读、公开问答与私人求助、工作人员答复和处理状态；版本化行程，本人后勤安排。
5. 主办方收件回执、不可变材料快照、人工评委指派与回避、权重评分、锁定和人工公布。
6. 破冰提供活动/自愿参与与分组记录；住宿先人工分配/导入预览，餐券先发放与单次核销，不假装完成酒店订房或餐饮支付。
7. 数据统计/CSV 导出按当前权限执行，CSV 文本防公式执行；小规模试用使用既有单实例持久 PGlite，线上 PostgreSQL 并发另行验证。

不在本轮实施的外部商业/高级能力：收费与退款/发票、手机短信账号、短信通知、酒店供应商预订、任意流程设计器、自动决定录取/晋级/获奖、跨平台微信聊天同步、未经授权读取备赛内容。邮件通知须接既有发送服务与投递状态；只有站内成功不能宣称已送邮箱。自动组队只做可解释建议、用户确认；首版可先用人工分配/自愿加入。

## 4. 信息架构与页面

| 页面 | 使用者 | 主要动作 |
| --- | --- | --- |
| /organizers | 公开/登录 | 理解办赛能力，申请入驻，查看审批状态 |
| /organizers/workspace | 已入驻工作人员 | 选择机构和赛事，处理真实待办 |
| /competitions | 公开 | 浏览主办方正式发布赛事，与 DSH 发现明确区分 |
| /competitions/[eventId] | 公开/报名者 | 看规则、报名状态、下一步、最新官方通知 |
| /competitions/[eventId]/register | 本人 | 填写/修改当前表单，提交与查看审核结果 |
| /competitions/[eventId]/teams | 有资格选手 | 找队伍/确认加入/进入关联私人团队空间 |
| /competitions/[eventId]/help | 公开问答/本人求助 | 发问题、查看明确答复和处理进度 |
| /competitions/[eventId]/schedule | 按可见范围 | 看行程、地点和更新说明 |
| /competitions/[eventId]/services | 本人/后勤人员 | 看自己的住宿、餐券、破冰活动 |
| /competitions/[eventId]/submit | 当前队伍授权提交者 | 确认材料快照、提交、查回执 |
| /competitions/[eventId]/results | 已公布范围 | 查看结果及允许公开的反馈 |
| /judging/[eventId] | 被指派评委 | 申报回避、读正式材料、保存/提交评分 |
| /admin/organizers | 平台当前管理员 | 核查机构申请，不自动保证赛事质量 |

这些路由是根接入目标，只有根组合完成后才标为已可用。源码模块不等于一级导航入口；主导航保留简洁，正式赛事由找比赛入口连接，主办方入口置于清楚的次级导航，评审从本人被指派入口进入。

## 5. 数据归属与共同接口

| 所有者 | 实体/事实 |
| --- | --- |
| O01 organizer | Organization、OrganizationApplication、StaffGrant、HostedEvent、不可变发布版本、模板、审计 |
| O02 event-registration | 表单配置/答卷版本、Registration、RosterTeam、成员接受/名额/锁定、项目关联请求 |
| O03 event-communication | Announcement/ReadReceipt、HelpTicket/Reply、ScheduleRevision、IcebreakerActivity、AccommodationAssignment、MealVoucher/Redemption |
| O04 event-judging | IntakeSnapshot/Receipt、评审轮/标准/指派/回避/人工分数/结果发布版本 |
| 既有 M02 | 私人 Project/ProjectMembership/任务协作事实；不复制造成员权限 |
| 既有 M03 | 经审核正式规则及来源；抓取线索不得直接获得机构认证 |
| 既有 M06 | 参赛侧 SubmissionRecord/运行事实；正式收件回执通过 Port 关联，不能创建互相矛盾的已提交状态 |

共用 src/shared/organizer-contracts.ts。所有访问由 actor 的真实会话和服务端事实产生；tenant/organization/event IDs 不可从请求 JSON 直接当授权。模块不能直接查/写另一模块表，跨模块用注入 Port，并复用同一 SqlExecutor。根负责目前 auth_users 表的当前账号检查、请求会话复核、Origin/CSRF、实际迁移和组合。

HostedEvent 是主办方运营标识；M03 eventId 是原赛事事实标识，两者显式关联才能同步确认规则和 M06 收件状态，不可因为名称相同合并。未关联项目的队伍允许完成主办方侧正式收件；不得伪造 M06 projectId 或平台验证记录。

公开结果只投影主办方明确发布字段；联系人、答卷、私密求助、住宿、完整评委记录不能混进公开赛事缓存或全站检索。每条导出、后台任务、文件和模型检索都带组织/赛事授权范围。

## 6. 关键状态与业务规则

- 入驻 pending/approved/rejected/suspended；学校、公司、社区均可申请，社区无营业执照可提供公开活动/授权依据供人核查。仅现有平台 admin 可审核，机构负责人不能自审或借 reviewer 身份通过。
- 赛事 draft/published/ended/archived；发布要求审核通过的组织、明确名称/时区/时间、负责人和可用模块配置。模板身份与实际官方赛道不同。
- 报名 draft/pending/approved/rejected/withdrawn。关闭审核时可在事务里 approved；审核打开时只表示已收到。唯一(eventId,userId)，额度/重放/撤回/审核写同事务，不让单纯重复请求产生多份报名。
- 正式队伍是赛事名单，私人空间是备赛协作。队长不能代替全员同意/报名通过；人数、锁定、成员资格、退出、名额均从真实事实派生。关联空间须当前项目管理员同意，不授主办方该空间权限。
- 公开问答和私人问题是不同范围。私人问题需本人明确确认才可匿名转成公开 FAQ，删除姓名仍不保证内容不识别本人，预览由本人确认。
- 通知已发布、站内已读、邮件接受、邮件实际投递分别记录；重要变更形成新版本，旧已读不能当新版本已读。只浏览不能标报名、提交或任务完成。
- 作品材料按明确预览冻结 URL/文字/文件元数据/哈希/规则版本，网址提交不表示服务端已运行代码。相同幂等键绑定同一输入，未知外部结果不盲目重发。
- 人工评分标准在轮次开始前校验权重合计100%、范围、评委数、缺分/同分处理；开始后冻结。不评分不能当0分；缺评、回避、撤销指派都需清楚显示。最终结果由有权负责人确认发布，不能从AI评分自动产生。
- 利益冲突有系统内关联检查与人工申报；平台不能知道所有线下辅导。回避后禁止该评委读/评分该作品；主办方管理员不自动获得替评委打分权限。
- 餐券 token 不公开到页面列表/日志/第三方二维码；核销授权和最后一次使用原子执行，重试不二次扣券。住宿只向本人和专责人员展示，不公开整张名单。
- 任一已使用配置重大修改形成新版本，展示影响和通知；不能用关模块清空历史、取消已经收到的作品或隐藏未解决求助。

## 7. AI 边界

自由聊天仍使用实际 DSH。选手助手继承本人导航记忆；主办方客服与评审辅助分开身份/上下文/检索/缓存/队列。评审绝不读取选手导航或空间 AI 记忆、测评或未提交代码。模型无执行工具，仅可按允许输入做格式检查、规则引用、查重线索、事实摘要。AI 摘要可展开原文依据，不用评价性措辞替评委决定分数、晋级或资格。官方答复需工作人员确认，AI 草案不能自动发布为赛事规则。

本轮先保障人工闭环，即使 DSH 失败仍可报名、沟通、收件、评分。新增真实 AI 调用由根纳入既有预算/unknown hold；网页读取不发起模型。没有正式隔离适配和真实验收前，不提供看似已分析的静态回答。

## 8. 根实施和并行顺序

1. 根先同步宪法、总体入口、本规划、四份分项、协作登记与公共 Port；不触碰域名服务和 live DB。
2. O01–O04 在各自新目录并行，先交模型/Port/API登记、再服务/SQL建议/组件/测试。跨模块接口变动请求根裁决，不私自修改共享文件。
3. 根逐项组合服务、固定方法API、组织/赛事上下文页、导航；增量042起迁移，先隔离数据库验证，再停实际网站冷备并迁移、构建、单实例重启。
4. 根执行两机构三赛事角色矩阵与手机流程；验证用户只看到对应比赛、同一用户切换赛事不会转投/泄漏、报名最后名额、撤权、求助私密、评审回避、作品幂等、券重复核销。
5. 域名代理完成免费可信证书后根受控配置现有穿透，再精确更新 AUTH_ORIGIN；真实手机、主办方试用、PostgreSQL并发另列验收结果。

## 9. 验收与完成标准

首版贯通：申请机构 → 人工审核 → 模板创建并发布 → 选手持链接登录并报名 → 组队 → 通知/求助/行程 → 选择正式材料收件 → 无冲突评委人工评分 → 负责人发布结果 → 本人查看反馈。

2026-10-11 用户补充：**报名链接属于主办方招生功能**。主办方在工作台发布正式规则和报名表后，复制本站 `/competitions/[eventId]/register` 完整链接，自行发布到微信、公众号、小红书等社交平台。各渠道使用同一场赛事的链接；无需队伍邀请，本站不替主办方自动向社交平台发消息。选手可匿名查看公开说明，提交前登录或注册，并返回原比赛。已发布规则但尚无报名表时，明确提示先配置报名表；未开始、已截止、已结束或运营暂停时保留真实说明与本人已有记录，不声称正在接收新报名。

主办方从显眼的“查看报名与审核”入口集中处理报名：默认查看待审核名单，可筛选全部、已通过、未通过等状态，核对本场答卷后通过或拒绝，并填写原因。启用人工审核时，提交只表示已收到，不能表示审核通过；关闭审核时按真实服务器确认结果显示。报名名单与答卷仅向当前本场报名管理人员开放，不因公开分享链接公开联系方式或答案。审核完成后，选手在报名页及“我的比赛”查看结果与下一步。

最低隔离场景：组织甲/乙与赛事A/B/C；账号同时是A选手、B评委、C工作人员，任何单独角色不能放大为跨赛权限。组织管理员不能读私人项目。直接猜ID/过期会话/撤权/缓存/导出均覆盖。

简单性验收：不用编辑JSON即可发布标准赛事；首次报名不重复填机构或私人画像；移动端看得到当前比赛、期限、下一步；工作人员待办能直接到目标问题；切换赛事明确处理本地草稿；启用模块均有入口，未实现能力标注并提供可执行替代。

交付状态区分：已派发、模块交付、根接入、隔离测试、本机运行、外部真实验收。两家主办方不同配置无改代码跑完真实赛事是后续试用标准，不由开发夹具冒充。
