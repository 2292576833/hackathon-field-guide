# 主办方入驻完善：认领已发现赛事与补充未知字段

日期：2026-10-11。依据用户"根据当前黑客松比赛，完善主办方入驻，规划、写宪法、完成"。
承接 [规划21 主办方入驻与多赛事运营](21-主办方入驻与多赛事运营.md) 与 [规划22 报名发布与专属入选通知](22-报名发布与专属入选通知.md)，对应宪法 v1.15.0。

本文件是**可实施规划**：第 1–8 节说明想法与依据，第 9 节起给出数据归属、接口、页面、状态与验收。**本轮只完成规划与宪法，不实施代码**；实施按第 14 节的登记另行授权。

## 1. 为什么要从"当前比赛"倒推主办方入驻

写这份完善方案前，我读取了运行库中**真实保存的 15 场赛事卡片**。它们的实际构成决定了主办方入驻该怎么做才顺手：

| 观察（真实数据） | 对主办方入驻的含义 |
| --- | --- |
| 来源集中在第三方目录与聚合站：`hackertrip.space`（7 场）、`lablab.ai`、比赛官网、高校就业网、即刻帖子 | 我们的公开赛事页**大量内容来自第三方**，主办方本人往往不在场 |
| **15 场里只有 3 场**有报名窗口或开赛窗口证据，其余为空 | "截止时间未知"是常态，而**只有主办方能给出权威答案** |
| 有证据的 3 场里，2 场仍标为 `status: unknown`（如"9月7日报名开启"没写截止日） | 连抓到的证据也常不足以确认关键字段 |
| 构成横跨：高校赛（中原大学、新竹政策、重庆大学）、企业赛（天猫、Anker、超聚变、知存科技、支付宝、Google Cloud、AMD）、社区/黑客松社区（GOSIM、ClawHunt）、海外（ETHGlobal Lisbon） | 只有"线上/线下/练习赛"三种模板不够用 |
| 赛制包含**初赛评审 + 网友人气投票 + 48H 总决赛**（天猫赛）；**线上报名 → 提案书 → 决赛**（中原大学） | 单轮"提交—评分—公布"覆盖不了真实赛制 |

**结论：主办方入驻最大的痛点不是"填表太麻烦"，而是"我们可能已经有这场比赛的一堆未经核验的信息，主办方却要从零再录一遍"。**

## 2. 核心想法一：让主办方"认领"已经发现的赛事

### 2.1 问题

现在两条线是断开的：

- 自动发现把比赛抓进来，标着"未人工核验"，主办方不知情、也管不了；
- 主办方入驻后要用模板**新建**一场赛事，等于把同一场比赛录第二遍。

结果是：**同一场比赛在网站上存在两份事实**——一份是抓来的（未核验、字段常缺），一份是主办方建的（权威、但和抓取结果互不相干）。这既浪费主办方的时间，也让选手看到两个入口。

### 2.2 想法：在入驻后提供"这可能是你的比赛"

主办方提交申请时或审核通过后，系统按**来源域名与机构名称**匹配已发现的卡片，给出一句具体的问法：

> 我们收录了这些比赛，可能是你们办的。要认领哪一场？

认领后：

- 该场**挂到该机构名下**，主办方获得这场赛事的运营权；
- 抓取到的事实（名称、来源链接、已提取的规则片段、分析结果）作为**预填草稿**带入，主办方逐项确认或改写；
- 公开页从此以**主办方确认的版本**为准，原抓取线索保留为历史与来源，不再作为并列的第二份事实展示。

### 2.3 认领必须证明身份，不能靠自称

任何人都能说"这是我办的"。认领要走身份核实，且核实方式要贴合真实主办方：

| 方式 | 适用 |
| --- | --- |
| 用**主办方官网域名**的邮箱接收验证信 | 有官网的机构（高校、企业） |
| 官网或官方公众号**有一段可核对的声明确认**，平台人工核对 | 多数国内赛事 |
| 提供**盖章授权文件或主办方联系人**，人工审核 | 学校院系、社区组织 |
| 平台已有的**官方来源**（如该赛事在 `ethglobal.com`、`lablaba.ai` 的官方页）与申请人身份互相印证 | 海外与平台型赛事 |

**未通过核实前，只能创建新赛事，不能改写已发现的公开卡片**——避免有人借认领篡改他人赛事信息。

### 2.4 认领失败也要有出路

如果匹配不到（很常见，新比赛还没被我们发现），就落到现有路径：**选模板新建**，并在新建后把官方规则页链接填上，让抓取与运营两边对齐。

## 3. 核心想法二：用"未知字段"引导填报，而不是让主办方从头填

这是当前数据给出的最大机会：**15 场里 12 场没有任何时间窗口证据**。

现在的主办方流程是"选模板 → 填一堆字段"。可以改成：

> 我们只确认了这些，剩下的请你补。

具体来说，认领后页面**直接列出我们不确定的项**，并按对选手的价值排序：

1. **报名截止时间**（最缺、也最影响选手决策）
2. 报名开始时间、开赛与结束时间、时区
3. 官方赛道与赛题方向
4. 必交材料与作品提交方式
5. 评审方式、轮次与结果公布时间
6. 费用、资格、AI 使用规则

每一项都显示**我们当前的依据**（例如"原文写'9月7日报名开启'，没写截止日"），主办方只需确认或改写。

**这样做的好处**：主办方感受到的不是"又一张表"，而是"你们已经帮我看过一遍了，我只要改错的地方"。这也直接提升公开页质量——把最常见的"截止时间未知"变成有权威答案。

### 3.1 一条不能破的边界

主办方确认的内容是**新的、权威的、有归属的事实**，不是把抓取结果"升级成已核验"。

- 抓取线索与主办方确认**分别留存**，公开页显示主办方版本并标注来源为主办方；
- 抓取的旧版本保留，便于事后核对"当初是谁说错了什么"；
- **不允许把模型分析结果直接当作主办方声明发布**（规划21 已有此意，此处再明确）。

## 4. 核心想法三：机构类型与赛制的模板要更贴近真实

### 4.1 机构类型

现有"学校/公司/社区"三分可以保留，但**核验材料**应按类型给出具体清单，避免主办方反复被打回：

| 类型 | 常见凭证 | 特别注意 |
| --- | --- | --- |
| 高校/院系 | 院系官网公告、学校邮箱、指导教师 | 常由学生社团代办，需说明授权关系 |
| 企业 | 企业域名邮箱、盖章文件 | 常有多场赛事、多个品牌线 |
| 社区/黑客松组织 | 历史活动页、社群公告、既有合作方 | 无营业执照，靠公开活动记录核查 |
| 平台型（ETHGlobal、lablab 等） | 平台官方页与账号 | 报名在其平台完成，我们只做信息与准备辅助 |

### 4.2 赛制模板

按真实数据补几类，仍坚持"有限参数、不用写 JSON"：

| 模板 | 对应真实例子 | 关键结构 |
| --- | --- | --- |
| 线上 48 小时 | Google Cloud AI Builder Cup | 报名 → 集中开发 → 提交 → 评分 |
| 初赛 + 决赛（含人气投票） | 天猫 AI 黑客松 | 报名 → 初赛材料评审 → 公布晋级 → 线下 48H → 路演 |
| 提案书 + 决赛（学术型） | 中原大学永續智慧創新黑客松、新竹政策黑客松 | 线上报名 → 提案计划书 → 决赛 |
| 企业校园赛 | 超聚变、重庆大学 AI 挑战赛 | 校园渠道报名 → 校内选拔 → 全国 |
| 海外平台赛 | ETHGlobal Lisbon、AMD（lablab） | 平台报名 → 线上提交 → 评审公布 |
| 社区聚会型 | ClawHunt 上海站、GOSIM | 轻量报名 → 现场活动 |

**多轮次**是重点：现有 O04 是"单轮评分—发布结果"，而真实赛制普遍有初赛、决赛、人气投票等多轮，各轮材料与评委可能不同。这属于需要单独评估的范围扩展。

## 5. 核心想法四：入驻页要先把"我们不做什么"讲清楚

真实赛事里，报名、收费、投稿常在第三方平台（ETHGlobal、lablab、hackertrip、学校系统）完成。主办方第一次来时最该知道边界，否则会带着错误预期入驻：

**我们做**：正式规则与报名表、报名审核、队伍名单、通知与问答、行程与现场服务、材料收件、人工评审与结果公布。

**我们不做**（现有规划已明确，建议在入驻页直说）：

- 不收款、不退款、不开票；
- 不发短信；
- 不接管选手的私人备赛空间与私人 AI 对话；
- 不自动决定录取、晋级或获奖；
- 不在第三方平台替主办方发消息。

**准确先说清边界，比事后解释更省事**，也避免主办方以为入驻就能自动招生。

## 6. 入驻流程（完善后）

```
看到说明与边界（/organizers）
   ↓
提交机构申请（类型 + 凭证 + 联系人）
   ↓
平台人工审核（通过/驳回/补充材料）
   ↓
[新增] 认领我们已发现的比赛  ← 匹配来源域名与机构名，逐个确认
   ↓            ↘ 没有匹配 → 选模板新建
用"未知字段"清单补全关键信息（报名截止优先）
   ↓
配置报名表 → 预览 → 正式发布
   ↓
拿到本站报名链接，自行发到微信/公众号/小红书
   ↓
集中处理报名与后续运营
```

## 7. 权限、隔离与诚实性（沿用并强调）

- 一个账号可跨机构、跨赛事担任不同身份；**任何单一身份都不放大为跨赛权限**（规划21 已定）；
- 认领是**显式授权关系**，不是"机构名相同就自动归属"；
- 未通过核验的认领不得改写公开卡片；
- 抓取线索与主办方确认事实分别留存，公开页必须能说清"这条是谁说的"；
- 主办方后台统计、导出、模型检索都带组织/赛事范围（沿用规划21 第5节）。

---

## 8. 明确不做（防止范围膨胀）

- 不做收费/退款/发票、短信账号与短信通知；
- 不做任意流程设计器，不为适配个别赛制引入可执行脚本或表达式配置；
- 不自动决定录取/晋级/获奖；
- 不与微信/公众号做自动同步或代发；
- 不读取选手的私人备赛内容、私人 AI 记忆或未提交草稿；
- **不把"认领成功"当作赛事质量的保证**——我们只确认归属，不替主办方背书。

## 9. 数据归属与新增事实

沿用规划21 的归属表；本方案新增两项事实，均由 **O01 organizer** 拥有，**不新建第二份赛事本体**：

| 实体 | 所有者 | 说明 |
| --- | --- | --- |
| `OrganizerClaimRequest` | O01 organizer | 一次"认领已发现赛事"的申请：目标 discovery ID、申请人、机构、所声明的关系、核实方式、状态、审核人、时间、revision |
| `HostedEvent.claimedDiscoveryId` | O01 organizer | HostedEvent 上的可空外键，指向被认领的自动发现卡片；**唯一**，同一 discovery 只能被一个 HostedEvent 认领 |

**关键约束**

- 认领**不复制**发现卡片的数据。预填值在认领确认时**写入 HostedEvent 草稿的对应字段**，之后按既有"草稿 → 预览 → 发布版本"流程走；发现的原始记录保持不可变。
- 发现卡片（`src/server/project-discovery.ts` 与 DSH 赛事分析）**继续由根与采集侧拥有**，本方案不改其所有权与不可变历史。
- 公开赛事页仍读 HostedEvent 的发布版本。认领后该场以主办方版本为公开依据；原发现卡片保留为"曾经抓到的线索"，可追溯但不作为并列的第二份事实。

## 10. 公共接口（NEEDS_INTERFACE）

新增/扩展的公共契约集中在 `src/shared/organizer-contracts.ts`，由根统一接入。模块不直接读另一模块的表。

```ts
// 认领候选：按来源域名与机构名匹配已发现卡片，只读
interface OrganizerClaimCandidatePort {
  list(sql: SqlExecutor, organizationId: string): Promise<readonly {
    discoveryId: string;            // 发现卡片 ID
    title: string;                  // 卡片标题（抓取所得，未核验）
    sourceUrl: string;              // 原文链接
    sourceHost: string;             // 来源域名，用于匹配
    analyzedAt: string | null;      // DSH 分析时间
    matchReason: "source_host" | "name_conflict" | "manual_pick"; // 为什么判为候选
  }[]>;
  // 认领确认前复核该卡片仍可认领（未被其他机构认领、状态仍 active）
  assertClaimable(sql: SqlExecutor, discoveryId: string): Promise<void>;
}

// 未知字段清单：数值来自发现卡片与 HostedEvent 现状，不新增完成状态
interface OrganizerEventReadinessPort {
  list(sql: SqlExecutor, eventId: string): Promise<readonly {
    field: "registrationClosesAt" | "registrationOpensAt" | "startsAt" | "endsAt" | "timezone"
         | "tracks" | "requiredMaterials" | "submissionMethod" | "judgingRounds" | "resultsAt"
         | "fee" | "eligibility" | "aiPolicy";
    state: "known_from_organizer" | "known_from_source" | "missing" | "conflicting";
    sourceEvidence: readonly string[]; // 抓取证据原文片段（可空）
    sourceUrl: string | null;          // 证据来源
    checkedAt: string | null;          // 我们最后一次核验时间
    priority: 1 | 2 | 3;               // 对选手决策的影响程度，报名截止为 1
  }[]>;
}
```

**硬性规则**

- 清单是**派生视图**，不落"完成百分比"、不落勾选表、不新建完成事实（沿用规划16/18 的既有约束）。
- `known_from_source` 与 `known_from_organizer` 在 UI 与数据上**必须可区分**；只有后者可作为"主办方已确认"对外标注。
- 主办方补的值写入 HostedEvent 草稿，发布后成为新版本；**不得把抓取值直接标成主办方确认**。

| 路由 | 使用者 | 主要动作 |

## 12. 状态、权限与业务规则

**认领状态**：`pending` → `approved` / `rejected` / `withdrawn`。仅平台当前 admin 可批准；机构负责人不能自审。

**核实方式**（`OrganizerClaimRequest.verification`，单选）

| 方式 | 判定材料 | 首版是否支持 |
| --- | --- | --- |
| `official_domain_mailbox` | 用该赛事**来源域名**的邮箱接收并回复验证信 | 支持（第二步） |
| `official_statement` | 官网/官方公众号可核对声明确认，人工核对 | 支持（第二步） |
| `authorized_document` | 盖章授权文件或主办方联系人，人工审核 | 支持（人工） |
| `platform_source_page` | 该赛事在官方平台页（如 ethglobal.com、lablab.ai）与申请人身份互相印证 | 支持（人工） |
| `other` | 需说明，人工判定 | 支持（人工） |

**规则**

- 认领候选**只作提示**，不作授权；候选匹配（来源域名相同、机构名相似）**不产生任何权限**。
- 未批准前，机构**不得**改写任何公开赛事内容；批准的认领才把该 discovery 挂到 HostedEvent。
- 同一 discovery **只能被认领一次**；已被认领时后续申请明确拒绝并说明现有归属。
- 认领失败不阻塞：仍可用模板新建赛事，新建后填官方规则页链接以对齐抓取。
- 撤回认领不删除已发布的赛事与历史；若该赛事的公开依据来自主办方版本，撤回后按现状继续展示并提示归属待确认，**不自动回退成抓取版本**。
- 机构停用/驳回后，认领与其赛事按规划21 的既有规则处理，不自动删除报名与评分。

**补全规则**

- 补全必须由本赛事工作人员（`event_manage`）执行；每次保存带 `expectedRevision`，冲突不覆盖。
- 报名截止等时间字段仍按既有规则带**时区**；同一赛事多阶段截止分别记录。
- 冲突情形（抓取值与主办方值不同）必须显式展示两侧依据，由人决定，**不自动取新值覆盖**。

## 13. 机构类型凭证与赛制模板

**机构类型凭证清单**（入驻表单按类型给出具体提示，减少反复驳回）

| 类型 | 常见凭证 | 特别注意 |
| --- | --- | --- |
| 高校/院系 | 院系官网公告、学校邮箱、指导教师 | 常由学生社团代办，需说明授权关系 |
| 企业 | 企业域名邮箱、盖章文件 | 常有多场赛事、多个品牌线 |
| 社区/黑客松组织 | 历史活动页、社群公告、既有合作方 | 无营业执照，靠公开活动记录核查 |
| 平台型 | 平台官方页与账号 | 报名在其平台完成，本站只做信息与准备辅助 |

## 15. AI 边界

沿用规划21 第7节：主办方客服与评审辅助与选手助手**分开身份、上下文、检索、缓存与队列**；评审绝不读取选手导航记忆、空间 AI 记忆、测评或未提交代码。

本方案补充：

- 认领候选匹配**不用模型自由发挥**：匹配依据是可核对的来源域名与名称，模型不得凭空判定"这就是你的比赛"。
- "未知字段"清单中的 `sourceEvidence` **只是抓取原文片段**，不是模型结论；不得把模型摘要当作主办方声明或核验结果。
- 主办方可用 AI 辅助**整理**自己要发布的规则文字（草稿），但**发布必须由工作人员确认**，AI 草稿不自动成为赛事规则。

## 16. 明确不做（防止范围膨胀）

- 不做收费/退款/发票、短信账号与短信通知；
- 不做任意流程设计器，不为适配个别赛制引入可执行脚本或表达式配置；
- 不自动决定录取/晋级/获奖；
- 不与微信/公众号做自动同步或代发；
- 不读取选手的私人备赛内容、私人 AI 记忆或未提交草稿；
- **不把"认领成功"当作赛事质量的保证**——我们只确认归属，不替主办方背书；
- 候选匹配不作为授权，未核验不得改写公开内容。

## 17. 分步与验收

**实施顺序**：同步宪法与入口 → 登记分项与会话 → P01 → P02 → P03 → 根组合（页面/路由/迁移/构建/重启）→ 真实试用。P04 单独排期。每步都要根做实际迁移、构建与重启，模块单独测试不等于上线。

**验收**

1. 主办方从入驻到发布**不需要编辑 JSON**，且能说清自己发布的内容与抓取线索的区别。
2. 认领候选出现但不产生权限；未批准的认领**不能改动任何公开卡片**。
3. 同一 discovery 只能被认领一次；重复认领被明确拒绝并说明现有归属。
4. 认领后公开页以主办方版本为准，旧抓取版本仍可追溯；撤回不自动回退成抓取版本。
5. 补全报名截止后，选手在该场看到有出处的权威时间，而不是空白；`known_from_source` 与 `known_from_organizer` 在界面上可区分。
6. 一个账号同时是 A 赛选手、B 赛评委、C 赛工作人员时，任一身分不产生跨赛读写。
7. 机构停用/驳回、撤权、过期会话、猜测 ID、导出与缓存均不越权。
8. 手机端能看到当前赛事、期限与下一步；主要按钮无需横向滚动。
9. 全程不依赖 AI：DSH 失败仍可入驻、认领、补全、发布。

## 18. 范围控制建议

P01、P02、P03 各自改动集中在主办方工作台与 `src/server/organizer-*`，适合并行；P04 因触及 O04 评审轮次模型，需单独评估后再排期。真实试用标准仍是"两家主办方不同配置、不改代码跑完真实赛事"，不由开发夹具冒充。
