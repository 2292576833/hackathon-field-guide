# 团队空间改造为「操作空间」· 诊断与方案

> **状态：设计讨论记录。实施请以 [27-团队空间操作空间与主页主路径](27-团队空间操作空间与主页主路径.md) 为准。**
> 本文保留诊断过程与我的判断纠错记录；其中"拖动可降级""只串重要节点"等结论已在 27 号文档与宪法 v1.16.0 中定案。

> 日期：2026-10-12 · 依据：真实库统计 + `buildMissionWorkbench` / `buildSpaceGuideTree` 实跑 + 组件源码
> 目标（用户原话）：**把团队空间做成操作空间，让人看得懂，也能高效地配合完成。**

## 1. 先纠正我自己两个判断错误

**错误一**：我上一轮以萌新视角走查后说"不会迷路，只是有几处文案重复"。**不准确**——第 6 节 D/E 两条确实是实测确认的问题，但更关键的疑点当时没看到。

**错误二（更严重）**：本方案初稿根据"122 条任务全部 `todo`、无一 `in_progress`、59/59 停在 `draft`"推断"**没人开始做，配合卡在计划之后**"。**这个推断不成立，我撤回。**

随后核对项目名发现，库里**绝大多数项目是我自己的验收脚本生成的**：

```
[draft] 邀请验收项目 1791493837331     ← 脚本（带时间戳）
[draft] 浏览器验收项目 1791493834427   ← 脚本（带时间戳）
[draft] 破壁者战队 / 胡方耀 / hjjjj     ← 疑似真人，仅 3 个
```

所以 `59/59 draft`、`122 todo`、`0 检查人`**主要反映我的验收脚本只跑了一半流程**，不能用来推断真人行为。

**副产品（有价值）**：这说明我的浏览器验收**只走到"生成计划并分配任务"就停了**，没走"开始任务 → 交成果 → 检查通过 → 阶段推进"。**验收脚本本身要补完整。**

## 2. 修正后能站得住的结论

1. **"开始做任务"这条路是通的**：`team-task-board.tsx` L306 对 `todo` 且 `canUpdate`（管理员或负责人）的任务会渲染主操作按钮，走 `begin("in_progress")`。**不是缺按钮。**
2. **但没有任何证据表明真人团队完整走通过**：既无真实团队数据，验收脚本也只走了一半。所以"高效配合完成"**从未被端到端验证过**——这是当前最大的未知，不是已知缺陷。
3. **计划生成之后的每一环都未被验证**：交成果、等待检查、检查通过、阶段推进、复盘——而这些正是"操作空间"的核心。

> **因此第 1 期最重要的工作不是改界面，而是先补一条端到端用例，把真相跑出来。改之前先知道哪里真的断。**

## 4. 待验证的可疑点（**尚未证实**，第 1 期负责证实或排除）

### 可疑点 A：任务池只对草案开放，"领取"这条路可能是断的

已核实的代码事实：

- `planning/service.ts` L328：`getTaskPool` 只找 `["draft","ready","needs_changes","stale"]` 状态的计划；
- 真实库 26 个计划**全部已生效、草案 0**；
- 任务板 L183 文案承诺"先看成果与工时，再**领取**适合自己的任务"。

**推论（待验证）**：计划生效后任务池恒为空 → 界面主推的"领取"走不到；而真正能开始的是任务卡上的"开始"按钮（L306，`canUpdate` 即可）。**若真如此，界面主推路径与实际可用路径不一致**，新人会先在"领取"上撞空。

**验证方法**：单人团队从"计划生效"走到任务 `in_progress`，**只用界面承诺的入口**。

### 可疑点 B：检查条件是模板话术，等于没说

真实数据 122 条任务的检查条件全是 `["实际完成并留下依据"]`。新人无法判断做到什么程度算完成，**既不敢开始，也不知道何时算做完**。这条与数据是否来自脚本无关，是"高效配合"的直接障碍。

### 可疑点 C：项目阶段可能从不推进

59/59 停在 `draft`（虽主要是脚本数据，但**没有任何机制被证实会推进阶段**）。若确实不推进：

- 标题里的阶段标签、指引树的"当前阶段"**永远显示第一阶段**；
- 指引树永远停在 `enter`；
- 实测中 `needs_review` / `empty` 反复出现，新人看到"我们还在第 1 阶段"而实际已在做事，会怀疑自己操作错。

**验证方法**：走完一次真实协作，看 `stage` 是否变化。

## 5. 已实测确认的缺陷

### 缺陷 D：入口重复，且不告诉人"做完了什么"

实测（`buildMissionWorkbench` 真实输入）：

- 主卡片与"可并行准备"第一条**逐字重复**（每个场景都是 1/共 N 项）；
- 主卡片点进去是同一个锚点 `#project-goal`；
- 没有任何地方回答"**哪些已经完成了**"——只有"下一步"和"待准备"。

操作空间需要"已完成 / 正在做 / 卡住 / 下一步"四态，现在只有后两者。

### 缺陷 E：术语不统一

同一屏出现"管理员保存后继续""空间管理员""与管理员核对"。加上主办方入驻后又有"平台管理员"。新人不知道该找谁。

## 6. 改造方向：从"说明书"变成"操作台"

### 设计原则（建议写进宪法）

1. **一屏一动作**：首屏只推**一个**当前动作；其余收进"还可以做"，且不与主卡片重复。
2. **每个动作可执行、可交付、可判定**：每张卡回答四问——做什么、交出什么、怎样算好、卡住找谁。答不上来就不该作为主推荐。
3. **四态可见**：已完成 / 正在做 / 卡住 / 下一步，同屏可辨，不用点进子页面才知道进度。
4. **状态说人话**：不把内部状态（"尚未读取""需要复核""输入版本变化"）直接抛给新人，翻译成"我们还需要你确认 X"。
5. **单人可用**：一个人也能从计划 → 开始 → 交付 → 复盘走完，不依赖对单人无意义的"管理员二次确认"。
6. **完成由记录点亮**：不新增勾选/百分比，只认真实检查记录（沿用现有宪法约束）。

### 目标体验（一句话）

> 打开团队空间，**第一眼就知道现在该我做什么**；做完能当场记下、队友立刻看见；卡住了能一键说清卡在哪。

## 7. 分期方案

### 第 1 期：先验证，再动手（最高优先）

| 工作 | 说明 |
| --- | --- |
| **补完整端到端验收** | 单人 + 双人各一条：建空间 → 填目标 → 生成计划 → 生效 → **开始任务** → 交成果 → 检查通过 → 阶段变化 → 复盘。**只用界面承诺的入口走。** |
| **证实/排除可疑点 A** | 若"领取"在生效计划后确实恒空，修到主推路径与实际可用路径一致。 |
| **证实/排除可疑点 C** | 记录 `stage` 是否随真实记录变化；不变化则定阶段推进规则。 |
| **缺陷 D 修复** | 首屏去掉与主卡片重复的项；主卡片只推一个动作。 |
| 缺陷 E 修复 | 统一为"空间管理员 / 平台管理员"，并说明各自负责什么。 |

> 第 1 期**必须先出验证结论**，再决定第 2 期做什么。避免像本方案初稿那样凭数据假设动手。

### 第 2 期：让"配合"看得见

| 工作 | 说明 |
| --- | --- |
| 四态总览 | 一屏看清：我做完的、我在做的、卡住的、下一步。 |
| 队友在做什么 | 从折叠列表提到一屏可见（谁在做哪项、在等谁）。 |
| 交接链路可见 | 交成果 → 等谁检查 → 检查通过，同屏可追。 |
| 卡点一键说清 | "有问题"要能一句话说清缺什么、需要谁提供什么。 |
| 检查条件可变具体 | 计划生效后允许负责人细化检查条件（留审计），不再只有模板话术。 |

### 第 3 期：让空间跟着工作走

| 工作 | 说明 |
| --- | --- |
| 阶段由真实记录驱动 | 目标+计划+任务进行 → `active`；有提交记录 → `finalizing`… |
| 指引树跟随 | 当前阶段与工作台一致，不再永远指第一阶段。 |
| 术语统一收口 | 全站统一称谓与责任边界。 |

## 8. 验收口径（可衡量）

1. **端到端用例通过**：单人、双人各一条，从建空间到复盘，`stage` 真实变化。
2. **主推路径可用**：界面承诺的"领取/开始"入口在计划生效后都能走通。
3. **零重复**：首屏主卡片与"还可以做"清单零重复。
4. **四问可答**：抽查任意主推荐，四问都答得上。
5. **不新增完成状态**：仍然只认真实检查记录（宪法约束）。
