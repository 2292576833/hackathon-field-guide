## 1. 目标

新人第一次参赛时，**时间应该花在完成作品上**，不该花在找入口、重复填写和等人回复上。本规划要做的是：

- 让用户**在看得见任务的地方就能动手**（现在是"看在这里、做在那里"）；
- 让协作里的**等待与余力可见**（在等谁、谁在等我、谁还有空）；
- 把配色收敛到**单一令牌来源**，使换肤不牵动任何功能与数据。

## 3. 设计定案（已写入宪法 v1.20.0）

1. **在看得见任务的地方就能动手**：只呈现"该做什么"却要求跳页才能做，属于未完成。
2. **新增工具必须复用既有写入路径、权限判定与并发处理**；出现第二套写逻辑比缺工具更糟。
3. **先核对既有能力**，已实现的不得当新功能重复建设。
4. **等待与余力由既有记录派生**，不新增完成状态或第二份事实来源。
5. **工具必须从当前位置可达**；仅在另一条路由里可达、或登录后才出现在菜单里的，不算已交付。
6. **提示与浮层不得遮挡**其位置上用户需要阅读的内容，也不得压住同区域其他入口。
7. **配色以令牌为单一来源**；皮肤只覆盖颜色变量，不改布局/结构/行为。
8. **配色必须满足对比度门槛**：正文与链接对底色 ≥4.5:1、按钮文字对按钮底色 ≥4.5:1、品牌色块 ≥3:1。
9. **红色只用于真阻塞**，品牌强调色不得与阻塞提示混用同一语义。

## 5. 验收口径

- **每个新工具都必须有真实浏览器验收**：能加入画布、能渲染真实数据、无未捕获异常。
- **派生类工具**：事实不足时不得回落到 0、百分比或"赛前"等占位；必须显式表示读不到。
- **就地操作类工具**：必须与既有界面写同一份事实，并有并发冲突测试。
- **配色**：每套方案必须有对比度实测数据，且皮肤只覆盖颜色变量（用构建产物核对）。
- 不得以"代码存在"当作"用户能看到"：入口必须有命中测试（可点中、不被遮挡、在视口内）。

## 8. 本次不做

### 8.1 违反宪法或会产生第二套事实（**禁止**）

| 不做 | 理由 |
| --- | --- |
| 任何"手动打钩 = 完成"的组件（含把私人待办接到任务状态、给队友状态加"我完成了"按钮） | 直接违反原则 X；`todos.ts:8-18` 的既有约束必须保留，私人待办的免责说明不得删除 |
| 完成百分比 / 进度条 / 成员排名 / 贡献度 | 宪法与 `teammates.ts:9` 明令禁止；`assignment` 也强调意愿不是能力排名 |
| 在线状态 / 最后活跃时间 / "谁在线" | 与"没有更新进度不等于没有工作"冲突（`team-assistant/generation.ts:10`、`teammates.ts:99`） |
| 工时计时器 / 工时榜 | 会产生第二套事实（`progressUpdates` 已是权威），且容易被当成考核 |
| 站内聊天 / 评论线程 | `TeamFeed.tsx:248` 已明确把自由沟通留给队伍现有沟通群 |
| 真正给队友发催办 / 推送 | 会变成第二套通知系统（新表、跨账号可见性、去重、静音、未读），与现有 `planning_notifications` 重叠。**替代方案**：只读的"我在等谁"清单 + 一句可复制的催办文案（纯本地，不落库） |
| 把站内检索扩到服务器任意文件 / 聊天记录 / 未授权空间正文 | 规划 18 与 AGENTS.md 明确禁止 |
| 再加一套"任务清单" | 已有 `space-todos` 与任务板；第三套说法违反"不建立第二套完成状态"的精神 |
| 实时推送 / WebSocket | 10–15 秒轮询对黑客松节奏足够；长连接带来断线重连、多实例与 PGlite 单写者等新问题，收益不成比例。**只给一个面板做实时也会造成"有的地方实时、有的地方延迟"的错觉** |

### 8.2 锦上添花，不要做

- 与「团队进度」重复的统计卡；
- 队友状态的筛选 / 排序 / 头像墙；
- 给"已确认职责"再加徽章（现有 `duties` 与 `ShareMarker` 已表达，且容易被读成完成状态）；
- 动态"上次看到这里"游标（唯一需要新表的一条，收益不抵成本）。

### 8.3 需要单独规划的

| 不做（本轮） | 理由 |
| --- | --- |
| 富文本实时协作文档 | 属于另一个产品，不是"小工具" |

### 8.4 若只能做三件（审查会话给出的优先级）

1. **团队动态进画布 + "只看与我有关 / 只看已采纳决定"** —— 修的是"决定根本找不到"，成本最小（把已有组件挪进已有容器）。
2. **交接助手** —— 每份成果交接都要用、新人门槛最高，而三个答案已经就在同一个组件里。
3. **容量对照卡** —— 数据已在客户端、零新表零迁移，直接回答"来不来得及"。

### 10.7.3 文档组件无法放大缩小（用户报，2026-10-13）

**现象**：文档组件滚轮缩放无效，其它组件正常。

**定位过程（前两次诊断都是我自己出错）**：
1. 第一次逐个组件测滚轮，结论"全部无效"——**诊断自身有缺陷**：我直接在卡片上按下拖动，
   而那是"拖动组件"手势，**根本没选中**，所以 `selected=false`，测的当然全是无效。
2. 第二次换成框选，`documents` 仍不在选中列表里——**坐标在视口外**（文档卡在文档坐标 y≈3280，
   我没滚动就按屏幕坐标比划），又是一次无效诊断。
3. 第三次先 `scrollIntoViewIfNeeded` 再框选，得到决定性数据：

```
放大 1→4 次: scale 1 → 1.21551  ✓
缩小 1→4 次: scale 回 1         ✓
在正文中间滚轮后: scale 1（没反应）✗   ← 只有这里不行
正文中心命中: { tag: "textarea", isEditor: true }
```

**根因**：空间文档卡片**默认就是编辑态**，正文是 `textarea` 且**占满整张卡**
（`.editor` 设了 `max-height:none`、正文内部不滚动）。而 `canvas-gestures.ts` 的规则把
`editor` 区域**一律**排除在滚轮缩放之外（`if (["editor",...].includes(region)) return false;`），
于是**鼠标只要落在文档正文上，滚轮就完全没反应**——那张卡几乎无处可缩。

**修复**（保留原设计意图：不能让缩放抢走长编辑框的原生滚动）：
- `canUseCanvasGesture` 新增第 4 个参数 `scrollableContent`，**默认 `true`（保守拒绝缩放）**；
  只有调用方明确测出"内部没有可滚动内容"时才允许缩放编辑区。
- 画布侧新增 `hasScrollableContent()`：检查事件目标及其后代是否还有内容可滚（前后各 40 个节点内）。
- **默认值我第一版写成了 `false`**，导致"有可滚动内容时仍以原生滚动优先"这条既有断言从 `false` 变成 `true`，
  被既有测试直接抓住——已改回 `true`。

**验证**：
- `canvas-gestures.test.ts` **16/16**（新增"无可滚动内容的编辑框应允许缩放卡片"）
- 新增 `tests/e2e/space-documents-zoom.spec.ts`，浏览器实测：
  `正文中心命中 textarea` → `正文中央滚轮 scale 1 → 1.05`、`反向滚轮 1.05 → 1`
- 全量模块测试 **2706 / 2706**；浏览器验收 **9 / 9**

**教训**：我在这一项上**连续两次给出无效诊断**（没选中、坐标在视口外），差点因此得出"没有 bug"的结论。
诊断脚本自身必须先自证有效（例如断言"选中=true"、断言坐标在视口内），否则结论不可信。

### 10.7.2 右击栏"完全点不动、点一下还会隐藏"（用户报，2026-10-13）

用户提供截图：右击栏能弹出，但**每一项都点不动，点一下还会隐藏**。

**复现（这是关键，我第一次没复现出来）**：在默认 1440×900 视口下一切正常，所以首轮诊断给出"都能点"的假结论。
改用**接近用户截图的较矮窗口**才复现：

| 视口 | 菜单矩形 | 结果 |
| --- | --- | --- |
| 1280×720 | y=300, 高 558 → 底部 **858** | 「重置视图」「缩放回 100%」TimeoutError |
| 1000×600 | 同上 | 下半部分多项 TimeoutError |

**两个根因**：

1. **菜单没有视口边界约束**（主因）：菜单高约 558px，窗口不够高时**下半部分在视口之外，物理上点不到**。
   截图里点不动的正是「画布视图」那一块。
2. **我那个"打开后 200ms 内不收起"的保护是错的**：用户点菜单项时 `pointerdown` **先于** `click` 到达，
   超过 200ms 就被判为"点外面"，菜单先被关掉，随后的 `click` 永远不来 ——
   表现正是"**点一下没反应，而且菜单隐藏了**"。
   正确做法是**按事件目标判断**（点在菜单内部就不收起），而不是按时间。
   另外原来还监听了 `scroll`（捕获阶段），菜单自身滚动也会把自己关掉，一并去掉。

**修复**：
- 收起判断改为"事件目标在菜单内 → 不收起"，只保留 150ms 的"跳过打开菜单那一次右击"。
- 移除 capture 阶段的 `scroll` 监听。
- 菜单增加**视口边界约束**：空间不足时向上翻转，并限制最大高度；高度用 `useLayoutEffect` 测量并写入 state
  （第一版写进 `useRef`，**不触发重排**，所以第一帧仍然是超出的位置——这个坑也记下来）。
- 菜单宽 236 时右边界按 252 预留。

**验证**：三个视口（900×760、1280×720、1000×600）实测，菜单矩形统一为 `y=12`、底部 `570`，
**在视口内**，7 项（画笔/荧光笔/箭头/文字便签/橡皮/重置视图/缩放回 100%）**全部 ok**。
新增回归用例 `tests/e2e/canvas-annotation.spec.ts` 的「右击栏在小窗口里也完整可见、每一项都点得动」
（1000×600 下断言菜单底部 ≤ 视口高，并逐个点击 7 项）。

**我在这件事上的教训**：
- **我第一轮诊断用默认大视口就下了"都能点"的结论，等于没有复现用户的问题。**
  用户截图明显是窄/矮窗口，我应该先按他的窗口尺寸复现。
- 把"时间"当作点击归属的判据是错的；应该用**事件目标**。

### 10.7.1 点击空白处收起 + 「取消批注」语义修正（用户 2026-10-13 追加）

用户追加三条要求，其中两条我第一次都理解错了，已修正：

**① 点击空白处侧栏隐藏（保持要求）**
- **右击栏**：`pointerdown`（捕获阶段）、`Esc`、`resize`、`scroll` 任一都收起。
  加了一个必要保护：右击本身会先派发 `pointerdown(button=2)`，若不处理，菜单会在打开的**同一瞬间被自己关掉**，
  所以打开后 200ms 内的 `pointerdown` 不触发收起。
- **「组件」栏**：由原生 `<details>` 改为受控 `open`。

**② 「取消批注」= 取消当前选中的工具，不是删除笔迹（我第一版做错了）**
第一版我把"取消批注"实现成"清掉本次批注并退出"，用户明确纠正：
**取消批注只是取消选中的工具，笔迹要保留**。现已改为：
- **取消批注（取消选中的工具）** —— 只退出绘制状态、回到正常画布操作，**保留已画好的笔迹**；
- **清空笔迹 / 删除全部笔迹** —— 这才是删内容。

**③ 一个严重 bug：组件栏一打开就自己关掉（用户报"选择不了工具"）**
- **现象**：点「组件」打不开或立刻收起，导致工具根本点不到。
- **根因**：我给 `<details>` 挂了 `onToggle`。React 把 `open` 设为 `true` 时浏览器**也会派发一次 `toggle`**，
  而那一刻 `currentTarget.open` 读到的仍是旧值 `false`，于是处理器立刻把状态设回 `false`——**打开即关闭**。
- **修复**：删掉 `onToggle`，`open` 完全由 React 控制；摘要点击 `preventDefault()` 后手动切换。
- **第二个原因**：关闭组件栏的监听没有过滤鼠标键。右击会先派发 `pointerdown(button=2)`，
  于是"右击画布 → 打开批注工具"这一步就把组件栏关掉了。已限定**只有左键**才关闭组件栏。
- **实测证据**：`打开后 details.open = true`、`组件项数量 = 9`、`点第一项后 details.open = true`、
  `场景三 点项后 details.open = true 组件数 5 -> 6`（成功加上了组件）。

**验证**：`tests/e2e/canvas-annotation.spec.ts` **3 项**，浏览器实测：
- 右击栏：点菜单之外的空白 → 收起；`Esc` → 收起；组件栏：点空白 → 收起
- **画完笔迹 2 → 取消工具后笔迹仍为 2**（取消不删内容）；取消后组件能长按拖动（位移 172）
- **清空笔迹后 0**（清空才删内容）

**我在这一项上犯的错（都记下）**：
1. 把"取消批注"做成"清空批注"——**没有先问清语义就实现**，用户纠正后才改对。
2. 用 `onToggle` 与受控 `open` 同时管理一个 `<details>`，导致打开即关闭（上面③）。
3. 测试"点空白"的坐标落在了**菜单自身矩形内**（菜单从右击点向右下展开，宽 236、高约 500），
   看起来像"收起失效"，其实是点在菜单上。已改为先量出菜单矩形、再找矩形之外的画布点。
4. 用 PowerShell 的 `-Raw` + `Set-Content` 批量替换测试文件里的中文按钮名，**把文件编码弄坏**
   （中文变乱码、相邻行被合并）。已用编辑工具整体重写修复。**结论：不要在 PowerShell 里读写含中文的源码文件。**

### 10.11.1 第二轮优化：清晰度 / 节奏 / 连贯性（用户 2026-10-13 追加）

用户要求：**优化连贯性、提高分辨率、节奏再快点**（并强调"主要是提高清晰度"）。

**清晰度**
- 输出从 1920×1080 提到 **3840×2160 原生 4K**（文字与矢量按 4K 渲染，不是放大 1080p）。
- 页面截图重采为 **3840×2160（2 倍像素）**，放在 `video/public/shots4k/`。
  这里踩了两个坑，都记下来：
  1. 夹具自带的 `f.page()` 固定 `deviceScaleFactor=1`，**CDP 覆盖也无效**（实测 `dpr=1`）——
     必须自建 `browser.newContext({ deviceScaleFactor: 2 })` 并沿用自己的 cookie。
  2. 加了 `deviceScaleFactor` 仍得到 1920 宽：**Playwright 的 `screenshot()` 默认按 CSS 像素输出**，
     必须显式传 `scale: "device"`。

**节奏**
- 入场曲线 `REVEAL_FRAMES`：0.75 秒 → **0.42 秒**。
- 各幕内容提前上屏：第一幕标题 0.2 秒、碎片 1.8 秒起；主路径 1.2 秒起点亮、每 1.9 秒一段
  （原来 2 秒起、每 3.1 秒）；其余各幕同步收紧。
- 总时长 134.4 秒 → **118 秒**（3540 帧），场景留白从十几秒压到 2~4 秒；
  音乐仍在，最后 300 帧淡出，不留"画面已结束还在放歌"的空白。

**连贯性**
- 新增 `ui.SceneFrame`，在**合成层**统一给每一幕包上淡入 0.15 秒 / 淡出 0.25 秒，
  避免深色幕与纸色幕硬切"闪一下"（在合成层做而不是逐幕改文件，保证一致且不易漏）。
- 第一幕背景从深色统一到纸面底；第六幕保留深色作为刻意的"边界"章节，但过渡已平滑。
- 时间轴自检 `assertTimeline()` 继续生效，配平后总和精确等于 3540 帧。

`ffprobe` 实测），首版 1080p 保留为 `项目纪录视频.mp4` 备查。
