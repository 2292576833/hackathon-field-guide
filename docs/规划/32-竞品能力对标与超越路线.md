## 1. 目标（以我们的产品为准，不是把竞品功能搬进来）

用户 2026-10-15 明确：**目的是让我们的产品更好，不是把他们的功能无脑融入，并且要避免新功能与网站本来功能冲突。** 因此本规划的顺序是"我们的真实问题 → 竞品的参考做法 → 冲突审查 → 只做不冲突且真的更好的部分"，每一项候选都要过 [第 4.0 节](#40-吸收闸门与冲突审查先过这一关再谈做不做)的吸收闸门。

竞品拆解只用于两件事：① 看清我们**已经领先**的地方，不被"竞品很全"带偏判断；② 找到我们**真实存在**的摩擦点，借它们验证过的机制改善**既有流程**，而不是新增一套并行功能。

1. **缺口互补组队**——改善既有"招募帖 + 名片 + 申请"，不是新建第二个找队友入口。
2. **提交前核对**——补在既有"保存 / 运行验证 / 正式收件 / 正式提交"流程的**提交前一步**，不新建第二套提交或第二份完成状态。
3. **评审公正**——在既有评审轮次内加"校准派生视图 + 公开规则版本 + 相似待复核"，不改原始分、不改人工公布流程。
4. **赛后复用**——复用既有公布版本与 M07 复盘，只做只读派生清单，不新增产品面。

**判断标准**：做完这些之后，一个新人**在既有路径上少一次卡住**（找不到人、不知道还差什么材料、不服气评分、下一届重搭一遍），而不是"我们的功能列表更长了"。

## 4. 设计定案（已写入宪法 v1.21.0）

### 4.0 吸收闸门与冲突审查（**先过这一关，再谈做不做**）

用户 2026-10-15 明确：**目的是让我们的产品更好，不是把竞品功能无脑融入，并且要避免新功能与网站本来功能冲突。** 因此每一项候选能力 MUST 先回答三个问题并记录结论；答不出或冲突无法避免 → **不做，或只改既有流程内的呈现**。

| 候选 | ① 解决我们的哪个真实问题（摩擦点） | ② 会碰到的既有能力 | ③ 冲突风险与处理决定 |
| --- | --- | --- | --- |
| 缺口互补组队 | 招募帖只能按角色/关键词浏览；发帖的人多、**"我们还缺什么、该找谁"没人替他算**，靠翻列表和群聊 | `recruiting` 名片/帖/申请、`projects` 成员与职责、`skills`、`space-workflow` 队友状态、`journey` 路线图 | **风险**：容易变成第二个"找队友"入口，与 `/recruiting` 大堂、空间成员面板重复。<br>**决定**：不新建入口，只在**既有招募帖页面内**加"缺口 + 可补缺口的人（含依据）"；空间成员面板只加"缺口覆盖"一行，不做第二个列表。 |
| 提交前核对 | 现在"保存 / 运行验证 / 正式收件 / 正式提交"是四个不同事实，新人**常不知道还差什么**，到了截止才发现演示打不开 | `github` 交付与运行验证、`event-judging` 正式收件与材料快照、`space-workflow` 待办、`scope-cut`/`ppt` 材料 | **风险**：容易造出第二套"完成状态/清单"，与待办、交付验证、收件回执冲突。<br>**决定**：只做**派生视图**（不新增状态列），挂在既有提交入口之前；可达性探测只提示不阻断、不写状态。 |
| 评审公正三件套 | 严评委/松评委的差异没人处理；**公平规则只在我们脑子里**（无公开规则表）；相似材料没有任何提示 | `event-judging` 轮次/快照/汇总/公布/审计、`organizer` 权限与发布版本、CSV 导出 | **风险**：校准若替换原始分或自动影响名次 → 与"人工确认公布"原则直接冲突；规则包若自动扣分 → 与"不得无依据判定"冲突；相似检测若自动定性 → 与"不认定抄袭"冲突。<br>**决定**：三件全部只做**派生与待复核**：原始分永久保留、规则公开且开赛前锁定、扣分与失格人工确认、相似只到 `needs_review`。任何一项做不到这个边界就**不做**。 |
| 赛后复用 | 比赛结束后**成果沉在空间里**，下一届要重新搭一遍（评审基准、时间表、表单字段、通知模板） | `event-judging` 公布版本、`event-registration` 表单版本、`event-communication`/`selection-notices` 模板、`retrospectives` 复盘、`projects` 归档 | **风险**：容易变成"赛后报表+影响力评分"新模块，与 M07 复盘和归档只读规则冲突。<br>**决定**：**不新增产品面**，只做只读"下一届可复用清单"（每项指回既有记录），生成由主办方手动触发；队伍转项目/复盘复用 M07 既有写路径。 |

**已按闸门判定"不做"的候选**（理由见上表②③与第 9 节）：选手互评、团队编成状态机与拖拽、多时区自动开赛、评委音频评语、场馆导航/现场日程/现场聊天、对外写入型 API、任何形式的"匹配分/适配度/排名"。

### 4.1 缺口互补组队（P1）

- **缺口怎么算**：从当前空间**已有事实**派生——招募帖声明的 `neededRoles`、成员已声明职责（M04/M05 事实）、项目要求（M03 已确认规则与赛道）。缺口 MUST 是"哪几项已声明职责/技能没有被任何活跃成员覆盖"，MUST NOT 由模型自由发挥。
- **谁能补**：候选来源限定为**已发布公开名片**的活跃账号 + 本人自愿加入的招募帖申请者。匹配结果只回答两件事：**覆盖了哪一项缺口**、**依据是哪条记录**。
- **依据分两类**：`平台记录已核验`（已确认参与的赛事、已收件的交付、已发布的复盘、已完成的检查）与 `本人自述未核验`（自填技能、作品链接）。两类 MUST 分开展示，MUST NOT 合成分数。
- **排序**：MUST NOT 出百分比、适配分或"最佳人选"。同一缺口内多人覆盖时按**中性稳定顺序**（如最近活跃时间）展示，并在界面上说明这不是能力评价。
- **推荐理由**：每条 MUST 是"缺 X → 此人声明/记录里有 X → 依据：<记录类型 + 时间>"，不允许只有标签没有依据。
- **复用**：只读既有 `recruiting`（名片/帖/申请）、`projects`（成员）、`skills`、`github`/`retrospectives`（可核验战绩）。**不新建第二份成员、职责或战绩事实**。

### 4.2 赛前自检与提交前核对（P2）

- **自检报告**（对应 HackerMate `ppt` 复查与 HackBuddy practice-judge）：按**本赛道已锁定规则**逐项检查我们自己的材料，输出"项 → 依据（文件/链接/记录）→ 缺口 → 下一步"。MUST 明确标注"**非正式、不进入正式评分**"，MUST NOT 给出分数、名次或"能否获奖"的判断。
- **提交前核对清单**：材料齐备、演示链接可达（真实探测，失败给原因）、仓库绑定与提交版本、必要确认项。可达性探测 MUST 是只读的网络检查，失败只提示不阻断。
- **复用**：既有 DSH 结构化调用、预算与未知结果 hold、M06 交付记录、正式收件材料快照。未知结果 MUST NOT 自动重发。

### 4.3 评审公正三件套（P3）

1. **评委严格度校准（派生视图）**：对每位评委在**本轮**的已完成评分计算均值与标准差；当**样本量达到门槛**（建议 ≥5 张已完成评分且 ≥3 个作品）时给出校准分，与原始分**并列展示**；样本不足只提示"暂不校准"。打分无区分度（分数压缩）或明显偏离的评委 MUST 提示主办方。
2. **公开量化的公平规则包**：超时提交、材料不全、完全未提交、赛前开发（依据仓库活动时间线）、截止后仓库变更、重复/相似提交、主题偏离等项，每项有**公开定义 + 默认分值/等级 + 版本**，开赛前锁定；系统只产出**待复核建议**（带时间戳与记录依据），扣分与失格由授权人员确认，保留审计与当事人可见的依据说明。
3. **相似/重复提交待复核**：可解释规则（标题相似度、同一仓库地址、材料哈希相同），只生成 `needs_review`，MUST NOT 自动判定抄袭。

- **复用**：`event-judging` 的轮次/快照/指派/汇总/公布/审计；`github` 的提交记录；`organizer` 的权限与公开规则版本。
- **红线**：校准不得单独决定晋级或获奖；正式结果仍人工确认公布。

### 4.4 赛后闭环（P4）

- 公布结果后，从**既有事实**派生：参赛与完成情况、材料齐全度、接受/退出、评审参与与耗时、相似提示处理结果；对主办方给"下一届可复用清单"（评审基准版本、时间表、奖项与赞助结构、报名表单字段、通知模板）。
- 队伍与成果物可**一键转为项目与复盘条目**（复用 M07），MUST NOT 新建完成状态或"影响力评分"。

## 5. 分期执行

排序原则是"**先做不新增写路径、不新增状态、能直接减少新人卡住的**"，风险越高、越接近结果与申诉的越往后。

| 期 | 内容 | 落在既有功能哪里（不新建入口） | 风险 | 前置 |
| --- | --- | --- | --- | --- |
| 第 1 期 | 缺口互补组队（只读派生 + 逐条依据） | 招募帖页面内；空间成员面板加"缺口覆盖"一行 | 低 | 决策点 1 |
| 第 2 期 | 提交前核对清单 + 演示可达性探测 | 既有提交入口之前，只读派生 | 低 | 无 |
| 第 3 期 | 相似/重复提交待复核 | 复用评审既有 `needs_review` | 中 | 决策点 2 |
| 第 4 期 | 校准派生视图 + 公开公平规则版本 + 扣分建议流 | 既有评审轮次页与公布页 | 高 | 决策点 3、4 |
| 第 5 期 | 赛前自检报告（AI，明确非正式） | 复用既有材料与 DSH 护航 | 中 | 第 2 期完成 |
| 第 6 期 | 赛后只读"下一届可复用清单" | 既有公布版本、表单版本、通知模板、复盘 | 低 | 第 4 期完成 |
| **不做** | 选手互评、团队编成状态机与拖拽、多时区自动开赛、评委音频评语、场馆导航、对外写入型 API | — | — | 第 4.0 节闸门判定：冲突或对新人价值不足 |

## 6. 验收口径

每个分期 MUST 区分：模块测试、根接入、隔离浏览器走查、真实外部验收。此外新增**对标验收**（证明"超过"而不是"做过"）：

1. **可核验性对比**：同一份匹配推荐/自检报告/扣分建议，界面上能回答"依据哪条记录、哪个版本、什么时间"；竞品对应功能给不出（HackerMate 算法不可观测、CraftStadium 判定靠人工）。
2. **不夸大对比**：全站搜索"百分比/适配度/最佳/排名"类文案，MUST 不出现能力或匹配百分比；对照竞品的 `Strong fit`、ROI 看板等表述给出我们的替代表达。
3. **公平规则可复算**：给一条超时提交记录与一条截止后仓库变更记录，规则包 MUST 产出可复核的建议，且 MUST 未经人工确认不生效。
4. **校准不改变原始事实**：提供同一轮数据，校准前后原始分 MUST 完全一致；样本不足时 MUST 不校准。
5. **反作弊不越界**：相似提示 MUST 停在 `needs_review`，MUST NOT 出现"抄袭/作弊"结论性文案。
6. **赛后闭环不新建事实**：复用清单里的每一项 MUST 能指回既有记录（公布版本、报名、复盘、通知模板）。
7. **闸门可复核（本轮新增的必查项）**：每期交付说明 MUST 写明第 4.0 节三个问题的答案，并给出"没有新增第二套入口 / 第二份状态 / 第二套写路径"的证据（例如：路由与入口清单对照、相关表的列变更说明、复用既有写路径的调用点）。任何一项只能靠"新加一个页面"实现时，视为**未通过闸门**，退回改造既有流程。

## 7. 风险与前置

- **样本量风险**：真实赛事评委少、作品少，校准容易失效；因此门槛与"暂不校准"提示 MUST 先落地。
- **申诉与解释风险**：扣分/失格直接影响结果，MUST 有依据说明与人工确认，且必须能回答"谁在什么时间依据什么改的"。
- **隐私风险**：缺口匹配只使用**已发布**名片与本人申请；MUST NOT 读取未发布档案、私人测评、私人 AI 记忆（延续既有权限边界）。
- **AI 成本与可靠性**：赛前自检走既有 DSH 预算与 hold 机制；未知结果不重发。
- **文案风险**：竞品对比内容进对外页面时 MUST 只引用已取得证据，MUST NOT 贬损或臆测竞品。

### 11.9 评委严格度校准（派生视图）—— 已实施并验证（2026-10-15）

用户 2026-10-15 明确要求"不是参考、而是利用源码对我们项目做深度优化"，因此直接改了代码，而不是只留计划。

**吸收闸门（第 4.0 节）三问的答案**

1. **解决我们的哪个真实问题**：评委之间的平均分与打分幅度不同，队伍会因为"遇到严评委"吃亏；本轮之前我们只有等权平均，主办方看不到也不需要看清这件事。
2. **会碰到哪些既有能力**：`event-judging` 的轮次/指派/汇总/锁定/公布/审计，以及 `ResultSummary` 的哈希与历史公布依据。
3. **如何避免冲突与第二套事实**：**不新增任何状态、表、写路径或入口**。校准是纯派生读：`ResultSummary`（正式分与名次）保持原样，校准分单独返回，因此 `lockedSummary` 与公布哈希不受影响；界面挂在既有"人工汇总与公布"下方的折叠面板里，不新增导航。顺带把 `summaryIn()` 里"按当前核查结论修正指派"的逻辑抽成唯一的 `checkedIn()`，避免校准再抄一份读逻辑。

**做法（对照竞品源码）**：按竞品 `server.ts` L294–382 的 $Z=(S-\mu_j)/\max(\sigma_j,\text{floor})$ 与全局分布映射实现，但**修掉它三个实测缺陷**：只用派生不替换原始分；每位参评评委都必须达到最小样本（5 份）否则整轮不校准（竞品 $N_j{=}1$ 时会把该评委压成全局平均）；无差异时返回 `no_variance` 不校准。另加"打分无区分度"提示与"未进入汇总的评分原因"清单（后者借鉴 Synnovator 的"先校验后聚合"）。

### 11.10 相似 / 重复材料待复核（人工线索，不是判定）—— 已实施并验证（2026-10-15）

**依据**：竞品文档写了"用编辑距离查重复"，但源码里**根本没有实现**（JUDGELAYER 全仓无该实现），而且这类功能极易被做成不透明的"相似度分数"。我们做一版能解释、能核对、也不下结论的。

**做法**：新增 `src/modules/event-judging/duplicates.ts`（纯逻辑）＋ 只读 `service.duplicates()` ＋ `GET organizer/events/:eventId/judging/duplicates` ＋ 主办方评审管理页折叠面板：
- 只比较**不同队伍各自最新一版**正式材料（同队连续版本是版本关系，不比较）；
- 只用**可核对的事实**：同一文件哈希（高）、同一材料地址（中，忽略查询串/片段/结尾斜杠）、同名作品（低，名称归一去掉空白与分隔符号）；
- 每条线索给出**具体依据文本**与强度标签，并明确写"这是人工复核线索，不是判定"，附四条限制（含"同一套模板/同一场工作坊脚手架也会造成相同地址或同名"）；
- **不做评分、不给百分比、不产出公开分级、不自动通知任何队伍**；线索超过 50 条时明确告知已截断。

**验证**：`duplicates.test.ts` 7/7（同队版本不计、哈希为最强线索并同时列出地址与同名、同名单独只算低强度、地址归一、名称归一、无共同事实零线索、截断告知）；根路由验收追加断言：工作人员 200 且单支队伍时**不得凭空造出线索**、评委 403、选手 403、匿名 401、读取后收件数仍为 1；模块全量 85/85；`npm run typecheck` 通过。

### 11.11 公开公平规则包 ＋ 赛前自检与赛后只读复用清单 —— 已实施并验证（2026-10-15）

**依据**：CraftStadium 的公开扣分页（逐字核对：`Base = Judge×0.75 + Peer×0.25`，迟交按 `<5→0% / 5–10→5% / 11–20→10% / 21–30→20% / ≥31 取消资格`）与 HackerTrip 的提交前自检。我们吸收前者"**事先公开、可预期**"，拒绝它的两处：**不做选手互评**、**不自动扣分**。

**① 公开公平规则包**（`src/modules/event-judging/fairness.ts`，只读 `service.fairness()`，`GET organizer/events/:eventId/judging/rounds/:roundId/fairness`，评审管理页折叠面板）：

- 规则包文本可一键复制，**是否公开、放在哪里由主办方决定**（不新增公开字段、不建第二份规则事实）。
