## 1. A · 工作人员受限邀请

### 1.1 行为（"点进去就是负责人"的安全版）

1. 组织管理员在"工作人员与授权"里点"生成邀请链接"，选**能力**（既有 7 类之一或多类）、**范围**（本组织全部比赛 / 指定一场）、**角色**（staff / organization_admin）、**有效期**（默认 7 天，上限 30 天）。
2. 系统返回一次性的链接与二维码；**只显示一次**，之后只能看到状态（未被领取 / 已过期 / 已撤销 / 已被谁领取）。
3. 对方点开 → 未登录先登录 → **领取页明确展示**：哪家机构、哪场比赛、将获得哪些能力、角色、有效期。
4. 明确点"接受邀请"后：写**既有 `StaffGrant`**（沿用组织 revision 并发校验、最后一名机构管理员保护、审计），邀请置为已领取并记录领取人。
5. 立即跳转到该模块的 section 页。

### 1.2 硬性规则（不可协商）

| 规则 | 原因 |
| --- | --- |
| 链接**单次**使用、有**有效期**、可撤销 | 转发不等于永久权限 |
| 领取必须**已登录且邮箱已验证** | 宪法 XI 授权按组织/赛事/模块/指派；不能是匿名自助升级 |
| 邀请可**绑定指定邮箱**（推荐默认绑定） | 防止链接被转给第三方 |
| `organization_admin` 邀请只能由**当前机构管理员**生成，且不得绕过"最后一名管理员不可撤销" | 既有规则不放松 |
| 领取**不新增第二套权限事实**，只写 `StaffGrant` | 宪法 XII 单一事实来源 |
| 过期/已领/已撤销/邮箱不符都**明确报错**，不静默 | 宪法 X 不把未知显示成成功 |
| 生成、领取、撤销**都写既有审计** | 可追溯 |

### 1.3 数据与接口（建议）

```
organizer_staff_invitations(
  id, organization_id, event_id NULL, role, capabilities[], note,
  token_hash, invitation_code, expires_at, max_uses=1,
  status open|claimed|revoked|expired, claimed_by_user_id NULL, claimed_at NULL,
  created_by_user_id, created_at, revoked_at NULL, bound_email NULL
)
```

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `organizer/organizations/:organizationId/staff-invitations` | 机构管理员 | 生成（返回 token 一次） |
| GET | `organizer/organizations/:organizationId/staff-invitations` | 机构管理员 | 列表与状态（不含 token） |
| POST | `organizer/staff-invitations/:invitationId/revoke` | 机构管理员 | 撤销 |
| GET | `/me/staff-invitations/:token` | 任意已登录 | 领取页只读预览（不泄露机构外内容） |
| POST | `/me/staff-invitations/:token/claim` | 任意已登录+邮箱已验证 | 领取并写 `StaffGrant` |

## 2. B · 每个主办方流程模块一个专属 DSH

### 2.1 助手注册表（"所有流程模块"逐项落地）

| 模块（既有 section） | 能力 | 只读读取的既有事实 | 只允许产出 |
| --- | --- | --- | --- |
| 本场概览 / 比赛设置 | `event_manage` | readiness、发布阻塞项、正式版本与变化回执 | 缺项清单、发布前核对摘要、变更说明**草稿** |
| 报名管理 | `registration_manage` | 报名计数与分页、报名表版本 | 待审优先建议（按时间/完整性，不评分）、审核说明草稿 |
| 队伍管理 | `teams_manage` | 正式名单、建议分组、名额 | 名额与资格**核对清单**、通知文案草稿 |
| 通知与答疑 | `communication_manage` | 公告、公开 FAQ、求助工单 | 公告草稿、FAQ 归纳、相似求助去重提示 |
| 行程管理 | `schedule_manage` | 行程草稿、已发布行程 | 冲突检测（同人时间重叠）、发布前核对摘要 |
| 现场服务 | `logistics_manage` | 住宿分配、餐券、破冰分组 | 未分配清单、按人合并的提醒草稿 |
| 收件与评审 | `judging_manage` | 收件回执、轮次冻结、指派、进度、校准/自检/公平包**只读** | 进度摘要、缺口清单、公布前核对、**公平规则备忘** |

### 2.2 运行与边界（宪法 XI 直接约束）

- **独立上下文与记忆**：每个助手使用**独立命名空间**（机构+赛事+模块+账号），与选手备赛 AI、全站聊天、团队助手**互不继承**记忆、检索范围、缓存与队列。
- **只读输入**：只读该模块**当前授权**的既有事实；评审助手只处理**当前授权的正式提交材料**，不继承任何私人记忆。
- **只出草稿**：输出为草稿/清单/摘要/去重提示，**用户必须显式复制或应用**；助手**不得**发布、发信、扣分、改结果、改权限、改报名状态。
- **可用性降级**：DSH 不可用或超预算时，**模块原流程照常可用**（宪法 IX）。
- **次数**：**不设平台强制的次数上限**（按用户裁定），用量由主办方自行决定；但每次调用 MUST 计入既有 AI 账本并**可核对**（谁、哪个模块、读了什么范围、花费），MUST NOT 静默限流或偷偷降级。若需要限额，只能是**主办方显式配置**的额度，平台不偷偷兜底。
- **可核对**：助手界面**列出它读了什么范围**（哪场比赛、哪些事实、读取时间），并标注 `provider:dsh` 与"建议不构成执行授权"。
- **审计**：记录谁、、哪个模块、读了什么范围、花费多少；只读可查。

### 2.3 分期（用户要"多个"，但一次全开有成本与隔离面）

**P-B1 框架 + 2 个**：先做"收件与评审"与"报名管理"（事实最结构化、价值最直观），把注册表、命名空间、预算、审计做扎实。
**P-B2 其余 5 个**：概览/设置、队伍、通知、行程、现场服务，逐个接上同一个框架（每接一个只需写上下文装配 + 指令，不重写运行时）。

## 3. C · 作品公开（可选）+ 点评（文字与数值互评都要）

### 3.1 三层开关（缺一不公开）

1. **赛事级**：主办方在"公开与社区"里开启`作品展示与点评`（默认 false）。
2. **队伍级**：队伍在正式交件时/之后，对本队每份材料**自己选择**公开范围：`不公开（默认）` / `仅本场参赛者` / `公开（含访客）`。主办方**不能**替队伍选。
3. **个人级**：参赛者对某件已公开作品**才能**留言/互评；未公开的作品在点评区完全不存在。

### 3.2 两种点评**分列**（宪法 XI 硬条件）

| | 文字留言 | 数值互评 |
| --- | --- | --- |
| 存储 | `ej_work_comments`（独立表） | `ej_peer_reviews`（独立表） |
| 形态 | 文字（长度上限**由主办方配置**）+ 可选"有帮助"标记 | 量纲（1–5 / 0–10 / 是-否等）与**互评维度**均由**主办方配置**，且 MUST 与评委维度**分开定义**，避免暗示等价 |
| 去自评 | 不适用 | **强制**：提交时回执成员快照内的人不能评本队作品 |
| 参与率门槛 | 不适用 | **强制**：参与率 < 门槛（建议 30%，主办方可调）时**只显示"样本不足"**，不显示汇总 |
| 与评委分关系 | 不参与任何计算 | **绝不并入** `aggregate()` / `projection()` / 名次 / 对外导出 |
| 展示位置 | 作品详情页独立区 | **独立页面/独立区**，标题写明"选手互评 · 不计入名次" |
| 评审隔离 | 评分期间评委侧**不返回**点评内容 | 同左（评分期评委侧不返回互评数据） |
| 治理 | 作者或主办方可隐藏；可举报；同账号同赛事限频 | 同左；不得成为人身评价或报复渠道 |

### 3.3 公开投影只含队伍选择公开的字段

作品展示只显示队伍**勾选公开**的字段（标题、简介、链接、文件按队伍逐项选择）；**永不包含**：联系人、邮箱、答卷、求助、住宿、队伍专属反馈、评委身份。沿用规划 33 §6.4 的对外口径。

### 3.4 验收（必须断言，不是目测）

- `aggregate()`、`results/preview`、`results-export`、公开结果投影在开启互评前后**逐字段不变**；
- 互评表的数据**不出现在**任何评委路由与对外导出里；
- 自评被拒（409/403，明确原因）；参与率不足只显示"样本不足"；
- 队伍未选择公开时，点评区**不存在**该作品（不是"空占位"）；
- 隐藏后的留言/互评不再返回。

## 4. D · 交友：名录 + 连接 + 私信

### 4.1 三层，逐层放大风险，因此逐层独立开关

**D1 本场参赛名录（只读，零新权限面）**
- 比赛页内新增"本场参赛名录"：只显示本人**已发布**的名片投影（含个人介绍、技能、城市）+ 本场**公开队伍**。
- 本人未发布/已撤回即不出现；沿用既有名片规则（不展示邮箱、年龄/MBTI 不用于筛选）。

**D2 连接（双向同意，不是单向关注）**
- 同一场比赛中，任一方可发起"想认识"请求；**对方接受后**才形成连接。
- 每人在单场赛事的未处理请求有上限（建议 20），拒绝后同一对不得重复骚扰（可设 30 天冷却）。
- 连接关系**只在本场赛事内有效**，不跨赛事、不跨机构。

**D3 私信（只在连接内）**
- 只有**已接受连接**的两人之间可发消息；单条限长；同账号同赛事限频；
- **屏蔽**：任一方可屏蔽对方，屏蔽后对方不能发起连接也不能发消息；
- **举报**：一键举报并附最近消息快照；主办方与平台管理员按既有权限处理；
- **通知**走**既有通知端口**，不新建第二套通知系统；
- 消息**可撤回**（本人），撤回后对手方不再看到内容。

### 4.2 安全底线（这一块是本轮最大的新面，必须写死）

1. **默认全关**：赛事未开启 / 本人未开启 → 既不可被搜索也不可发起。
2. **仅同场参赛者**：只允许本场**报名通过且名单有效**的人参与；不接受访客。
3. **不自动暴露联系方式**：邮箱/电话不由平台补全；是否给联系方式由本人在消息里自行决定。
4. **屏蔽与举报是硬功能**，不是可选项；被举报内容在人工处理前可对当事人隐藏。
5. **不承诺年龄核验**：本平台不做实名/年龄核验，因此私信**默认关闭**，由本人逐场开启，且平台**不宣称**对未成年人提供保护。
6. **数据边界**：消息内容不进入任何模型训练（宪法 XII）；账号导出/删除沿用既有本人数据路径。
7. **可关闭**：主办方随时关闭本赛事的名录/连接/私信；关闭后**不再返回**新数据。既有连接与消息按**主办方配置的保留口径**处理：`保留可读` / `冻结只读`（默认） / `到期清理`（可设天数），口径 MUST 在界面写明。

## 5. E · 赛事级独立能力配置（不动共享枚举）

新增赛事级结构 `EventCommunityConfig`（挂在赛事配置，随正式发布版本冻结，**不进** `EventModuleFlags`）：

```
workShowcase: boolean          // 作品展示（默认 false）
peerFeedback: boolean          // 文字留言（默认 false）
peerReview:   boolean          // 数值互评（默认 false）
peerReviewScale: "1-5"|"0-10"|"yes-no"  // 互评量纲（主办方配置）
peerReviewDimensions: {id,label}[]        // 互评维度（主办方配置，与评委维度分开）
peerReviewPassRate: number     // 参与率门槛（默认 0.3，范围 0.1–1）
commentMaxLength: number       // 留言长度上限（主办方配置）
participantDirectory: boolean  // 本场名录（默认 false）
connections:  boolean          // 连接（默认 false）
directMessages: boolean        // 私信（默认 false）
directMessageRetention: "keep"|"freeze"|"purge"  // 关闭后的保留口径（默认 freeze）
directMessagePurgeDays: number|null       // purge 时的天数
assistants: Record<sectionKey, boolean>   // 各流程模块助手开关（默认全开，可逐模块关）
```

- **落点**：比赛设置内新增"公开与社区"折叠区；草稿→预览→发布沿用既有发布流程，**开启/关闭随版本冻结**，历史版本可追溯。
- **默认全 false**；未开启时相关接口一律 403/空，界面不渲染任何入口。
- **为什么不动共享枚举**：`EventModuleFlags` 被前端、校验、发布版本与看板同时读取，加键会牵动多处并改变已发布赛事的版本语义（规划 33 已验证过这条成本）。

| 数值互评开关 + 量纲 + 维度 + 参与率门槛 | C | false | 同上 | **是** |
| 本场名录开关 | D | false | 同上 | **是** |
| 连接开关 + 请求上限 / 冷却 | D | false | 同上 | **是** |
| 私信开关 + 保留口径 + 清理天数 | D | false | 同上 | **是** |
| 既有模块开关（报名/队伍/破冰/评审/行程/住宿/餐券） | 既有 | 模板默认 | 比赛设置 → 功能与报名 | **是**（既有规则） |

**分野**：面向**选手**的社区与公开能力随正式发布版本冻结（可追溯、可回滚到旧版本语义）；**内部运营项**（邀请、助手开关、助手额度）即时生效并写审计。

## 6. 分期与分会话建议

| 期 | 内容 | 建议会话范围 | 依赖 |
| --- | --- | --- | --- |
| P1 | E 赛事级能力配置 + D1 本场名录 | 主会话（配置）+ `event-communication` 或 `recruiting`（名录只读投影） | 无新权限面 |

| P4 | B1 助手框架 + 评审/报名两个助手 | 新模块（如 `src/modules/organizer-assistants/`） | 既有 DSH 管道与预算 |
| P5 | C② 文字留言 | `event-judging` | P2 |
| P6 | D2/D3 连接 + 私信（含屏蔽/举报/限频） | 新模块或 `recruiting` 扩展 + 根通知 | P1、P4 的经验 |
| P7 | C③ 数值互评（满足宪法全部条件）与 B2 其余助手 | `event-judging` / 助手模块 | P5、P4 |

**顺序理由**：P1 复用既有事实、零新权限面；P2 只改披露；P3 动权限路径；P4 动成本与隔离；P5–P7 涉及内容治理，放最后。
