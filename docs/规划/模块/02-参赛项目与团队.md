# M02 参赛项目与团队：详细模块规划

日期：2026-10-08  
状态：设计建议；接口、数据结构与状态尚未实现。  
依据：[产品构想](../../../草根黑客松情报局-产品想法与问题分析.md)、[宪法 v1.1.0 草案](../../../.specify/memory/constitution.md)。宪法批准状态不因本规划变化。

配套：[总体规划](../00-总体规划.md)、[数据与接口协作约定](../10-数据与接口协作约定.md)、[工具与灵感库](09-工具与灵感库.md)。

## 1. 目标、范围与决策状态

参赛项目是四个核心功能的共同上下文：比赛要求、作品目标、成员、测评摘要、分工、时间计划、任务、仓库和交付都关联同一个 `Project`。团队管理解决的是已认识成员的协作，首版不扩展成陌生人匹配平台。

| 项目 | 状态 | 本规划建议 |
| --- | --- | --- |
| 围绕同一参赛项目贯通核心功能 | 已明确 | 使用稳定项目 ID，不在各模块复制互不相连的项目 |
| 邀请队友、保留项目与成果 | 已明确 | 私人项目、有效期邀请、历史记录 |
| 支持个人参赛 | 建议默认 | `Project.teamId` 可空，不强迫个人创建虚假队伍 |
| 同一队伍参加多场比赛 | 建议默认 | Team 与 Project 分开，队伍可关联多个项目 |
| 两种项目角色：管理员/成员 | 建议默认 | 通过成员关系授权，后续需求再扩展 |
| 项目公开分享、最大人数、邀请默认有效期 | 待确认 | 首版默认私人，人数遵从赛事要求，邀请建议 72 小时 |

**MVP：** 创建/编辑参赛项目、填写作品目标与赛事关联、建立团队、邀请与加入、退出与移除、项目成员角色、成员可用时间、项目状态、活动记录、共享资料收藏、只复制必要上下文的下一场参赛入口。工具与灵感库为用户后续明确方向，内容与筛选由 M09 负责。

**非目标：** 陌生人匹配、队伍公开排行榜、聊天系统、视频会议、复杂组织层级、成员绩效评定、多人实时富文本编辑、自动拉人进入 GitHub。

## 2. 用户故事

| 故事 | 验收结果 |
| --- | --- |
| 我想先独自分析比赛，再邀请队友 | 未建团队可创建私人项目；后续可关联团队并邀请项目成员 |
| 队长想让队友明确项目目标与截止时间 | 项目概览展示来源、目标、成员与下一步；未确认时间明确提示 |
| 一个人想参与多个不同团队 | 成员关系彼此独立，切换项目不混入别队任务或报告 |
| 队友只想看到自己参加的项目 | 同队身份不自动公开队伍所有私人项目 |
| 队员临时退出时，队长需要重新分工 | 退出保留成果与历史，未完成任务进入需要重新分配状态 |
| 团队参加下一场比赛时想复用经验 | 可以选择复用目标模板与经验卡，截止时间、授权和成员状态重新核验 |

## 3. 正常流程与页面

正常路径：登录 → 创建项目 → 关联赛事或暂填规则 → 填写最小作品目标 → 设置截止时间与时区 → 邀请成员 → 成员确认投入时间与共享范围 → 测评 → 分工/规划 → 执行与交付。

| 页面 | 目的与关键内容 |
| --- | --- |
| `/app/projects` | 我参与的项目、状态、最近活动、明确截止时间；为空时提供创建入口 |
| `/app/projects/new` | 项目名、赛事关联、目标、时间与时区；允许草稿，不伪造未知规则 |
| `/app/projects/{id}` | 必交要求摘要、计划版本、团队成员、阻塞项、三类交付状态与下一步 |
| `/app/projects/{id}/members` | 当前成员、角色、可投入时间、已授权测评摘要、邀请状态 |
| `/app/projects/{id}/settings` | 名称、可见性、关联队伍、转交管理员、归档 |
| `/app/teams/{id}` | 队伍资料、成员、本人有权查看的参赛项目 |
| `/join/{token}` | 邀请对象和角色；登录后主动接受；不显示全队私人报告 |
| `/app/projects/{id}/activity` | 核心范围、负责人、截止时间、成员、仓库绑定等变更记录 |
| `/app/projects/{id}/resources` | 项目成员共同可见的工具、设计参考与资料收藏；引用 M09 资源或手动保存 URL |

跨模块导航统一为“概览 / 比赛要求 / 分工 / 任务计划 / GitHub 与交付 / 复盘”。不要求用户先理解模块编号；未完成前置输入时解释缺什么，并允许手动补充。

## 4. 项目与成员状态

建议项目生命周期：

`draft → preparing → active → finalizing → submitted → retrospective → archived`

| 状态 | 含义 | 进入条件与注意事项 |
| --- | --- | --- |
| `draft` 草稿 | 核心输入还在整理 | 允许未知赛事时间，但不能生成伪装成确定的计划 |
| `preparing` 备赛 | 规则、成员与目标准备中 | 至少有目标；赛事关键未知项可见 |
| `active` 执行中 | 团队开始按确认的计划执行 | 至少有已确认计划或手动任务，不依赖全部人必须测评 |
| `finalizing` 整理提交 | 核验仓库、视频、文档与演示 | 仍可修复，不能自动认为全部功能完成 |
| `submitted` 已记录提交 | 已有明确提交记录 | 可能是成员自报，概览标注来源；不等于平台核验成功 |
| `retrospective` 复盘中 | 正在整理过程与经验 | 已提交或未提交都可复盘 |
| `archived` 已归档 | 停止日常编辑，保留历史 | 不删除数据；恢复时重新检查截止时间与授权 |

以上是工作阶段标签，提交事实由 M06 的 `SubmissionRecord` 单独保存，M07 只读引用。未完成提交的项目可以从 `active/finalizing` 进入复盘或归档，但不能因此显示“已提交”。阶段变更由有权限的人主动执行并记录，不能仅因截止时间过去就改成成功。

成员状态建议：`invited / active / left / removed`。邀请状态为 `pending / accepted / expired / revoked`；邀请已接受与成员活跃不是同一个状态，成员后来退出不会使原邀请重新可用。

## 5. 业务规则、权限与并发

1. `ProjectMembership` 是私人项目访问依据；`TeamMembership` 只说明队伍归属，不自动赋予全部项目权限。
2. 项目创建者初始为项目管理员；团队队长与项目管理员分别记录，可以是不同的人。角色候选见 [M01](01-账号登录与权限.md)。
   `Project.createdBy` 仅记创建历史，不能作为授权捷径；转交管理后创建者是否仍有权，只以其当前 `ProjectMembership` 为准。
3. 创建个人项目无需 Team；将个人项目关联团队时显示将要加入哪些项目成员，由管理员确认，不默认把队伍全员拉入。
4. 任何项目至少保留一名活跃管理员。最后管理员退出、被删除或被移除前，必须转交或归档；不能产生无人负责的活跃项目。
5. 邀请限定团队或项目、目标角色、有效期和可选指定邮箱。默认单次接受，不允许未经登录确认就获得权限。
6. 重复接受同一邀请是幂等操作，不创建重复成员；团队满员或赛事资格变化时重新提示，不静默绕过。
7. 团队名额和赛事作品人数不是网站全局固定常数。赛事要求未核验时标“待确认”，不把无法确认的数据当硬性禁入依据。
8. 原始测评不随入队公开。成员可选择共享项目所需摘要，退出后不再允许其他成员读取本人私有数据。
9. 成员可用时间记录时区、时间窗口、预计有效工时和确认时间，不把墙钟剩余时间当工作容量。更新将提示 M05 检查计划，不静默改变已确认计划。
10. 成员退出或移除后，其已完成交付和版本记录保留作者归属；未完成任务标记需重分配，不能自动标完成或删除。
11. 改动目标、关键时间、成员和仓库绑定均记录版本与操作人。前端发送预期版本，过期写入返回冲突，让用户对比后再保存。
12. 复制项目时不复制会话、GitHub 令牌、有效仓库授权、旧提交成功状态、他人原始测评或未同意复用的私人记录。
13. 个人收藏与项目收藏分开；个人收藏不会因入队而自动共享。项目收藏按 `ProjectMembership` 读取，记录收藏者、用途和来源。
14. 外部资料仅保存合法 URL、标题和用途备注，不能把引用链接当执行命令。资源失效或官方工具价格变化时标记待核验，不静默删除团队备注。手动 URL 标为成员参考/待核验，不自动发布成已审核 Resource，也不自动宣称免费、可商用或比赛允许使用。
15. `Resource` 内容和费用/许可/账号/栈等核验信息归 M09，审核发布归 M08；M02 只保存项目引用与备注，不允许项目成员借收藏接口修改已审核资源事实。AI 推荐只引用已审核 Resource ID，不自动推荐成员手动添加的未核验网址。

团队权限建议：队长可以修改队伍资料、邀请/移除团队成员、转交队长和解散队伍；普通成员可以修改本人资料和可用时间、查看本人有权参与的项目、退出队伍。活跃队伍至少有一名队长，最后队长退出前需转交或解散。退出队伍不自动等于退出每个项目，界面列出相关项目并让用户明确选择，逐项执行对应项目的管理员与任务检查。

## 6. 数据与接口建议

候选技术为模块化单体 API + PostgreSQL，身份、项目和其他模块共享稳定 ID；DSH 采集使用独立 Worker。该候选尚未确认。

| 实体 | 建议字段与约束 |
| --- | --- |
| `Team` | `id, name, createdBy, status, version, createdAt` |
| `TeamMembership` | `teamId, userId, role, status, joinedAt, leftAt`；每一队伍/用户最多一个当前关系 |
| `Project` | `id, name, teamId?, eventId?, createdBy, goal, minimumDeliverable, stage, timezone, version`；`createdBy` 仅为创建者，无独立权限 |
| `ProjectMembership` | `projectId, userId, role, status, joinedAt`；权限依据 |
| `Invitation` | `scopeType, scopeId, tokenHash, role, expiresAt, maxUses, acceptedBy, revokedAt` |
| `MemberAvailability` | `id, projectId, userId, timezone, windows, effectiveHours, confirmedAt, version`；`windows` 引用 M05 子窗口 ID/版本，`effectiveHours` 由有效窗口计算或明确标初步自报，不重复计算容量 |
| `ProjectRequirementLink` | `projectId, requirementId, evidenceVersion, acceptedAt`；关联 M03 规则，不复制成无来源文本 |
| `ProjectActivity` | `projectId, actorId, type, objectId, beforeSummary, afterSummary, occurredAt` |
| `ProjectResourceBookmark` | `id, projectId, resourceId?, url?, title, purposeNote, savedBy, savedAt, status`；`resourceId` 或 `url` 至少一个，权限随项目，不复制工具凭据；相同资源的项目引用幂等合并 |

建议 API 均以 `/api/v1` 开头：

| 接口 | 行为 |
| --- | --- |
| `POST /projects` | 创建项目与本人管理员关系，在同一事务完成 |
| `GET /projects` | 只返回本人有权查看的项目 |
| `GET /projects/{id}` | 项目概览；摘要依然按数据权限过滤 |
| `PATCH /projects/{id}` | 修改允许字段，携带 `expectedVersion` |
| `POST /teams` | 建队与初始队长记录 |
| `POST /projects/{id}/invitations` | 创建限定范围邀请，返回一次性的邀请链接 |
| `POST /invitations/{token}/accept` | 检查登录、有效期、撤销、目标角色和容量，幂等接受 |
| `DELETE /projects/{id}/invitations/{invitationId}` | 撤销尚未消费邀请 |
| `PATCH /projects/{id}/members/{userId}` | 角色变更，不能移除最后管理员 |
| `POST /projects/{id}/leave` | 本人退出，检查管理员与未完成任务影响 |
| `PUT /projects/{id}/my-availability` | M02/M05 共用入口，事务更新本人集合及关联子窗口，触发计划输入过期提示，不另维护第二套容量 |
| `POST /projects/{id}/stage-transitions` | 记录阶段变化与说明；不代替提交事实 |
| `POST /projects/{id}/clone` | 选择字段复制，默认新项目草稿 |
| `GET /projects/{id}/resources` | 返回本项目共享资料，按权限过滤 |
| `POST /projects/{id}/resources` | 成员显式收藏工具/灵感，验证 Resource ID 或 URL 与字段 |
| `DELETE /projects/{id}/resources/{bookmarkId}` | 收藏者或项目管理员移除项目引用；不删除 M09 原始资源 |

创建示例：

```json
{
  "name": "第一次黑客松",
  "teamId": null,
  "eventId": "event_example",
  "goal": "做一个能演示的中文规则解读原型",
  "minimumDeliverable": "输入一份规则并显示带来源的提交清单",
  "timezone": "Asia/Shanghai"
}
```

用户输入目标文本是数据。不得因目标里出现命令而让 Agent 执行命令、调用仓库写入或更改成员权限。ID 归属、日期格式、成员关系都要在服务端校验。

## 7. 异常与恢复

| 场景 | 恢复行为 |
| --- | --- |
| 未知赛事或采集暂失败 | 允许手动创建草稿，显示来源未核验；M03 后续补规则 |
| 两人同时编辑目标 | 后提交者收到版本冲突并看到差异，不覆盖前者 |
| 成员临近截止退出 | 保留其交付，列出待重分配任务，给 M05 提供重规划输入 |
| 邀请链接外泄 | 管理员撤销；指定邮箱邀请只允许对应已验证账号接受 |
| 邮件通知失败 | 项目内仍显示邀请状态；可复制链接，不把邮件成功当加入成功 |
| 项目误归档 | 管理员恢复；已过期截止时间与 GitHub 授权需重新确认 |
| 队伍解散 | 项目不能直接丢失；选择保留管理员管理或逐项归档 |
| 旧计划引用已离队成员 | 旧版本保留，当前任务显示负责人已离队并阻止新分配 |

私有项目与 Team 的删除不等同于删除第三方仓库。原始测评、共同任务、成果、日志的保留由明确政策处理，不制造“删除队伍就抹掉全部成果”的隐含行为。

## 8. 模块依赖与事件契约

| 上下游 | 连接方式 |
| --- | --- |
| M01 身份权限 | 用户、成员权限、登录与邀请认证 |
| M03 赛事分析 | 关联赛事/规则版本；关键时间更新提示计划输入变化 |
| M04 测评分工 | 提供当前成员和项目目标；只接收有授权的测评摘要 |
| M05 时间任务 | 提供可用时间、当前成员和项目范围；成员变动让计划进入需复核状态 |
| M06 GitHub | 项目关联 `RepositoryBinding`，仓库授权由 M06 独立检查 |
| M07 复盘 | 阶段、目标、成员、活动与交付记录进入复盘证据 |
| M09 工具与灵感库 | 引用精选资源，保存个人选择加入项目的收藏；不扩展聊天或社区 |

建议事件：`ProjectCreated`、`ProjectScopeChanged`、`ProjectMemberJoined`、`ProjectMemberLeft`、`MemberAvailabilityChanged`、`ProjectStageChanged`、`ProjectArchived`、`ProjectResourceBookmarked`。携带 `projectId, actorId, version, occurredAt` 及必要变化字段。事件仅表示事实变化，不授权 AI 自动实施重新分工或仓库写入。

## 9. 开发任务

| 顺序 | 任务与可交付结果 |
| --- | --- |
| M02-T01 | 建立项目/团队/成员/邀请迁移和唯一约束，确定角色与默认私人策略 |
| M02-T02 | 项目创建、列表、概览；个人项目无 Team 也能使用 |
| M02-T03 | 邀请创建、过期、撤销、接受；验证重复接受与对象越权 |
| M02-T04 | 成员角色与退出流程；最后管理员保护、任务重分配提示 |
| M02-T05 | 目标、时间与成员可用时间编辑；版本冲突与活动记录 |
| M02-T06 | 接入赛事、分工、任务和仓库摘要，避免模块数据分裂 |
| M02-T07 | 阶段、归档和选择性复制；验证不复制私有资料与授权 |
| M02-T07B | 接入 M09 项目资料收藏；验证个人收藏不自动共享、移除引用不删除源资源 |
| M02-T08 | 贯通一支真实小队的建项目、邀请、退出及恢复流程 |

对多人编辑、事务和权限用自动化验证；文案、布局和导航用页面检查，不为每一段可逆文案制造实现镜像测试。

## 10. Given / When / Then 验收

1. **Given** 已登录用户还未建团队；**When** 创建个人项目；**Then** 得到私人草稿项目和本人管理员关系，可进入赛事分析。
2. **Given** A、B 同队但 B 未加入 A 的私人项目；**When** B 请求该项目；**Then** 无权查看，队伍页面也不泄露项目私有内容。
3. **Given** 有效邀请尚未接受；**When** 同一用户重复点击接受；**Then** 只有一条有效成员关系，响应可安全重试。
4. **Given** 两人从版本 3 编辑目标；**When** 一人保存到版本 4 后另一人保存；**Then** 后者看到冲突，不覆盖版本 4。
5. **Given** 唯一项目管理员申请退出；**When** 提交退出；**Then** 必须先转交或归档，不能留下活跃无人管理项目。
6. **Given** 一位成员有两个未完成任务；**When** 退出；**Then** 成果和历史保留，任务显示待重分配，已确认计划提示需要复核。
7. **Given** 已归档项目有旧仓库绑定和提交成功记录；**When** 复制到下一场比赛；**Then** 新项目为草稿，不继承仓库写权限、旧提交状态或他人原始测评。
8. **Given** 提交截止时间已过且尚无提交记录；**When** 项目进入复盘；**Then** 展示“未记录正式提交”，不显示自动成功。
9. **Given** 成员有个人工具收藏；**When** 加入项目；**Then** 收藏仍只由本人查看；显式加入项目后才成为项目共享资料。

## 11. Constitution Check

| 原则 | 检查结果与实施要求 |
| --- | --- |
| I 新人流程 | Project 统一四模块上下文、明确下一步与成员范围；项目资料按任务用途组织，收藏不当完成 |
| II 事实追溯 | 赛事要求引用证据版本；未知截止时间显式显示；Resource 显示来源、核验时间、费用/许可状态，手动 URL 不伪装审核条目 |
| III 分工 | 成员、意愿、可用时间供分工使用，不默认公开原始回答 |
| IV 时间 | 改时间/成员/范围提示重规划；重大修改保留版本 |
| V GitHub | 成员身份不扩大仓库权限，不复制授权 |
| VI 隔离 | 团队和项目权限分域，私人默认、邀请撤销 |
| VII 简单实现 | 单体模块、统一 ID、事务与版本；M09/M08 管理 Resource、M01/M09 个人 ResourceBookmark、M02 项目 ProjectResourceBookmark，暂不微服务 |
| VIII 行为验证 | 权限、邀请、最后管理员、并发、复制和个人收藏显式共享有验证；AI 引用未审核资源需拒绝 |
| IX 失败恢复 | 手动草稿、冲突恢复、离队交付保留、归档可恢复 |

## 12. 风险与待决项

- **跨模块数据漂移：** 计划、分工和仓库不得各有独立成员名单；都引用 `ProjectMembership` 和版本。
- **队长过度控制：** 管理权限不能推导成私人测评或 GitHub 访问权限。
- **工具维护负担：** 首版概览突出接下来的少量动作，成员可用时间先用简单表单，避免完整日历系统。
- **状态混淆：** 工作阶段、保存成功、运行验收和正式提交始终分开。
- **需确认：** 项目角色名称、队伍与项目关系、邀请有效期与名额规则、公开分享是否首版需要、归档/删除保留期限。

建议记录创建到首份计划的耗时、邀请接受率、切换项目误操作、成员变动后重分工完成率。真实试用应确认个人参赛和 2–5 人小队都能顺利完成同一条流程；此人数是测试样本建议，不是赛事硬性限制。
