# M03 赛事聚合与证据分析：模块实施规划

日期：2026-10-08｜版本：0.1｜状态：供实施决策的规划草案

关联：[产品构想](../../../草根黑客松情报局-产品想法与问题分析.md) · [项目宪法](../../../.specify/memory/constitution.md) · [M08 采集审核后台](08-采集审核与运营后台.md) · [M06 GitHub 与交付](06-GitHub助手与赛事交付.md)

跨模块字段、角色与响应沿用 [数据与接口协作约定](../10-数据与接口协作约定.md)；宪法检查依据当前 v1.1.0。

## 1. 目标与需求性质

帮助新人回答三个问题：这场比赛是否适合当前队伍、规则要求交什么、现在应准备什么。所有会改变参赛决定的结论都应能回到规则原文，系统不替主办方保证赛事质量。

| 性质 | 内容 |
| --- | --- |
| 用户已明确 | 赛事信息分析、AI 参赛建议、识别潜在问题；DSH 指 DeepSeek Harness |
| 宪法约束 | 事实、建议与未知分开；关键字段有依据；截止时间保留时区；多阶段分别记录 |
| 本规划默认建议 | 首批 2–3 个经验证来源、10–20 场赛事；先人工核验关键字段再公开发布 |
| 待确认 | 来源名单、赛事地域、目标年龄范围、内容更新频率、收费方式；上述数量是验证规模建议 |

成功行为：用户通过规则页找到此前遗漏的资格或提交要求，将赛事关联到参赛项目，并把要求转换为可执行清单。浏览次数和 AI 生成次数只用于诊断，不单独证明价值。

## 2. 第一版范围

### 必须完成

1. 游客可浏览已审核赛事；登录用户可关联赛事到自己的参赛项目。
2. 列表支持状态、线上/线下、地域、是否注明新人资格等少量有依据的筛选。
3. 详情展示主办方、官方入口、资格、费用、团队规模、材料、规则依据与核验时间。
4. 报名、开发、提交、路演等阶段单独记录；展示原时区与用户本地时间。
5. 基于项目背景生成适配建议、备赛清单和待确认问题；报告可编辑、可追溯。
6. 来源过期、冲突和缺失字段显式显示；支持用户提交纠错。
7. 公共赛事更新不静默改写队伍已确认的计划；生成版本差异及重新确认入口。

### 后续方向

收藏、来源订阅、赛事日历导出、多语言翻译、更多赛事来源和更细的过滤器。是否纳入下一阶段由试用反馈决定。

### 第一版非目标

不做赛事可靠性百分比、不保证奖金兑现、不凭资料缺失推断内定；不做全网无限抓取、陌生人组队市场、自动报名、替用户向主办方发消息。

## 3. 用户故事

| ID | 角色与动作 | 可观察价值 |
| --- | --- | --- |
| E-01 | 新人按可参加时间与形式查看赛事 | 找到能参加的候选，而非只看奖金额度 |
| E-02 | 用户展开提交截止时间的证据 | 能核对官方文字和时区，发现不确定项 |
| E-03 | 项目管理员填入项目目标、成员经验与预算后分析 | 得到针对本队的适配建议及理由 |
| E-04 | 成员查看必交材料和未知条款 | 知道还要准备什么、向谁确认什么 |
| E-05 | 项目已开始后规则发生变化 | 看见变更并自行决定如何更新计划 |
| E-06 | 用户发现赛事信息错误 | 提交链接和说明，看到处理状态 |

## 4. 页面与主流程

| 页面 | 建议路由 | 主要动作 |
| --- | --- | --- |
| 赛事目录 | `/events` | 筛选、查看核验状态、进入详情 |
| 赛事详情 | `/events/:eventId` | 查看规则与证据、打开官方入口、创建/关联项目 |
| 项目赛事分析 | `/app/projects/{id}/rules` | 补齐团队背景、生成适配分析、确认要求快照 |
| 纠错表单 | 详情内抽屉 | 指明字段、附来源、查看反馈编号 |

**主流程：**浏览目录 → 核查关键条款 → 登录并创建/选择项目 → 提供团队背景 → 生成分析草案 → 查看依据与未知项 → 项目管理员确认赛事要求快照 → 传递给分工、规划和交付清单。项目根页 `/app/projects/{id}` 是概览，本页是其规则子页；`/projects` 在本文仅用于 API 路径。

用户输入 URL 时仅提交采集请求，不让浏览器直接抓取任意地址。非白名单来源进入受限核验流程；无法获取时允许粘贴规则文字，标为用户提供，不能冒充官方核验。

页面分成三个相邻区块：**规则事实**、**针对本队的建议**、**尚未确认**。每项建议要说明使用了哪些事实和哪些团队输入。未明确允许 AI 的比赛写“AI 使用规则未说明”，不改写成“允许 AI”。

## 5. 状态与版本

### 赛事内容发布状态

`draft → pending_review → published → archived`

审核可退回 `draft`。已发布赛事采到新内容时生成新的候选版本，旧版本继续展示并注明更新处理中；重大字段冲突时显示 `needs_recheck` 质量标记或暂时撤下。**内容状态**与**赛事阶段**分开，赛事阶段由已确认日期推导为报名中、进行中、待提交、已结束或未知。

### 分析任务状态

`queued → running → succeeded / failed / cancelled`

`succeeded` 只代表结构化分析已生成且通过基础校验，不代表规则已人工核验。项目使用的分析另有 `draft / confirmed / superseded` 状态；生成新草案不会覆盖已确认版本。

### 日期规则

- 保存规则中的原始文本、IANA 时区、UTC 时间、是否只有日期、证据 ID。
- 未注明时区不使用主办方所在地作静默推断；可给建议时区，但必须标为假设并经用户确认。
- “10 月 20 日前”不能无依据自动变成 23:59:59；需要核验具体含义。
- 多个阶段分别存储 `stageType`、名称、开始/结束、提交入口；跨午夜和夏令时按时区库计算。
- 修改日期后生成差异，不自动修改 M05 的已确认任务期限。
- 未知截止时间的项目可以保存草案，但不得显示精确倒计时或“保证可完成”。

## 6. 数据设计

以下为逻辑模型，字段名供接口与数据库设计参考，不锁定 ORM。日期统一由服务端解析。

| 实体 | 关键字段与约束 |
| --- | --- |
| `Event` | `id`、标准名称、主办方、形式、地域、官方 URL、`publicationStatus`、`qualityFlags`、`publishedVersion`、`lastVerifiedAt` |
| `SourceConfig`（引用） | M08 所有；来源域/路径白名单、获取方式、频率、凭据策略、允许用途与启停状态，不承担单次抓取证据 |
| `EventSource` | `id`、`eventId`、可选 `sourceConfigId`、单次来源 URL/类型、内容哈希、抓取时间、来源可信范围、候选版本；是某次来源快照及证据载体，不存不必要全文 |
| `RuleEvidence` | `id`、`eventId`、来源 ID、字段/条款类型、短摘录、定位信息、原始日期文本、核验人/时间、冲突关系 |
| `EventAnalysis` | `id`、`eventId`、可选 `projectId`、输入摘要/哈希、事实引用、建议、未知项、模型/提示版本、`status`、确认人/时间 |
| `AnalysisRun` | `id`、关联分析、排队/执行时间、输入版本、状态、错误分类、调用用量、重试次数、结果版本 |
| `Project`（引用） | 关联赛事、已确认规则版本、团队背景版本；不得把最新版赛事直接当作已接受规则 |
| `AuditEvent` | 谁在何时确认/修改了哪个版本、修改原因；避免记录完整私人输入 |

赛事阶段、资格和必交材料先作为 `Event` 版本内容中的结构化子记录；实施时可按查询需要独立建表。提交清单每条有稳定 ID、来源、必需/可选/未知、适用阶段、关联任务 ID，便于 M05 与 M06 追踪同一要求。

事实引用必须引用数据库中真实存在且属于同一赛事版本的 `RuleEvidence`；模型输出的 URL 或证据 ID不能未经校验直接入库。用户团队背景只用于项目私有建议，不发布到公共赛事详情。

## 7. API 草案

统一前缀 `/api/v1`，使用服务端项目权限检查。列表分页，时间为带时区的 ISO 8601；错误返回 `code / message / recoveryAction / requestId`。

| 方法与路径 | 作用与限制 |
| --- | --- |
| `GET /events` | 仅返回公开版本；支持筛选和游标分页 |
| `GET /events/:id` | 公共事实、证据和质量状态；不返回私人项目建议 |
| `POST /event-intake-requests` | 登录用户提交 URL/规则文本，限频、去重；返回请求状态 |
| `POST /events/:id/corrections` | 提交纠错；游客是否开放待定，默认登录后开放 |
| `PUT /projects/:id/event` | 项目管理员关联赛事及指定版本；需项目版本号避免覆盖 |
| `POST /projects/:id/event-analyses` | 生成异步草案；传赛事版本、团队背景版本、幂等键 |
| `GET /projects/:id/event-analyses/:analysisId` | 成员查看本项目报告与任务状态 |
| `POST /projects/:id/event-analyses/:analysisId/confirm` | 项目管理员确认适用要求；不得删除原始证据 |
| `GET /projects/:id/event-changes` | 当前确认版本与公开新版本的差异 |

写入请求须验证资源所属项目，而非只验证客户端传来的 `projectId`。长任务返回 `202` 和 run ID，前端有限轮询或服务端推送，不持续重复触发模型。

## 8. 权限规则

- 游客可读已公开事实及证据；不读用户分析或未审核内容。
- 项目权限以活跃 `ProjectMembership` 为依据：`status=active, role=manager` 的项目管理员可更换赛事或确认新要求；`role=member` 的活跃成员可读本项目确认要求、提交纠错、提出补充。`TeamMembership.role=captain` 不自动授予这些项目管理权限。
- 项目中的自行补充规则标为“团队补充”，不能修改公共赛事事实。
- 运营审核员管理公共候选内容；没有默认读取私人测评、仓库或团队对话的权限。
- 发布内容需要 M08 的审核权限；AI、采集 Worker 和普通成员无公开发布权限。

## 9. 异常与恢复

| 情况 | 显示与恢复 |
| --- | --- |
| 官方页不可访问 | 保留上次公开版本，显示核验时间与抓取失败；提示用户打开官方入口核对 |
| 两个来源日期冲突 | 并列展示冲突，不自动挑最晚日期；进入关键字段复核 |
| AI 输出无证据或非法日期 | 校验失败，保留输入与错误摘要；最多有限重试，允许手工整理 |
| 分析失败 | 已确认要求和旧报告可读；用户可补充资料后重试，不清空项目 |
| 原页面更新或删除 | 标记来源状态，保留获准保存的最小证据与历史版本 |
| 队伍背景变化 | 分析标“基于旧背景”，允许重生成，旧建议留档 |
| 规则与计划不一致 | 显示具体差异并产生 M05 复评提醒；不静默改变任务 |

## 10. 模块依赖与事件

- 依赖 M01 身份与权限、M02 项目成员与背景、M08 采集审核发布。
- 向 M04 提供赛事允许工具与任务上下文；向 M05 提供确认后的阶段日期与材料；向 M06 提供仓库/视频/路演等交付规则。
- 建议内部事件：`EventPublished`、`EventRulesChanged`、`ProjectEventConfirmed`、`ProjectRequirementsConfirmed`、`EventCorrectionSubmitted`。
- 第一版使用模块内调用与数据库 outbox 即可；事件带 ID、版本和项目 ID，消费者幂等，不为此提前搭建微服务消息平台。

## 11. 可实施任务

| 任务 | 交付物 | 前置与检查 |
| --- | --- | --- |
| E-T01 来源验证 | 2–3 个来源的获取方式、允许用途、样例与失败记录 | 来源/模型可访问性技术验证；由 M08 共同负责 |
| E-T02 规则 schema | 阶段、资格、材料、证据、未知/冲突结构与校验 | 数据约束、日期样例；不先接 UI 伪数据 |
| E-T03 公共目录与详情 | 发布版本查询、筛选、证据展开、质量状态 | 仅读公开版本，空列表和过期状态 |
| E-T04 项目关联与快照 | 项目保存指定规则版本与变更比较 | M02 权限；并发确认保护 |
| E-T05 AI 分析适配器 | 输入构造、结构化校验、异步状态、版本与成本记录 | 事实引用可核对；模型超时降级 |
| E-T06 确认与任务映射 | 要求稳定 ID、项目管理员确认、传递 M05/M06 | 不重复创建同一材料任务 |
| E-T07 纠错与更新 | 用户提交、运营处理、项目变更提示 | M08 审核；旧版本仍可回查 |
| E-T08 行为验证 | 日期、权限、错证据、过期与端到端验证记录 | 区分测试样例与真实赛事 |

任务量在来源验证后估算；不能把“10 场赛事已采到”当作采集长期稳定的证明。

## 12. Given / When / Then 验收

1. **Given** 官方规则有报名和提交两个日期，**When** 展示详情，**Then** 分别展示阶段、原时区、用户时间和证据，不合成一个截止时间。
2. **Given** 规则未写 AI 使用限制，**When** 分析比赛，**Then** 输出“未说明/待确认”，不输出“允许”。
3. **Given** 模型引用不存在的证据，**When** 校验结果，**Then** 报告不进入可确认状态且能手动处理。
4. **Given** 另一队项目有私有适配报告，**When** 当前用户请求其 ID，**Then** 服务端拒绝并不泄露报告摘要。
5. **Given** 队伍确认了版本 1，公开规则更新为版本 2，**When** 打开项目，**Then** 显示差异与待确认状态，原任务期限不变。
6. **Given** 模型不可用，**When** 用户打开已有项目，**Then** 仍能读已确认要求并手工维护备赛清单。
7. **Given** 报名截止原文只有日期且没有时区，**When** 建立任务计划，**Then** 该输入列为假设，未经确认不生成精确倒计时。

## 13. Constitution Check

| 原则 | 本模块处理与门禁 |
| --- | --- |
| I 新人流程 | 赛事要求进入同一项目，页面展示下一步 |
| II 可追溯事实 | 发布前核验关键字段；证据、时区、冲突与版本可见 |
| III 测评 | 只提供规则上下文，不从赛事标签推断个人能力 |
| IV 可交付规划 | 多阶段要求与快照供 M05 使用，不改写已确认计划 |
| V GitHub 可靠性 | 只描述仓库规则，真实写入及提交归 M06 |
| VI 隔离 | 团队背景私有，采集数据不能取得执行权 |
| VII 可维护 | schema、查询、模型适配器分开；输出校验与迁移可测试 |
| VIII 真实验证 | 关键日期、证据、项目权限和版本变化有行为检查 |
| IX 可恢复 | 保留已确认数据，失败任务有限重试与手工路径 |

## 14. 风险与待决策

- **来源维护可能比模型调用更费力。** 试用期记录每场核验时长和错误字段；据此决定扩大来源还是缩小覆盖。
- **“适合参加”缺乏统一标准。** 先展示资格匹配、时间容量和任务缺口等具体依据，不输出无法解释的总分。
- **“正规”标签可能被理解为担保。** 标签建议用“官方来源已核对”并显示核对范围；是否采用额外验证须先定义标准。
- **用户更需要执行帮助而非目录。** 观察分析是否真的进入项目计划，避免把目录数量当主要目标。
- **待决定：**首批来源、哪些字段必须人工审核、过期阈值、用户提供规则的使用范围、纠错响应目标、文本保留期限与成本限额。

具体 DSH 隔离与采集限制由 [M08](08-采集审核与运营后台.md) 实施；本模块不通过网页访问直接启动有用户凭据的 Agent。
