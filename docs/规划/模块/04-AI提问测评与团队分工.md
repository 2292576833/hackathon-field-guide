# M04｜AI 提问测评与团队分工规划

日期：2026-10-08  
状态：实施建议稿；评分标准、题量和试用参数需要在真实队伍中校准。  
定位：把成员的经验、试做表现、意愿和可投入时间，转成当前项目的可编辑分工。  
依据：[项目构想](../../../草根黑客松情报局-产品想法与问题分析.md)、[项目宪法 v1.1.0](../../../.specify/memory/constitution.md)。

## 1. 模块目标与边界

本模块回答三个问题：成员目前有哪些可用证据、接下来适合交付什么、队伍还缺什么。测评服务于当前项目，不生成永久能力标签，不承诺找到“全局最优分工”。

项目权限采用 M02 的 `ProjectMembership.role = manager / member` 与 `status`。本文“项目管理员”指活跃 `manager`，界面可称“项目负责人”；项目普通成员指活跃 `member`。队伍归属与项目授权分别处理，同队或担任团队队长都不会自动获得项目权限。私人原始答案始终由本人管理。

### 第一版交付范围

- 成员填写经历、工具、岗位偏好和可用时间；分别记录自评与实际作品证据。
- 使用经过审核的任务模板及固定评分规则；AI 可以变换题面并根据回答追问。
- 支持答题草稿、继续答题、提交、异步评分、解释结果和申请重新评估。
- 覆盖需求、设计、开发与调试、测试、文档、素材、路演等贡献；每队不必设置全部岗位。
- 输出成员个人报告、队伍可见摘要和分工草案；队伍可改人、改任务、补理由。
- 分工保存版本，向 M05 提供任务候选、负责人、协助者、依赖和交付条件。
- 某成员未测评、拒绝测评或模型失败时，仍允许手动分工和继续参赛。

### 第一版不包含

- 科学能力诊断、职业资格认证、全站排名和跨题型未经校准的统一排行。
- 摄像头监考、强制身份测验、代码沙箱或用户任意代码执行。
- 依靠年龄、学历、提交次数或代码行数自动决定能力。
- 自动分配仓库权限或在 GitHub 写入代码；这些属于 M01、M02、M06 的授权边界。
- 将测试结果自动同步为长期公开能力画像；长期沉淀由 M07 按用户授权处理。

## 2. 用户故事与优先级

| ID | 优先级 | 用户故事 | 可观察结果 |
| --- | --- | --- | --- |
| M04-US01 | 必需 | 成员希望填写经验和任务偏好，避免只被安排技术工作 | 可选择非技术任务并补充证据 |
| M04-US02 | 必需 | 成员希望离开页面后继续答题 | 草稿与题目版本保持一致 |
| M04-US03 | 必需 | 成员希望知道为什么得到这个分数 | 每个结论有评分项、证据和未验证项 |
| M04-US04 | 必需 | 项目管理员希望看到队伍能完成哪些交付物 | 摘要提供候选职责和明确缺口 |
| M04-US05 | 必需 | 队伍希望调整 AI 分工 | 手动修改后仍能通过项目与人员校验 |
| M04-US06 | 必需 | 队伍希望一个未答题的成员不会卡住所有工作 | 可采用临时手动分工，清楚显示依据缺失 |
| M04-US07 | 必需 | 成员希望原始答案只由自己查看 | 项目管理员和网站运营管理员不能通过常规接口读取原始答案 |

“必需”表示本模块的首版范围，不代表所有页面需要同时上线。先完成手动分工和权限，再接入生成与评分。

## 3. 测评内容与评分机制

### 3.1 任务模板

按真实交付能力拆分维度，不让团队成员为了凑齐岗位全部作答：

| 维度 | 情境任务示例 | 主要检查什么 |
| --- | --- | --- |
| 需求与取舍 | 给出作品目标和赛事材料，选择最小版本 | 理解要求、优先级、可交付范围 |
| 设计与页面 | 解释页面流程，提交简单原型或页面证据 | 使用流程、信息层级、实际产出 |
| 开发与调试 | 阅读报错或修改代码，说明验证步骤 | 排查过程、验证行为、求助边界 |
| 测试与交付 | 根据功能列检查清单，找出提交遗漏 | 验收标准、异常意识、材料完整性 |
| 文档与素材 | 写项目说明，整理演示素材清单 | 清晰表达、信息准确性、可复用材料 |
| 路演与协作 | 用短说明介绍项目，再回应一个追问 | 叙述结构、理解深度、协作表达 |

试用可先安排一项公共取舍题和少量与目标职责有关的小任务；题量、最长追问轮次、预算与预计作答时间作为可配置参数记录，不能写成所有用户必须完成的固定长考试。

比赛允许使用 AI 时测评可允许使用 AI，并记录使用方式。目标是理解成员能否借助工具交付与验证，不通过“是否用了 AI”简单判定好坏。禁止或限制 AI 的赛事，提示相关来源并使用符合规则的任务方式。

### 3.2 固定规则、可变题面

每个题目绑定 `QuestionSet`、任务模板、难度标识和不可变 `RubricVersion`。发布后修订规则必须产生新版本；已开始的测评继续使用原版本，不能半途中改变评分标准。

AI 变题必须保留任务目标、约束、允许材料和评分项。追问必须说明要补充哪项证据，不能临时增加新的评分维度或用更难题惩罚某个成员。超出已审题型范围的题面进入“待审核”，不直接发给用户。

第一版优先使用少量审核过的题面。AI 动态变题产生的未校准差异，必须在结果中说明；不宣称难度等价。

### 3.3 可解释评分

建议使用行为锚点，而非让模型凭印象给 0–100 分。下面是待试用的评分规则示例：

| 项目 | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| 验证步骤 | 无步骤或与任务无关 | 知道需要验证但不能描述 | 提供可执行的主要验证步骤 | 有步骤、预期结果与异常处理 |
| 交付依据 | 没有产出证据 | 自述产出，尚未核对 | 有作品或过程证据 | 证据可复现，并说明限制 |

具体评分项、权重和“不适用/证据不足”的处理在每个 `RubricVersion` 中固定。证据不足不等于能力为零；未评分项与已评分项分别展示。不同维度各自呈现，不要求相加为 100%。

如显示百分比，定义必须随结果出现：

> 本次任务测评得分 = 已评分项目加权所得分 / 这些项目可得分。仅反映这一题组与评分版本下的表现；未覆盖能力另列。

只有同题组、同评分版本及同任务条件的结果，才允许并列检查具体评分项。即使条件一致，首版也不生成全队“能力总榜”；未经校准不得合并不同任务成绩。不能将 75/100 写为“真实开发能力 75%”或“任务成功概率 75%”。

评分输出必须包含证据片段标识、理由、未验证项和模型/提示/规则版本。模型返回不存在的证据 ID、评分越界、遗漏必要项或不符合 JSON Schema 时，评分进入失败或待复核状态，不发布伪造的完整结果。

### 3.4 评分纠错

成员可对评分项补充说明、作品或可复现步骤。重新评估创建新 `AssessmentScore`，保存旧版本与修改原因。具备题库职责的网站运营管理员可以维护题库和查看脱敏运行记录，不默认读取私人原始答案；需要人工协助查看答案时，由本人明确分享必要内容，并记录访问范围与审计事件。

## 4. 分工生成与修改

输入来自项目目标、赛事要求摘要、成员意愿、可用时间、测评摘要和已存在任务。推荐顺序如下：

1. 列出当前项目的具体交付物和验收条件，先覆盖赛事必交材料和核心演示流程。
2. 根据证据为每项任务推荐负责人及可选协助者，说明依据与缺失项。
3. 检查负责人是否为项目成员、是否愿意承担、是否存在可用时间；不将测评分数直接换成开发速度。
4. 明确无人可承担的工作，提出缩小范围、使用熟悉模板、补充协助或手动指定的方案。
5. 由队伍编辑和确认，生成 `AssignmentVersion`，再交由 M05 验证时间和依赖。

分工草案的期限属于建议；M05 使用实际可用窗口和截止点生成计划后，才形成可检查的任务安排。报告不能声称分工已确认即可按时交付。

负责人变更、关键交付物变更和删除任务均在版本差异中显示。第一版采用活跃项目管理员确认应用，成员可评论或提出修改；这是授权操作规则，不等于系统判断所有成员都同意。新的分工版本不静默改动已应用的 `PlanVersion`，必须进入 M05 重新规划或手动同步流程。

## 5. 页面与状态机

### 页面

| 页面 | 核心信息 | 主要动作 |
| --- | --- | --- |
| 成员资料 | 经历、偏好、可用时间入口、证据使用说明 | 保存、跳过测评、开始小任务 |
| 作答页 | 当前题目、允许工具、预计作答量、草稿状态 | 保存、补充证据、继续、提交 |
| 个人报告 | 已评分项、依据、未验证项、共享范围 | 纠错、补充证据、调整共享摘要 |
| 队伍摘要 | 已完成/未完成、候选职责、关键能力缺口 | 手动分工、请求更新 |
| 分工编辑与版本 | 交付物、负责人、理由、依赖、草案差异 | 修改、确认应用、转时间规划 |

不得在队伍页暴露原始答案、个人不必要的背景或默认显示年龄。报告不使用羞辱性标签；用“此项尚无证据”“建议有人协助验收”等描述当前任务边界。

### 状态机

- `AssessmentAttempt`：`draft → in_progress → submitted → scoring → completed`；评分失败进入 `scoring_failed`，重试回到 `scoring`。成员可在提交前取消；超时未完成标 `abandoned`，不改成已失败能力。
- `QuestionSet`：`draft → reviewed → published → retired`；停用只影响新测评，历史版本可追溯。
- `AssessmentScore`：`proposed → validated → published`；校验失败进入 `rejected`；成员申诉生成新结果而非修改旧评分。
- `AssignmentVersion`：`draft → needs_changes / ready → applied → superseded`。`ready` 表示结构合法，不表示进度可行；M05 单独检查。

异步任务必须显示排队、运行、失败和可重试状态，刷新页面不会重新计费生成。个人答题页和团队分工页保存各自版本；网络失败时保留可恢复草稿，不错误显示提交成功。

## 6. 数据结构与输入输出约定

以下为接口约定示例，不是现成实现。标识符为示例，时间使用包含时区的 ISO 8601 值。

| 实体 | 关键字段与约束 |
| --- | --- |
| `AssessmentAttempt` | `id, projectId, membershipId, userId, questionSetId, rubricVersionId, status, answers, evidenceRefs, revision`；`membershipId` 指 `ProjectMembership.id`，`userId` 为原始答案作者，私人读取依据作者本人 |
| `QuestionSet` | `id, taskTemplateIds, questions, difficultyLabel, allowedTools, status, version`；发布版本不可变 |
| `RubricVersion` | `id, dimensions, criteria, weights, anchors, missingEvidencePolicy, version`；明确每项可得分 |
| `AssessmentScore` | `attemptId, rubricVersionId, criterionScores, evidenceRefs, limitations, validatedAt, modelVersion` |
| `AssignmentVersion` | `projectId, baseVersionId, inputSnapshot, proposedAssignments, gaps, changes, status, appliedBy` |
| `ProjectMembership` | `id, projectId, userId, role, status`；角色为 `manager/member`，只允许活跃项目成员访问，退出或移除后不再有项目访问权 |
| `MemberAvailability` | M02 管理的本人项目可用时间集合，引用子窗口 ID 与版本；M04 只读引用，不另建容量事实 |
| `AvailabilityWindow` | M05 的可用时间子窗口，按 `MemberAvailability` 关联；M04 通过集合版本引用 |

本文 `membershipId`、`ownerMembershipId` 与 `helperMembershipIds` 均引用 M02 的 `ProjectMembership.id`，不是账号 ID 或团队成员 ID。原始答案作者单独保留 `userId`；成员状态使用 `ProjectMembership.status`，生成与应用时核对 `active` 状态与项目归属。M02 本人时间集合按 `projectId + userId` 关联，M04 通过项目成员关系找到该集合。

      "membershipId": "pm_1",
      "preferredTasks": ["页面", "测试"],
      "assessmentSummaryId": "as_1",
      "assessmentStatus": "completed",
      "memberAvailabilityVersionId": "mav_2"
    },
    {
      "membershipId": "pm_2",

## 7. 权限与数据可见性

| 操作或数据 | 本人 | 项目其他成员（member） | 项目管理员（manager） | 网站运营管理员 |
| --- | --- | --- | --- | --- |
| 原始答案、未分享作品证据 | 读写自己的 | 无权 | 无权 | 常规管理无权 |
| 队伍分工摘要 | 查看与管理自己的共享范围 | 按项目成员权限查看 | 按项目成员权限查看 | 不默认获得项目内容权限 |
| 分工草案 | 查看、提出修改 | 查看、提出修改 | 编辑与确认应用 | 不替代项目管理员应用 |
| 题库与评分规则 | 查看相关说明 | 查看相关说明 | 查看相关说明 | 按后台职责维护 |

加入项目时说明默认共享的最小摘要范围：本人确认可承担的职责、相关测评表现及限制。不把原始问答加入团队提示词；需要证据解释时引用本人选择分享的片段。撤回共享后，新摘要和新分工不再使用该内容；已应用的工作安排保留必要版本事实，删除和保留政策由 M01/M07 明确，避免承诺自动删除所有审计记录。

所有读写在服务端核对活跃 `ProjectMembership`、角色与资源归属；`TeamMembership` 不替代项目访问检查。测评输入视为数据，成员答案中的“忽略规则”“读取其他成员答案”不能改变评分器权限或提示词控制层。

## 8. 接口、事件与模块依赖

接口前缀统一为 `/api/v1`。`expectedRevision` 与 M02 的 `expectedVersion` 均表示客户端所见资源版本，使用相同的乐观锁语义：不匹配返回冲突，禁止覆盖最新事实。接口实施时统一字段名称；异步生成接口支持幂等键。以下仅表达契约，不要求机械实现全部端点。

| 接口 | 用途 | 权限与结果 |
| --- | --- | --- |
| `POST /projects/{id}/assessment-attempts` | 新建本人测评 | 成员；绑定题组和评分版本 |
| `PATCH /assessment-attempts/{id}/answers` | 保存本人草稿 | 本人；校验 `expectedRevision` |
| `POST /assessment-attempts/{id}/submit` | 提交并评分 | 本人；返回异步任务 ID，重复提交不重复建任务 |
| `GET /assessment-attempts/{id}/report` | 个人完整报告 | 本人；不接受项目管理员越权 |
| `PATCH /assessment-attempts/{id}/sharing` | 修改共享摘要 | 本人；立即影响后续读取与生成 |
| `GET /projects/{id}/assessment-summaries` | 队伍最小摘要 | 当前成员；过滤隐私字段 |
| `POST /projects/{id}/assignment-versions` | 生成或手动建立分工草案 | 项目管理员；可配置开放成员提案，首版不必开放 |
| `PATCH /assignment-versions/{id}` | 修改草案 | 项目管理员；已应用版本不可原地覆盖 |
| `POST /assignment-versions/{id}/apply` | 确认分工 | 项目管理员；验证基线，保存审计和差异 |

依赖关系：M01 提供会话与账户权限；M02 提供项目及成员；M03 提供版本化赛事要求；M02 提供 `MemberAvailability` 集合，M05 维护关联的 `AvailabilityWindow` 并消费分工；M06 提供用户选择的成果链接；M07 可使用经授权的验收与复盘摘要。无 GitHub 绑定也能完成本模块。

领域事件建议：`AssessmentSubmitted`、`AssessmentScoringFailed`、`AssessmentSummaryUpdated`、`AssignmentApplied`；成员变化消费 M02 的 `ProjectMemberJoined`、`ProjectMemberLeft`，可用时间变化消费 `MemberAvailabilityChanged`。事件只携带项目、版本和必要标识，不广播原始答案。事件消费与业务事务需要避免“版本已应用但下游永远不知道”的状态，可采用事务性事件记录。

## 9. 异常与降级

| 情况 | 应有行为 |
| --- | --- |
| 模型超时、预算用尽或不可用 | 保留答案与队伍资料；展示失败原因类别；允许受限重试和手动分工 |
| AI 评分结构错误 | 拒绝发布；不补一个看似有效的总分；保存脱敏校验错误 |
| 自评与作品证据冲突 | 展示证据差异和待核验项，不给成员贴“作弊”标签 |
| 某成员未完成测评 | 标记证据不足；允许临时安排，优先用短试做验证关键任务 |
| 已分工成员离队 | 相关草案失效或提示；已应用任务标待重新分配，通知 M05 重新评估 |
| 生成期间项目或成员版本变化 | 标记草案过期，重新校验后生成或手动修改，不静默应用 |
| 并发编辑分工 | 返回冲突与最新版本；保留用户修改，可对照重新提交 |
| 原始答案被撤回或请求删除 | 权限立即收敛；后续生成不再引用；按明确的数据政策处理历史记录 |

模型调用记录每次时长、费用、失败类别、重试次数和用户确认率。缓存以输入快照、题组、规则和提示版本为键；改变共享权限后不得误用旧缓存泄露摘要。

## 12. Constitution Check

| 原则 | 对应设计 | 实施门禁 |
| --- | --- | --- |
| I 新人可执行 | 小任务、可跳过、具体交付物、下一步明确 | 试用记录作答与维护成本 |
| II 事实可追溯 | 引用赛事版本，不重新编造赛事规则；题目如使用资源仅引用 M09 已审核条目 | 来源与核验状态可查；未知费用、许可或赛事适用性不作确定声明 |
| III 测评用于分工 | 固定规则、证据、非技术职责、可改分工 | 不输出真实能力百分比或无校准排名 |
| IV 时间可交付 | 分工交给 M05 校验，得分不换算速度 | 未规划的期限保留建议状态 |
| V GitHub 授权 | 成果链接仅作证据；不扩大仓库权限 | 本模块不持有或调用写入令牌 |
| VI 数据隔离 | 原始答案私有，摘要最小共享；角色与成员状态由 M02 提供 | 自动化验证跨成员、跨项目及同队未入项目访问 |
| VII 可维护 | 不可变题组、规则版本、结构校验、适配器 | 历史结果可重现评分依据 |
| VIII 行为验证 | 权限、评分约束、版本并发与端到端验收 | 关键检查通过，披露未校准结果 |
| IX 外部失败恢复 | 草稿保存、有限重试、人工分工 | 模型停用时仍能继续项目 |

## 13. 风险、观测与待决项

主要风险是题面理解成本、AI 代答造成证据失真、同一评分规则在不同模型上的漂移、成员不愿共享结果和项目管理员把建议当作命令。通过小型试做、解释验证、固定版本、共享控制与成员反馈降低风险，但不能承诺消除。

试用记录：作答与追问时间、放弃原因、评分争议项、人工改分次数、分工采纳与修改原因、关键任务验收情况、每队调用与人工复核成本。通过这些证据判断是否缩减题量、强化实际试做或扩大题库，不提前承诺统一成功率。

待决项：首批任务维度和题量、规则权重、人工复核职责、摘要默认共享字段、成员提案权限、个人数据保留与删除政策、首批试用队伍。可用时间的数据归属已统一：M02 管理集合，M05 管理子窗口，M04 只引用。所有参数应标注建议值及试用依据；未决定模型供应商不阻止编写评分契约和手动分工。
