# M05｜任务规划与动态调整规划

日期：2026-10-08  
状态：实施建议稿；缓冲、提醒频率和估算参数需要用真实比赛校准。  
定位：把赛事要求、分工与成员可用时间转成可检查的任务计划，进度变化后及时暴露风险并提出可确认的新方案。  
依据：[项目构想](../../../草根黑客松情报局-产品想法与问题分析.md)、[项目宪法 v1.1.0](../../../.specify/memory/constitution.md)。

## 1. 模块目标与边界

本模块帮助团队回答：最小作品是什么、每个人何时交付、哪些任务互相阻塞、当前计划是否仍可行、需要删掉什么。计划以实际比赛和团队为输入，不能默认每场比赛持续 48 小时，也不能承诺保证按时完成。

管理和应用权限采用 M02 的 `ProjectMembership.role = manager / member` 与 `status`：活跃 `manager` 为项目管理员，界面可称“项目负责人”；活跃 `member` 为项目普通成员。同队或担任团队队长不自动获得项目权限。

### 第一版范围

- 从 M03/M02 读取多个截止点、必交材料、项目目标和当前任务；从 M04 读取确认分工与证据限制。
- 成员填写自己的可用时间窗口，明确时区、休息和已占用安排。
- AI 提出最小可交范围、任务、工时区间、依赖、检查点和缓冲；服务端做确定性校验。
- 可编辑任务看板和轻量进度更新，支持报告卡点与剩余工时。
- 根据任务用途提供 M09 已审核资源的可选入口，区分熟悉工具和需要额外学习的工具。
- 在关键进度变化或用户请求时生成新计划草案；先展示版本差异与影响，再由项目管理员确认应用。
- 计划历史和变更理由可查；AI 不可用时可以继续更新任务和手动调整。

### 第一版不包含

- 全局最优排程、自动监控本地开发状态、靠代码量判断完成度、自动保证工时准确。
- 自动执行开发任务或强制更改成员的可用时间。
- 无人确认的自动删需求、换负责人、推迟必交截止点。
- 大型甘特排程工具、复杂资源采购和外部团队排班系统。
- 默认通过邮箱或第三方聊天工具发送提醒；首版先用网站内提醒，外部通知另行设置授权。

## 3. 计划输入与事实层

### 必需输入

1. 当前时间由服务端获取；展示时区使用项目/用户选择，不依赖服务器所在时区。
2. 每个截止点分别保存：报名、作品提交、视频提交、演示、补材料等；不将“比赛结束时间”当成唯一截止点。
3. 赛事必交要求及来源版本；未确认截止点或资格影响计划时，输出明确假设。
4. 项目最小目标、必须功能、可选功能、已有成果和运行验收条件。
5. 项目成员、意愿、分工版本、可用时间窗口和学习/排错需要。
6. 现有任务、依赖、已验收结果、阻塞项和剩余工作估算。

赛事截止点保存 `instantUtc` 与 `sourceTimeZone`，同时保存来源原始文本。用户输入仅为“周五晚上”“10 月 10 日”或 offset 与时区相互矛盾时，必须让其补充或确认；系统不得默默推断精确截止时间。未确认可以建立计划草案，但不能显示已经核验的可行性结论。

首次使用可用少量问题收集输入，避免填写完整管理表才允许开始。缺信息时提供可编辑假设清单，允许先手动建立任务。

### 成员时间窗口

M02 的 `MemberAvailability` 是本人的项目可用时间集合，保存时区、确认时间和集合版本；M05 的 `AvailabilityWindow` 是该集合关联的子窗口。集合可引用子窗口 ID 与版本，不能同时维护互相矛盾的两份时间事实。`effectiveHours` 由有效子窗口计算或标为成员初步自报，不可同时当成另一项可用容量。

`AvailabilityWindow` 是成员愿意用于这个项目的时间，不是比赛持续时间。明确学习、休息、课程和其他安排；已排除的休息不得再次扣除。相互重叠窗口先合并，避免重复计算；与其他项目重叠时提示占用，首版可先由成员确认，而非假设拥有全站排程能力。

辅助者的时间也需分配，不能只计算主负责人。一个任务包含实现、测试和交接时，优先拆成有交付物的子任务，避免让“协助”变成不可量化的无限容量。

## 4. 任务、估时与可行性机制

### 4.1 最小可交范围

每项任务使用 `must` 或 `optional`：

- `must`：赛事必交要求或队伍确认的最小作品所必需的工作。
- `optional`：可以删除而不违反已确认必交规则和最小目标的增强功能。

赛事明确要求的提交材料不能因为剩余时间不足就自动改为可选。可削减的是作品范围与增强功能；硬性要求仍不可满足时，显示不可行并建议确认规则、寻求协助或调整参赛决定。

任务至少有标题、负责人、交付物、验收条件、估时、依赖和目标截止点。无人负责的必须任务、无法核验的交付物和已经过去的截止点均应成为显式问题。

### 4.2 工时区间

建议字段：`optimisticMinutes`、`likelyMinutes`、`pessimisticMinutes`，明确这些是工作时间估算，并满足 `0 ≤ optimistic ≤ likely ≤ pessimistic`。长任务可切成可验收小任务，但拆分不能减少真实工作量。

AI 根据方案提出初值；成员和项目管理员可修改并写明依据。新手学习、调试、环境、交接和返工需要单独包含，不能将测评分数线性换算成工时。推荐陌生工具时，包含学习、账号设置和接入成本，并提供继续使用熟悉工具的选择。区间缺少证据时标记“低依据估算”；不用一个精确分钟数掩盖不确定性。

运行/部署时间、等待外部服务和工作工时区分。任务需连续时标记不可分割；可拆分任务可跨多个有效窗口，但需保留合理交接和上下文恢复安排。首版先支持清楚的可拆分标志，不实现复杂日历优化器。

### 4.3 依赖图

`TaskDependency` 定义任务间前置条件。首版以完成后才能开始的依赖为主；可以提前并行准备的 README、素材收集或测试清单拆为独立任务，再在最终验收上依赖核心功能。

服务端必须验证：

- 所有引用在同一项目，任务不能依赖自身。
- 依赖图无循环；发现循环返回具体链路供修改。
- 被删除任务的后继任务有明确处理，不能留下悬空引用。
- 必须任务不能依赖已删除或被排除的可选任务。
- 已完成且验收通过的任务保留事实，不因重规划自动重新打开。

### 4.4 可选工具与参考资源

任务可附 `resourceRefs`，只能引用 M09 工具与灵感库中已审核且当前可展示的 `Resource.id`。AI 不自行生成下载地址、收费承诺或不存在的工具链接；链接与费用、账号要求、使用门槛、技术栈和许可由资源事实层提供，保留官方/原始来源、最后核验时间与未知项。设计灵感引用不代表拥有图片、品牌或代码使用许可；工具可用也不代表该赛事允许使用。资源推荐不自动成为任务前置依赖，也不把付费工具暗示为参赛必需。

建议按任务目的、技术栈和成员经验筛选，并说明推荐用途。成员可以忽略推荐或选择熟悉工具；替换工具影响估时、验收或技术方案时，在重规划差异中显式展示。资源失效或下架时移除新推荐入口，保留旧计划的资源标识和失效状态，主任务仍可手动继续。

### 4.5 确定性校验与排程

AI 提供建议，不作为可行性判定的唯一来源。首版可采用“依赖拓扑顺序＋按截止点和必须优先级分配可用窗口”的可解释策略；不声称得到最优解。处理顺序相同但得到不同有效方案可以人工选择。

校验流程：

1. 锁定输入快照：赛事要求、成员、可用时间、分工、任务进度版本。
2. 校验日期、关联关系、估时区间、优先级和依赖图。
3. 扣除已占用窗口并为每个负责人建立有效容量；固定休息和不可用时间不被 AI 覆盖。
4. 分别检查常规估算与保守估算下，任务是否能放入窗口、依赖是否成立、截止点是否满足。
5. 检查多人协作、测试、集成、材料与提交缓冲是否真实占用时间。
6. 标记阻塞链、关键任务、人员容量缺口和待确认输入；给出可操作取舍方案。

计划状态：

| 状态 | 含义 | 展示建议 |
| --- | --- | --- |
| `unknown` | 关键截止、时间窗口或必需任务信息不足 | 草案与假设，先补充什么 |
| `feasible` | 在当前输入和保守估算下通过规则校验 | 当前估算可安排，持续检查 |
| `at_risk` | 常规估算可排，保守估算或关键假设尚有风险 | 风险任务与提前检查点 |
| `infeasible` | 必须任务在常规估算下也无法满足当前约束 | 明确缺口及可削减方案 |

这些状态表示当前估算和输入下的结果，不能包装成按时完成概率。输入过期时附 `staleInputs`，不继续展示旧的“可行”状态为实时事实。

### 4.6 缓冲与检查点

提交缓冲配置在具体截止点前，依据平台、材料体量、网络和队伍经验设定。首次试用可以提供建议时长，由队伍调整；不能统一规定所有比赛最后 6 小时才提交。

应安排环境可运行、核心流程可演示、停止扩功能、完整材料核对和正式提交检查点。检查点有负责人和验收证据，不只是日历标记。文档与素材在开发中同步准备，不一律放到最后。

缓冲被工作侵占时产生明确风险提示；扩大缓冲导致必需工作无法容纳时，要展示取舍，不能同时声称全部工作与缓冲都满足。

## 5. 进度更新与动态调整

### 轻量更新

成员更新自己任务的状态、交付链接、阻塞原因和剩余工时区间。百分比可选，不能作为唯一事实；“进行中”或一次 GitHub 保存不等于任务完成。

`done` 必须符合验收条件。第一版建议由任务指定验收人或项目管理员确认；没有验收人时允许明确记录“本人自检”，并显示依据。M06 的仓库保存成功、作品运行验收和赛事正式提交保持独立状态。

### 重规划触发

- 项目管理员主动请求，或关键任务延期、卡住、负责人离队、截止点变更、范围变化后提示建议。
- 触发相近时合并请求，避免每次拖动卡片都调用模型。
- 没有新进度时提醒数据旧，不凭空填写完成情况。
- 模型调用有超时、重试次数和队伍预算；具体参数在试用后设置。

### 重规划应用流程

`输入快照 → AI 草案 → 确定性校验 → 版本差异 → 队伍讨论/修改 → 项目管理员确认 → 原子应用`

差异必须包含新增/删除任务、`must/optional` 变化、负责人、期限、依赖、估时、范围、缓冲、风险，以及对已完成工作和必交材料的影响。重大变化清楚标识，不能只展示“已优化”。

第一版由活跃 `ProjectMembership.role=manager` 的项目管理员作为项目授权操作人确认；成员能查看和提出修改，不用等待全体完成测评。AI 生成不构成修改授权。应用同时校验最新项目、任务和当前计划版本；期间成员提交新进度则重新评估受影响部分，避免用旧草案覆盖新成果。

旧计划保留。恢复旧版本也需要按当前时间和实际完成情况重新校验，不将旧截止安排直接回滚成可执行事实。

## 6. 页面与状态机

| 页面 | 用户完成什么 | 关键信息 |
| --- | --- | --- |
| 规划输入 | 设定最小范围、确认截止点和可用时间 | 来源、时区、假设、人员缺口 |
| 项目计划总览 | 看是否来得及、下一检查点和风险 | 剩余有效容量、必须任务、缓冲 |
| 任务看板 | 更新工作与卡点 | 负责人、交付物、依赖、目标期限 |
| 时间安排 | 看个人有效窗口与任务占用 | 休息、学习、协作和重叠冲突 |
| 重规划对比 | 确认调整的实际影响 | 旧版/草案、变化理由、校验问题 |
| 计划历史 | 查询是谁改了什么 | 版本、输入快照、应用人和理由 |

状态机：

- `Task`：`todo → in_progress → blocked / review → done`；`blocked → in_progress`；验收未通过由 `review → in_progress`。删减可选任务使用 `cancelled` 并保留理由；已完成任务不能被 AI 自动取消。
- `PlanVersion`：`draft → validating → ready / needs_changes → applied → superseded`；生成失败有 `generation_failed`；输入变化可标 `stale`。
- `ProgressUpdate`：追加记录，不覆盖历史；修正更新需记录新事件及修正理由。
- 异步生成任务：`queued → running → succeeded / failed / cancelled`，与计划业务状态分开。

`ready` 代表草案满足应用检查，可行性字段仍可能为 `at_risk` 或 `infeasible`。结构合法但不可行的计划可以保存为讨论草案；应用为执行计划时必须显式确认未解决约束并显示问题，不能把它标成可按时交付。

## 7. 数据结构与 schema 示例

示例是规划契约，不是已实现功能。建议技术路径为 Next.js + TypeScript + PostgreSQL 模块化单体；计算规则独立于页面和模型适配器。

| 实体 | 关键字段 |
| --- | --- |
| `PlanVersion` | `id, projectId, basePlanVersionId, inputSnapshot, feasibility, assumptions, issues, changes, status, appliedBy, revision` |
| `Task` | `id, projectId, requirementRefs, title, priority, ownerMembershipId, helperMembershipIds, acceptanceCriteria, durationEstimate, schedule, deadlineRef, resourceRefs, status, revision` |
| `TaskDependency` | `projectId, predecessorId, successorId, dependencyType` |
| `MemberAvailability` | M02 的 `projectId, userId, timezone, windows, effectiveHours, confirmedAt, version`；`windows` 引用 M05 子窗口 ID/版本，集合与窗口原子更新 |
| `AvailabilityWindow` | M05 的 `id, projectId, membershipId, startsAt, endsAt, sourceTimeZone, purpose, version`；通过项目与 `ProjectMembership.userId` 关联本人集合，子窗口不形成第二套成员名单 |
| `ProgressUpdate` | `id, taskId, actorId, status, remainingEstimate, blocker, evidenceRefs, createdAt` |
| `AssignmentVersion` | M04 的分工输入版本；M05 引用，不私自改写历史版本 |

`membershipId`、`ownerMembershipId`、`helperMembershipIds` 均指 M02 的 `ProjectMembership.id`。读取该关系的 `userId` 与 `projectId` 关联 `MemberAvailability` 本人集合，读取 `status` 核对活跃资格；这些字段不是团队关系 ID。离开或移除项目使未完成任务进入重新分配流程，已完成产出仍保留作者 `userId`，不创建第二套成员身份。

## 8. 权限、接口与事件

### 权限

- 成员编辑自己的可用时间、更新自己负责的任务、查看项目共享计划并提出修改。
- 项目管理员编辑项目范围、负责人、全队安排、缓冲和截止配置；赛事来源时间不能作为可编辑事实静默覆盖，人工更正要保存原值和依据。
- 项目管理员确认应用计划；成员请求重规划可作为提案，首版按队伍设置限制预算和频率。
- 项目外用户无权读取任务、时间窗口和更新记录。网站运营管理员不默认拥有项目内容读取权。同队未加入项目的用户没有计划访问或应用权限；所有任务负责人必须是当前活跃 `ProjectMembership`。
- 所有写接口核对资源归属与项目角色；项目管理员不能代替成员授权 GitHub 写操作。

### 接口契约

统一 `/api/v1`，写操作使用 `expectedRevision` 或基线版本。`expectedRevision` 与 M02 的 `expectedVersion` 都是同一乐观锁语义：比较客户端所见资源版本，过期则返回冲突，不覆盖最新事实；实施时统一字段名称。生成与应用支持幂等键。

| 接口 | 用途 |
| --- | --- |
| `GET /projects/{id}/plan` | 当前计划、风险和输入新鲜度 |
| `PUT /projects/{id}/my-availability` | 与 M02 共用本人可用时间入口；在事务内更新集合与子窗口，检测重叠与时间非法 |
| `GET /projects/{id}/tasks` | 看板任务及权限允许的进度 |
| `POST /tasks/{id}/progress-updates` | 提交状态、阻塞和剩余估时 |
| `PATCH /tasks/{id}` | 按角色修改任务；关键变更记录版本和理由 |
| `POST /projects/{id}/plan-versions` | 初次规划或重规划，返回异步任务 |
| `GET /plan-versions/{id}/diff` | 基线与草案的影响对比 |
| `PATCH /plan-versions/{id}` | 编辑草案并重新校验 |
| `POST /plan-versions/{id}/apply` | 校验最新基线后，事务内应用任务与计划版本 |
| `GET /projects/{id}/plan-versions` | 历史与应用记录 |

典型错误：时间不明确返回需确认项；依赖成环返回问题链；版本冲突返回最新基线；无权限不泄露项目存在与私人内容；模型失败返回可恢复任务状态。不可行属于业务结果，不使用通用“服务器出错”掩盖。

### 模块事件

消费：M03 `EventRulesChanged`、`ProjectRequirementsConfirmed`，M02 `ProjectMemberJoined`、`ProjectMemberLeft`、`MemberAvailabilityChanged`，M04 `AssignmentApplied`，M06 `GitSaveSucceeded`、`DeliveryValidationRecorded`、`SubmissionRecorded`。事件中的来源与验证范围决定它能改变什么状态：`GitSaveSucceeded` 最多触发相关任务检查，不自动宣布运行验收完成；运行验证与赛事提交记录保留用户自报、验证记录或真实平台确认的区别。M09 提供已审核 `Resource` 查询与资源失效状态，模型只接收可引用的候选 ID 和必要事实，不凭空构造网址。

发布：`ProgressUpdated`、`PlanRiskDetected`、`PlanDraftGenerated`、`PlanApplied`、`MilestoneVerified`。M07 使用经授权的计划、验收与变更记录复盘；M08 可观察脱敏失败与成本，不获取成员私人答案。

事件只携带必要标识和版本，不混入仓库令牌；使用事务性事件记录或等效机制确保已应用版本与事件一致。重复事件不会重复生成计划或产生多次提醒。

## 9. 异常、并发与降级

| 情况 | 行为与恢复 |
| --- | --- |
| 必须工作超过容量 | 显示缺口、受影响截止点及缩减建议，不把工作静默挪到比赛后 |
| 依赖图成环 | 拒绝应用，指出循环任务链并允许编辑 |
| 截止点不确定或已过去 | 标明原因；草案不冒充已核验可行，建议补充或确认参赛安排 |
| 生成时成员提交新进度 | 草案标输入变化；确认前重新核对并保留新成果 |
| 同一成员任务时间重叠 | 校验失败或风险提示，调整安排，不能把两个任务都视为独占完成 |
| 负责人离队或撤回窗口 | 任务标待重新分配，当前计划变旧，保留已有产出 |
| 模型输出不合法或建议删必须材料 | 服务端拒绝该部分，展示失败；人工编辑仍可用 |
| 网络中断或重复点击应用 | 返回同一应用结果，不重复修改任务；能查询最终真实状态 |
| 模型不可用或队伍预算不足 | 当前看板、进度与手动计划继续工作，生成入口说明原因 |
| 用户不更新进度 | 显示最后更新时间与未知项，不按时间流逝自动增长完成率 |
| 旧版本恢复 | 重新验证当前截止、成员与任务，不抹掉实际已完成记录 |

## 11. Given / When / Then 验收

| ID | Given | When | Then |
| --- | --- | --- | --- |
| M05-AC01 | 同一赛事有报名与提交两个截止点 | 生成计划 | 分别保留，不用报名时间或比赛结束时间替代提交时间 |
| M05-AC02 | 时间没有时区或相互矛盾 | 请求应用计划 | 提示需确认项，不静默猜测精确时间 |
| M05-AC03 | 成员只声明 3 小时窗口 | AI 安排 8 小时任务 | 校验报容量缺口，不当作全天可用 |
| M05-AC04 | A 依赖 B、B 依赖 A | 保存依赖或应用计划 | 拒绝循环并显示任务链 |
| M05-AC05 | 必须任务依赖拟删除的可选任务 | 确认删减方案 | 必须修正依赖或证明替代产出，不留下悬空引用 |
| M05-AC06 | 正式规则要求视频 | 模型建议删视频以赶截止 | 拒绝把规则材料改成可选，报告不可行 |
| M05-AC07 | 存在可选功能和过量工作 | 请求重规划 | 提出具体删减并说明是否影响最小作品 |
| M05-AC08 | 草案建议更换负责人和截止 | 查看重规划页面 | 应用前显示差异、理由与影响，不静默改动 |
| M05-AC09 | 草案生成后成员完成一个任务 | 应用旧草案 | 检查版本冲突并保留新进度，不自动重新打开已验收任务 |
| M05-AC10 | 提交缓冲已被任务占用 | 查看计划 | 显示缓冲侵占和截止风险，不重复计算同一时间 |
| M05-AC11 | 仓库文件已保存但未运行 | 接收 M06 保存事件 | 保持运行验收未完成；不标记赛事已提交 |
| M05-AC12 | 模型超时 | 成员更新自己的任务 | 更新成功；计划可手动维护，失败请求可恢复 |
| M05-AC13 | 两次提交同一应用幂等键 | 服务端处理 | 只产生一个应用版本和一组任务变更 |
| M05-AC14 | 项目外用户知道任务 ID | 读取或更新任务 | 服务端拒绝并不暴露内容 |
| M05-AC15 | 没有实际进度更新 | 时间经过数小时 | 不虚构完成度；显示数据过期或未知 |
| M05-AC16 | 计划标为 feasible | 查看状态解释 | 明确只在当前输入和估算下通过校验，不承诺按时完成 |
| M05-AC17 | 模型推荐一个未审核 Resource 或自行生成网址 | 服务端校验推荐 | 拒绝未知引用；主任务保留并可手动继续 |
| M05-AC18 | 成员选择陌生工具完成必须任务 | 更新计划估时 | 包含学习与接入成本，展示熟悉工具替代方案 |
| M05-AC19 | 用户只属于项目关联队伍，未加入项目 | 读取计划或请求应用 | 服务端拒绝，不以团队角色代替项目 manager 权限 |
| M05-AC20 | 成员更新 M02 可用时间集合 | M05 重新计算容量 | 使用同一集合版本与关联子窗口，不重复计算 effectiveHours |

测试包含跨时区、跨日、成员窗口重叠、不可拆任务、多个截止、人员离队、循环依赖、基线冲突和重复事件。对时间与容量规则做自动化验证；真实队伍用端到端试用验证更新负担与建议价值。

## 12. Constitution Check

| 原则 | 对应设计 | 发布门禁 |
| --- | --- | --- |
| I 新人可执行 | 最小作品、轻量进度、明确下一步 | 新人能说明当前风险与自己下一任务 |
| II 事实可追溯 | 多截止点、来源版本、时区与假设；资源保留官方来源、费用/许可与核验状态 | 不覆盖规则原值；不编造链接；灵感不自动授予使用许可 |
| III 分工可解释 | 引用 M04 版本，不将分数换成速度 | 无测评也能手动规划，能力缺口可见 |
| IV 以交付约束 | 必须/可选、估时区间、依赖、容量与缓冲 | 时间与容量规则通过自动化验证 |
| V GitHub 可靠 | 保存、验收、正式提交分开 | 仓库事件不产生虚假完成状态 |
| VI 权限与隔离 | 活跃项目成员更新本人、manager 确认；团队角色不扩大项目权限 | 跨项目和同队未入项目权限测试、必要审计 |
| VII 可维护 | 业务校验独立模型；不可变计划快照 | Schema、引用、循环和日期校验 |
| VIII 可观察验证 | Given/When/Then、真实与模拟区分 | 贯通试用与并发恢复验证 |
| IX 失败恢复 | 人工可用、有限重试、版本保留 | 模型停用后任务仍可更新 |

## 13. 风险、指标与待决项

### 主要风险

- 工时估计普遍偏乐观：使用区间和早期小规模验收，记录实际偏差；不能靠模型语气修复估时。
- 新人不持续报进度：减少更新字段，在检查点更新；不用虚假的自动完成度替代。
- 重规划太频繁造成混乱：合并触发、显示版本差异，设置有限通知，避免不断改负责人。
- 全队缺乏关键技能：缩小范围或补充协助，系统无法通过排表创造能力。
- 来源截止变更：保留来源版本、触发重新核对；用户自填时间须标来源。
- 项目管理员忽略不可行提示：应用页展示具体未解决约束并保存确认，产品不承诺阻止所有错误决策。

### 试用观测

记录计划生成与校验时长、调用成本、任务工时偏差、过期输入、风险被发现的时间、删减是否实际执行、计划采纳与人工修改原因、更新耗时和次数、各阶段真实验收与提交状态。重点观察团队是否在截止前作出有效取舍；不把使用看板次数当成参赛成功。

### 待决项

首批赛事形式、默认缓冲与检查点建议、不可拆任务规则、多人协助的容量表达、验收人设置、成员是否可直接请求生成、风险提醒频率、计划应用权限、不可行计划确认方式、跨项目窗口冲突深度、模型预算和输入保留期限。

这些应形成可调整配置与试用记录。常规 UI 和 API 实现可先进行；精确预算与提醒参数未定，不阻止人工任务流程和确定性规则开发。
