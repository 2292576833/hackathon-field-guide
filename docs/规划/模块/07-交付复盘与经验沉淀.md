# M07 交付复盘与经验沉淀：详细模块规划

日期：2026-10-08  
状态：设计建议，未实现。  
依据：[产品构想](../../../草根黑客松情报局-产品想法与问题分析.md)、[宪法 v1.1.0 草案](../../../.specify/memory/constitution.md)。本文件不批准宪法草案。

配套：[总体规划](../00-总体规划.md)、[数据与接口协作约定](../10-数据与接口协作约定.md)、[工具与灵感库](09-工具与灵感库.md)。

## 1. 目标与第一版边界

让团队区分“保存了文件”“作品能演示”“已完成赛事正式提交”，并把本次有效做法、卡点和交付证据留下来。下一次参赛可以有选择地复用经验，而不是让用户重新填一遍所有背景。

| 内容 | 状态 | 本规划处理 |
| --- | --- | --- |
| 保留参赛项目、成果和经验 | 已明确方向 | 私有复盘与经验记录，关联原项目证据 |
| 区分仓库保存、运行验收、正式提交 | 宪法明确 | 三种状态单独存储、显示来源 |
| 结构化复盘 + AI 整理草稿 | 建议默认 | 先人工填写，再让 AI 提炼；不以生成代替确认 |
| 个人经验与团队经验分开 | 建议默认 | 本人私人笔记不自动分享给队伍 |
| PPT 或完整演示文稿自动生成 | 待确认/后续 | 首版可以导出提纲，不承诺生成完整 PPT |
| 公开作品集、社区、成员排行榜 | 后续候选 | 首版不做，避免扩散私人信息和无依据评价 |

**MVP：** 正式提交记录与材料清单的汇总视图、运行验收记录、简短结构化复盘、带证据的 AI 草稿、经验卡、本人/项目范围分享、Markdown 或 JSON 导出、下次项目选择性复用。

**非目标：** 全自动跨平台正式提交、自动评定成员价值、根据提交次数给能力排名、自动发布复盘到社交平台、公开视频托管、复杂知识图谱、永久“成功经验”保证。

M06 负责 GitHub 写入、运行验收 `DeliveryVerification` 和赛事提交 `SubmissionRecord` 的事实服务；M07 只读引用这些结果，提供展示、复盘及复用。M07 页面中的“记录验收”调用 M06 接口，不另建写入服务或第二份“提交成功”数据。

## 2. 用户故事

| 用户故事 | 结果 |
| --- | --- |
| 我想知道这次到底交了什么 | 看见仓库链接/版本、运行验收与平台提交记录，以及每条记录的来源 |
| 团队希望赛后快速复盘 | 回答少量问题即可保存，无 AI 也能完成 |
| 我想知道哪里耽误了时间 | 结合任务版本、卡点与实际日期查看证据，不凭提交数推断 |
| 我有一些不想公开的个人感受 | 默认个人可见，主动选择哪些内容分享 |
| 下一场比赛不想再踩同样的坑 | 创建新项目时选择经验卡；旧赛事要求和截止时间不自动照搬 |
| 我希望离队后仍能处理本人资料 | 本人可以导出/删除个人笔记；共享项目成果按已说明规则处理 |

## 3. 页面、流程与状态

流程：查看交付概览 → 核对三种事实状态 → 填写个人或团队复盘 → 可选生成 AI 草稿 → 核对证据与修改 → 保存经验卡 → 选择导出/复用。没交上作品的项目也可以复盘，不把未提交者排除在经验沉淀之外。

| 页面 | 主要内容与状态 |
| --- | --- |
| `/app/projects/{id}/delivery` | 各必交项状态、仓库版本、运行验收、官方提交入口与提交记录 |
| `/app/projects/{id}/retrospective` | 项目目标、计划变化、卡点、有效做法、下次改进；草稿/生成/待确认/已保存 |
| `/app/projects/{id}/retrospective/history` | 草稿与已确认版本、修改人、时间、来源变化 |
| `/app/experience` | 本人有权查看的经验卡；按场景/问题筛选，不全站公开 |
| `/app/experience/{id}` | 来源项目、适用条件、证据、建议步骤、失效提示与共享范围 |
| 新建项目中的“复用经验” | 选择经验卡与模板，列出复制内容与需要重新核验的字段 |

复盘状态建议：`draft → generating → review_required → confirmed`；失败回到可编辑草稿并保留人工内容。经验卡可为 `draft / confirmed / outdated / archived`。不因为 AI 说“有效”就直接进入 confirmed。

## 4. 三类交付事实

| 记录 | 可说明什么 | 不能说明什么 |
| --- | --- | --- |
| 仓库保存结果 | 某次操作实际保存到哪个仓库、分支、版本 | 代码一定能运行，或赛事已收到 |
| 运行/演示验收记录 | 某人用什么环境、步骤验证了哪些行为及结果 | 所有环境都可用，或评审已通过 |
| `SubmissionRecord` | 指定平台、时间、材料、状态与记录来源 | 仓库里每项功能完成，或会获奖 |

正式提交契约与 M06 统一：`status = not_submitted / reported / verified / rejected_or_withdrawn`。实际记录的 `verificationSource = user_reported / platform_verified`，显示为“队员记录”或“平台核验”。没有记录时显示未记录/未提交，不虚构核验来源；准备材料进度、失败上传和未知远端结果属于独立清单或操作状态，不再混入正式提交枚举。

`reported` 不能冒充 `verified`；平台拒绝或用户撤回时保留原证据与变化原因。一个项目有多个提交阶段时用 `eventId + stageId` 区分，视频提交不能自动替代作品正式提交。

在首版不接平台回执 API 的情况下，用户填写“我已提交”，附平台项目地址、时间或可选回执。网站显示用户自报，不宣称已平台验证。上传回执注意隐藏不必要的个人信息，首版可只接收链接/文本，减少敏感附件存储。

运行验收由 M06 的 `DeliveryVerification` 保存：验收人、日期、环境摘要、可选仓库 commit、测试步骤、预期行为、实际结果、阻塞项、证据链接。M07 只展示这些事实及其版本；只让用户填写必要项，不把完整测试平台塞进首版。

## 5. 复盘结构与经验卡

### 5.1 五个默认复盘问题

1. 原来计划交付什么，最后实际交付了什么？
2. 最大的阻塞是什么，在哪个检查点发现，怎样处理？
3. 哪项分工或做法最有帮助，依据是什么？
4. 哪个功能删掉了，是否帮助按时提交？
5. 下一次最想保留或改变的一件事是什么？

可选补充“使用了哪个工具或参考、解决了什么问题、有哪些限制”。工具信息来自 M09 资源或用户引用的链接，记录当时使用条件与成本，不因为选择某个 AI 工具就推断成员具备某项能力。

输入允许“不知道”“没有记录”“不愿分享”。AI 只能依据用户输入和有权限的项目记录整理，缺少数据时标注“无法确认”。不自动对成员性格、天赋或真实能力作结论。

### 5.2 经验卡字段

| 字段 | 示例与用途 |
| --- | --- |
| 标题 | “在功能冻结前准备演示素材” |
| 问题场景 | 新人小队、短时赛事、需要演示视频 |
| 原因/证据 | 视频任务在最终检查点才开始，已确认计划和任务记录可查 |
| 建议步骤 | 开发中记录素材；设置视频负责人；提前试上传 |
| 适用条件 | 同类材料要求、团队具备素材整理人手 |
| 不适用/未知 | 与本次平台上传限制无关的比赛不能直接照用 |
| 来源项目与版本 | 关联项目、任务、复盘版本，不内嵌队友私人回答 |
| 使用工具与参考 | 可选 `resourceId` / 项目收藏引用，说明具体用途与使用限制；不保存工具账号或密钥 |
| 确认人与时间 | 谁确认了该建议，何时确认 |
| 可见范围 | `personal` 或 `project`；首版不默认公开 |

经验卡是“有条件的建议”，不是“通用成功公式”。重复参赛出现反例时可标为 outdated 并补充适用范围，不抹掉历史记录。

## 6. 业务规则与权限

1. 团队复盘属于项目，项目成员可看已共享内容；个人笔记属于本人，项目管理员默认不可读。
2. 成员可以提交本人记录；发布共同结论由项目管理员确认，或首版指定复盘负责人确认。采用哪种方式待确认，必须保留来源作者与不同意见。
3. AI 草稿与人确认版本分别记录。团队结论不能因为某次生成自动覆盖已确认复盘。
4. AI 不使用未经共享的原始测评、个人笔记或其他项目数据。模型输入清单能说明使用了哪些字段与记录版本。
5. 分工是否合适要结合任务交付、验收、成员反馈；提交数量、代码行数、活跃时长不能单独当作贡献或能力指标。
6. 缺失进度记录时说明“无更新”，不能推断“未工作”；没有正式提交记录时说明“未记录”，不能推断“未提交”。
7. 经验复用是一项显式操作，用户选择卡片和字段，并看到来源、适用条件与待核验项。
8. 新项目不继承旧截止时间、旧赛事资格、仓库授权、成功提交状态。旧测评只在本人同意且版本适用时作为过往证据，不能作为当前能力保证。
9. 导出仅包含请求人有权查看的数据；默认剔除凭据、他人原始测评、私人笔记、撤回共享内容与敏感附件。
10. 复盘删除/共享撤回遵循 M01 数据政策；共同项目中的必要交付记录不能被某人删除账号后静默破坏。
11. 归档项目仍能查看有权访问的经验；编辑需要恢复或另存新版本。AI 失败不阻止人工复盘。
12. 工具使用记录服务于下一次选择与踩坑提醒，不作为能力排名依据；复用时重新核验可用性、费用、账号要求、技术栈、许可与比赛允许的 AI 使用范围。记录官方/原始链接、当时核验时间；设计参考不意味着图片、品牌或组件代码获许可。
13. AI 草稿中的资源推荐只允许引用 M09 已审核 Resource ID；没有匹配资源时说明暂无资源，不编造网址。用户人工留下的外部工具经历可以保存，但标注成员记录/待核验，不能自动成为推荐或审核事实。

## 7. 实体与 API 建议

接口示例是待实施设计，不代表已有服务。API 前缀统一 `/api/v1`。

| 实体 | 关键字段 |
| --- | --- |
| `SubmissionRecord`（只读引用） | `projectId, eventId, stageId, requirementsVersion, platformUrl, submittedAt, verificationSource, repositoryCommitSha?, status, evidenceRefs`；M06 为事实所有者，来源与状态枚举见第 4 节 |
| `DeliveryVerification`（只读引用） | M06 的 `id, projectId, repositoryCommitSha?, verifierId, verifiedAt, environmentSummary, steps, outcome, blockers, evidenceRefs`；本模块不另建验收表或写入服务 |
| `Retrospective` | `id, projectId, authorId, scope, status, answers, inputSnapshotVersion, version` |
| `RetrospectiveVersion` | `retrospectiveId, content, sourceType, modelVersion?, confirmedBy?, createdAt` |
| `ExperienceCard` | `id, ownerId, sourceProjectId, title, scenario, advice, conditions, evidenceRefs, visibility, status, version` |
| `ExperienceReuse` | `experienceCardId, sourceVersion, targetProjectId, appliedFields, appliedBy, createdAt` |
| `ExportJob` | `requestedBy, scope, format, status, expiresAt, resultRef` |

建议接口：

| 接口 | 行为 |
| --- | --- |
| `GET /projects/{id}/delivery-summary` | 汇总三种状态，标明来源、时间与未知项 |
| `POST /projects/{id}/delivery-verifications` | M07 页面调用 M06 事实服务的同一个接口；M06 校验权限、记录验收和事件，本模块不重复实现 |
| `POST /projects/{id}/retrospectives` | 新建个人/项目复盘草稿 |
| `PATCH /retrospectives/{id}` | 校验本人或适用项目权限；带 `expectedVersion` |
| `POST /retrospectives/{id}/generate` | 异步生成草稿，冻结有权读取的输入快照 |
| `POST /retrospectives/{id}/confirm` | 人确认草稿版本，记录确认人 |
| `GET /experience-cards` | 仅返回本人有权访问的卡片 |
| `POST /experience-cards` | 从确认复盘提炼或人工创建，保留证据 |
| `PATCH /experience-cards/{id}` | 修改可见性、适用条件、状态，记录版本 |
| `POST /projects/{id}/experience-reuses` | 显式选择卡片与字段，校验目标项目权限 |
| `POST /projects/{id}/exports` | 异步导出允许的数据，不导出授权凭据 |

生成任务示例：

```json
{
  "retrospectiveId": "retro_example",
  "inputVersion": 4,
  "include": ["confirmed_plan", "task_blockers", "delivery_summary"],
  "scope": "project"
}
```

`include` 只是请求范围，服务端仍按权限过滤。生成输出需校验引用、项目归属、日期和状态；不存在的任务或无法读取的证据不能进入已确认经验。

## 8. 异常与降级

| 情况 | 处理 |
| --- | --- |
| 模型不可用或成本上限到达 | 人工复盘表、原记录、导出可继续使用；显示生成失败与合理重试 |
| 模型编造记录或引用 | 结构化校验失败，保留草稿但不确认；用户补充或删除结论 |
| 仓库删除、变私有或链接失效 | 保留历史版本标识，标记当前不可访问；不伪造可下载内容 |
| 平台无法核验提交 | 明确显示用户自报/未知，不影响记录复盘 |
| 两人同时编辑共同复盘 | 版本冲突，支持比对/另存；不能静默覆盖 |
| 数据共享被撤回 | 后续访问过滤；受影响经验卡标记依据变化，复核后再用 |
| 导出大文件或超时 | 异步任务显示进行中/失败，限期下载；不让页面无限等待 |
| 参赛失败或错过截止 | 可记录原因与改进，不能自动发布羞辱性评价 |

## 9. 依赖与事件

- M01：个人/项目可见性、数据删除与导出权限。
- M02：项目目标、阶段、成员、活动记录；[项目与团队规划](02-参赛项目与团队.md)。
- M03：确认规则及其版本，用于解释漏交材料等事件，不重新无来源解读。
- M04：已共享的分工理由及版本，不消费未经同意的原始测评。
- M05：计划、任务变更、卡点、验收记录；只记录已发生事实。
- M06：仓库真实保存结果、材料清单、`DeliveryVerification` 与 `SubmissionRecord`；M07 只读或调用原服务，不重复实现事实写入。
- M09：关联使用的工具与设计灵感；复盘保存适用条件，工具推荐不等同于能力判定或效果保证。

消费 M06 事件：`GitSaveSucceeded`、`DeliveryValidationRecorded`、`SubmissionRecorded`；M07 发布：`RetrospectiveConfirmed`、`ExperienceCardConfirmed`、`ExperienceCardVisibilityChanged`、`ExperienceReused`。跨模块事件带对象 ID、版本与时间，不传私人正文。复盘确认可以建议项目进入复盘阶段，但阶段转移仍记录用户动作。

## 10. 开发任务

| 任务 | 交付与依赖 |
| --- | --- |
| M07-T01 三类事实引用 | 与 M06 统一 SubmissionRecord/DeliveryVerification 字段、来源、阶段与接口；本模块只读引用，避免同义字段分裂 |
| M07-T02 交付概览 | 读取仓库、验收、提交记录，覆盖未知/失败/自报状态 |
| M07-T03 人工复盘表 | 私人/项目范围、自动草稿保存、版本冲突处理；无模型也可完成 |
| M07-T04 AI 整理适配 | 权限过滤输入快照、结构化输出、证据校验、超时/成本限制 |
| M07-T05 经验卡与检索 | 人确认、证据来源、范围/失效说明、本人可见列表 |
| M07-T06 选择性复用 | 接入新建项目，明确哪些内容复制、哪些需要重新核验 |
| M07-T07 导出与删除 | Markdown/JSON 导出脱敏、下载有效期、共享撤回处理 |
| M07-T08 实际参赛复盘 | 找真实队伍验证复盘负担、卡片可理解性和下次复用动作 |

M07 可以在主流程贯通后完成轻量版。首轮优先人工复盘与证据链接，AI 整理和搜索体验在基础数据可信后迭代，不让复盘拖延核心提交能力。

## 11. Given / When / Then 验收

1. **Given** 仓库保存成功但无运行验收、无提交记录；**When** 打开交付概览；**Then** 只显示保存成功，其他两项显示待处理/未记录。
2. **Given** 队员手动记录正式提交；**When** 查看状态；**Then** 展示“队员记录已提交”、记录时间与来源，不写成平台核验成功。
3. **Given** AI 模型不可用；**When** 填写并保存复盘；**Then** 人工内容正常保存、可查看导出，只有 AI 整理显示失败。
4. **Given** 成员有私人笔记和原始测评；**When** 管理员生成共同复盘；**Then** 这些内容未进入输入与结果，只读取已共享证据。
5. **Given** 任务没有更新记录；**When** AI 解释延期原因；**Then** 标记资料不足，不断言成员没有工作。
6. **Given** 有已确认经验卡；**When** 复用到新比赛；**Then** 卡片和来源被记录，旧截止时间、仓库授权和提交成功状态不继承。
7. **Given** 用户只能查看部分项目数据；**When** 导出；**Then** 只导出允许字段，不包含他人私人笔记、测评正文或令牌。
8. **Given** 经验卡依据被撤回共享或失效；**When** 下一次打开或复用；**Then** 提醒证据变化，用户确认适用性后再使用。

## 12. Constitution Check

| 原则 | 本模块落实 |
| --- | --- |
| I 可执行流程 | 围绕实际交付与下一次参赛复用，控制复盘题量；工具经验说明实际用途，浏览不当作完成 |
| II 可追溯 | 规则、任务、交付引用版本与来源；工具引用来源/核验时间、费用/许可等未知；AI 推荐审核 Resource ID，不编造链接 |
| III 分工依据 | 不用提交数评价能力，不公开原始测评，分工反馈有证据 |
| IV 可交付规划 | 回顾估算/实际差异，下一次重新核验容量，不照搬截止时间 |
| V GitHub 真实状态 | 文件保存、运行验收、正式提交独立，不假成功 |
| VI 隐私隔离 | 私人笔记默认本人可见；导出、共享撤回、删除按权限 |
| VII 可维护 | M06 写入保存/验收/提交事实、M09/M08 管理资源内容，M07 只读消费和整理，不重复创建真相源；不扩为资源抓取平台 |
| VIII 验证行为 | 三状态、输入权限、导出脱敏、选择性复用与 Resource ID 审核校验需自动验证 |
| IX 失败恢复 | 无模型也可复盘，失效链接保留历史，失败可恢复 |

## 13. 风险、待决与衡量

**风险：** 用户可能赛后不愿填表；资料不完整时 AI 会编造归因；私人感受可能误共享；旧经验不适合新赛事；公开评价会让年轻成员承受不必要的标签；记录保留会增加存储和数据处理负担。

**待确认：** 首版是否需要 AI 草稿、共同复盘确认人、经验卡共享粒度、导出格式、附件是否支持、数据保留期与删除流程、下一次参赛复用入口位置。默认允许个人私有笔记，不要求所有队员必须共同给出一致意见。

**建议指标：** 从开始到保存复盘的时间、实际完成率、人工修改 AI 结论比例、证据缺失比例、下一场比赛选择复用的卡片数、因旧规则误用产生的问题。指标只用于验证产品帮助，不作为成员成绩榜。第一轮验收关注一支真实队伍能保存可读的复盘，并在下一次创建项目时选择至少一条适用经验。
